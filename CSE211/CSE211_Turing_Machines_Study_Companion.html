Turing Machines

From "why finite automata aren't enough" all the way to "a Turing machine can simulate your laptop, and vice versa" — covering Lectures 4, 5 and 6, built to survive an exam.

01Why Turing Machines

Every automaton you've built so far — DFA, NFA, PDA — is a machine with a bounded kind of memory. A DFA remembers nothing but "which state am I in" (a fixed, finite amount of information). A PDA gets a stack, which is unbounded, but disciplined: you can only touch the top. Neither can be regarded as a genuinely general model of computation.

Here's the proof by example. Take the language

A language no PDA can recognize

L = { aⁿbⁿcⁿ | n ≥ 0 }

A PDA can check "equal number of a's and b's" by pushing a's and popping on b's. It can check "equal number of b's and c's" the same way. But it cannot check both simultaneously — by the time it needs to compare the c-count against the a-count, the a-count has already been consumed matching the b's. One stack isn't enough to remember two independent quantities at once. (You'll meet the formal proof of this — the pumping lemma for context-free languages — as a corollary once you have this vocabulary; for now, take it as the motivating gap.)

A Turing machine closes that gap. It can recognize aⁿbⁿcⁿ, and a great deal more besides — it is, in a precise sense, as powerful as any computer you own.

The core idea

A Turing machine is a finite automaton bolted onto a single tape of infinite length, on which it can both read and write. The "program" — the finite control — looks exactly like a DFA's transition diagram. What's new is the tape: instead of the input flying past a read-only head in one direction, the TM gets a scratchpad it can revisit, overwrite, and wander across in either direction, forever if it wants to.

That's the entire conceptual leap. Read/write access to unbounded memory, with a head that can move both ways. Everything else in this course — the formal 7-tuple, the programming tricks, multitape variants, the equivalence with real computers — is working out the consequences of that one idea.

Named after Alan Turing — who was he thinking about?

Alan Turing (1912–1954) introduced this model in 1936, before electronic computers existed, to answer a purely mathematical question: is there a mechanical procedure that can decide, for any mathematical statement, whether it's provable? (Hilbert's Entscheidungsproblem.) Turing's answer was "no" — and to prove a negative like that rigorously, he first had to pin down, mathematically, what "mechanical procedure" even means. The Turing machine is his answer: the most primitive machine that can still do everything a step-by-step mechanical procedure could do. That it later turned out to be exactly as powerful as a general-purpose computer wasn't the original goal — it fell out for free.

02The Formal Machine

Picture first

A Turing machine has:

  • A finite control — a state, exactly like a DFA's.
  • A tape, divided into cells, extending infinitely in both directions. Each cell holds one symbol from a finite alphabet.
  • A tape head, positioned over one cell at a time (the machine is "scanning" that cell), that can read the symbol there, overwrite it, and then move one cell left or right.

Initially the input string sits on the tape starting at the leftmost cell, the head sits on the leftmost input symbol, and every other cell — infinitely many in both directions — holds a special reserved symbol called the blank, written B. The blank is a tape symbol, but never an input symbol: no string you feed the machine is allowed to contain a B.

One move, precisely

A move is a function of (current state, symbol under the head). In one move the TM:

  1. changes state (optionally to the same state it was already in),
  2. writes a tape symbol into the scanned cell, replacing whatever was there (optionally the same symbol — an effective no-op write), and
  3. moves the head one cell left or right.

This formalism requires a move every step — there is no "stay put" option. (You'll meet machines later in the course that add an S = stay option; it's a notational convenience, not extra power.)

The transition function, unpacked

δ takes a state and a tape symbol, and — if it's defined there — returns a triple:

δ(q, X) = (p, Y, D)

  • p ∈ Q — the next state
  • Y ∈ Γ — the symbol written into the scanned cell, replacing X
  • D ∈ {L, R} — which way the head moves
Trap: δ is a partial function

Nothing forces δ to be defined for every (state, symbol) pair. Where it's undefined, the machine simply halts — this is the mechanism used for rejection. There's no explicit "reject and stop" instruction; you reject a string by constructing your δ so the machine gets stuck on it. When you design a TM, "what happens on inputs I didn't plan for" is not an afterthought — it's how half your rejecting behavior gets implemented.

Notational conventions

The course (following Hopcroft–Ullman) is consistent about letters, and it pays to internalize this so you can read someone else's TM construction fluently:

  • Lower-case letters near the start of the alphabet (a, b, c, …) — input symbols.
  • Capital letters near the end (X, Y, Z, …) — tape symbols that may or may not be input symbols (B is always reserved for blank, regardless of where it sits alphabetically).
  • Lower-case letters near the end (w, x, y, z) — strings of input symbols.
  • Greek letters (α, β, γ) — strings of tape symbols (may include blanks/working symbols).
  • q, p, and nearby letters — states.

03Instantaneous Descriptions

A PDA's configuration was a triple: (state, remaining input, stack). A TM's tape is infinite, so at first it looks like you'd need infinite information to describe a snapshot. You don't — because after any finite number of moves, the machine can only have visited finitely many cells.

Instantaneous description (ID)

Every ID has an infinite prefix and infinite suffix of cells the machine has never touched — necessarily all blank (or, in edge cases discussed below, holding original untouched input). So we only ever write down the cells strictly between the leftmost and rightmost nonblank cell — everything outside that window is uniformly blank, forever, and doesn't need stating.

To show where the head is and what state we're in, we embed the state name into the tape string itself, writing it immediately to the left of the cell being scanned:

X₁X₂ … Xᵢ₋₁ q Xᵢ Xᵢ₊₁ … Xₙ

This means: q is the current state, the head is scanning the i-th symbol from the left, and X₁…Xₙ is everything on the tape between the leftmost and rightmost nonblank cell. (Two things have to line up for this to be unambiguous: no state name is ever allowed to double as a tape symbol — trivially arranged by renaming — and there's a special convention for when the head sits at or past the blank boundary, covered just below.)

The move relation ⊢

We write ID₁ ⊢ ID₂ ("ID₁ yields ID₂") for one move of the machine, ⊢* for zero-or-more moves — exactly the PDA notation, carried over.

L
Moving left — if δ(q, Xᵢ) = (p, Y, L):
X₁…Xᵢ₋₁ q Xᵢ Xᵢ₊₁…Xₙ  ⊢  X₁…Xᵢ₋₂ p Xᵢ₋₁ Y Xᵢ₊₁…Xₙ
the state jumps to before Xᵢ₋₁, since the head is now one cell further left, and Xᵢ gets overwritten to Y in place.
R
Moving right — if δ(q, Xᵢ) = (p, Y, R):
X₁…Xᵢ₋₁ q Xᵢ Xᵢ₊₁…Xₙ  ⊢  X₁…Xᵢ₋₁ Y p Xᵢ₊₁…Xₙ
Trap: the four boundary exceptions

The rules above silently assume there's tape on both sides to shuffle into. Four situations break that assumption, and each needs its own handling — these are exactly the cases where an ID grows or shrinks by one cell:

situationwhat happens
i = 1, move Lhead was already at the leftmost known cell and steps further left, into virgin blank territory: qX₁X₂…Xₙ ⊢ pBYX₂…Xₙ — a fresh B appears on the left.
i = n, Y = B, move Lthe rightmost cell gets blanked and the head steps off it leftward — that blank rejoins the infinite trailing blank run and is simply dropped from the ID: X₁…Xₙ₋₁qXₙ ⊢ X₁…Xₙ₋₂pXₙ₋₁ (one cell shorter).
i = n, move Rsymmetric to the first case, but on the right: a fresh B appears.
i = 1, move R, Y=Bsymmetric to the second case: qX₁X₂…Xₙ ⊢ pX₂…Xₙ, the ID shrinks from the left.

The unifying idea: the written-down ID always shows exactly the nonblank window, so writing a blank at an edge shrinks it, and moving past a known edge into unexplored territory grows it.

Why this matters beyond bookkeeping

Every worked example below is really just a long ⊢-chain. Being fluent with this notation is what lets you read (and write) a full accepting computation for an exam question in one line per step instead of drawing the whole tape each time.

04Worked Example: 0ⁿ1ⁿ

Time to build one. Target language: L = {0ⁿ1ⁿ | n ≥ 1} — balanced blocks of 0's then 1's, at least one of each. (Note the strict n ≥ 1: this particular construction's start state has no rule for a leading blank, so — unlike the language definition you'll see quoted elsewhere for n ≥ 0 — this specific machine rejects the empty string. Worth noticing, because it's exactly the kind of off-by-one an exam loves to probe.)

The strategy

Repeatedly: cross off the leftmost remaining 0 (turn it into X), skip right past whatever's left of the unmarked block to find the leftmost remaining 1, cross it off too (turn it into Y), then walk back to the start and repeat. As the machine works, the visited portion of the tape always matches the regular expression X*0*Y*1* — some 0's already matched (now X), some not yet; some 1's already matched (now Y), some not yet.

Formally, M = ({q₀,q₁,q₂,q₃,q₄}, {0,1}, {0,1,X,Y,B}, δ, q₀, B, {q₄}):

stateon 0on 1on Xon Yon B
q₀(q₁,X,R)——(q₃,Y,R)—
q₁(q₁,0,R)(q₂,Y,L)—(q₁,Y,R)—
q₂(q₂,0,L)—(q₀,X,R)(q₂,Y,L)—
q₃———(q₃,Y,R)(q₄,B,R) ✓
q₄— accepting, halts —
q₀
the "find next unmatched 0" state. On a 0: cross it to X, move right, go hunt for the matching 1 (q₁). On a Y (all 0's exhausted): every 0 has been matched — switch to the cleanup sweep (q₃).
q₁
skip right over remaining 0's and already-matched Y's. On the first raw 1 found: cross it to Y, reverse direction (q₂).
q₂
skip left back over 0's and Y's. On hitting the rightmost X (the boundary of already-matched 0's): step right onto the next unmatched 0, back to q₀.
q₃
sweep right over the remaining Y's, confirming no stray 1 is left. Hit a blank → accept (q₄).
Trap: why does q₃ exist at all — why not accept the moment the last 0 is matched?

Because matching every 0 doesn't prove there's no extra 1 left over. Input 001 would otherwise slip through: both 0's get matched to the first two 1's, but a third 1 remains unconsumed. State q₃'s entire job is to walk across everything to the right of the last matched 0 and confirm it's only Y's before the blank — if it meets a bare 1 instead, δ(q₃,1) is undefined and the machine halts without accepting. This is a general pattern: matching a prefix is not the same as matching the whole string, and a well-designed TM proof-reads its own work before accepting.

Try it — step through the machine yourself

Pick a preset or type your own string of 0's and 1's, then step or press play. Watch the head; the current rule fires below the tape.

Transition diagram

Same machine, drawn as a graph. Arcs are labeled X/YD — read symbol X, write symbol Y, move direction D.

Reading transition diagrams — the fixed rules

Nodes = states. An arc from q to p labeled X/YD means δ(q,X) = (p,Y,D); D is drawn as ← or → rather than written out. "Start" with an arrow marks q₀. Double circles mark accepting states. The one thing you cannot read off the diagram is which symbol is the blank — by convention it's B unless stated otherwise.

06Computing Functions

So far a TM has been a language recognizer — a fancy accept/reject box. That's the modern framing. But Turing's own original picture was different: he thought of the machine as computing integer-valued functions, with integers written in unary — the number k represented as a block of k identical symbols. The machine computes by growing, shrinking, or relocating those blocks on the tape. Since it's not accepting a language, the 7th component (F, the accepting states) is simply omitted — you'll see machines specified as 6-tuples in this mode, and that omission is deliberate, not sloppy notation.

Worked example — proper subtraction (monus)

Define m −̇ n = max(m − n, 0) — ordinary subtraction, floored at zero so it never goes negative. Input tape: 0ᵐ 1 0ⁿ (a block of m zeros, one separator 1, a block of n zeros). Output: the machine halts with 0^(m−̇n) on the tape, nothing else.

The algorithm

Same "cross things off and match them up" idea as the 0ⁿ1ⁿ machine, but now matching consumes a symbol from each block per round rather than checking equality:

1
Find the leftmost remaining 0 of the first (m-) block; blank it.
2
Search right, past the separator, for the leftmost remaining 0 of the second (n-) block; convert it to a 1 (a "used" marker).
3
Walk back left until hitting the blank boundary just created in step 1, step one cell right — that's the next 0 of the m-block — and repeat.

The repetition ends one of two ways:

A
Searching for a 0 in the n-block, the machine hits a blank instead. Every one of the n zeros has already been converted to a 1 — the n-block is exhausted, but the m-block still had an unmatched 0 left (the one blanked at the start of this round). So m > n: blank out the separator and all the "used" 1's, restore that one over-consumed cell back to a 0, and halt. What's left on the tape is exactly the untouched tail of the m-block, now made contiguous — m −̇ n zeros.
B
At the very start of a round, the machine looks for a 0 in the m-block and finds a 1 (the separator) instead. Every 0 in the m-block is already blanked — so n ≥ m, meaning m −̇ n = 0. Blank out everything else that remains (separator and n-block) and halt on a completely empty tape.
Trap: case A's "restore one cell" step is the single easiest place to get this wrong

The natural first instinct is: "we hit a blank while hunting in the n-block, so just leave everything left of the separator as-is and blank the separator + used 1's." That's wrong by exactly one — because the current round had already optimistically blanked a fresh 0 from the m-block before discovering there was no partner for it in the n-block. If you don't give that cell back, your machine reports m −̇ n − 1 instead of m −̇ n. The fix is to have the cleanup sweep travel all the way back past the untouched tail of the m-block (skipping over those 0's unchanged) until it hits the first blank cell — that's the over-consumed one — and turn only that one back into a 0. Trace it by hand for m=3, n=1 if this doesn't click immediately; it's a genuinely subtle off-by-one, and exactly the kind of detail an exam question likes to test.

Try it — with the lecture's own example (m=2, n=4)

This is a verified, runnable realization of the algorithm above (7 states, matching the lecture's q₀…q₆ naming). Presets replay the exact 0²10⁴ trace from the slides plus a few others; the custom box accepts any m,n pair.

Why unary, and why does this feel so wasteful?

It is wasteful — representing the number one million takes a million tape cells. That's precisely why, once the course reframes TMs as language recognizers, nobody computes in unary again; you'll use binary (or leave numbers implicit in string structure) from here on. Unary survives in this one corner of the course purely because it makes "the machine scans past a whole block" trivial to describe and verify — no carrying, no place value, just counting matched pairs. It's a pedagogical stepping stone, not the model you're expected to compute with going forward.

07Language & Halting

The language of a TM

Definition

For M = (Q, Σ, Γ, δ, q₀, B, F), the language L(M) is the set of strings w ∈ Σ* such that

q₀w ⊢* αpβ  for some p ∈ F and any tape strings α, β

In words: start the machine on w, run it, and if it ever reaches an accepting state — regardless of what's elsewhere on the tape at that moment — w ∈ L(M). This is exactly the definition silently assumed back in the 0ⁿ1ⁿ example.

Recursively enumerable languages

The class of languages accepted by some Turing machine is called the recursively enumerable (RE) languages. ("Recursively enumerable" is a name inherited from an older, independently-developed formalism that turns out to define the exact same class of languages — you'll meet the term again heavily once decidability is on the table.)

Acceptance by halting

There's a second, commonly-used notion of "accepting" worth having in your vocabulary now, even though the course's default is acceptance-by-final-state:

Halting

A TM halts when it's in some state q, scanning symbol X, and δ(q,X) is undefined — there's simply no move to make. This is exactly the mechanism flagged as a trap back in the formal definition: every TM you've built already halts-to-reject constantly, every time it falls off the edge of its own δ table.

For a language recognizer, "accept" and "eventually enter an accepting state" coincide — but a machine can also halt without accepting (reject), and, as you'll see very shortly once nontermination enters the picture, a machine is not guaranteed to halt at all on every input.

A function-computing machine's relationship to halting

The monus machine above was never designed to accept a language — it has no F. Its entire "correctness" claim is a halting claim: for every string of 0's, 1's, no matter what it looks like, that machine provably halts (either via the case-A cleanup or the case-B cleanup — those two branches are exhaustive). That it always halts, on every input, is worth noticing precisely because it won't be true of every machine you meet later in the course — some machines run forever on some inputs, and telling in advance whether a given machine will halt on a given input turns out to be uncomputable in general. Filed away for later; for now, just notice that "does this thing halt" is a real, nontrivial property to have to argue for.

08Programming Tricks: Storage in the State

A TM is exactly as powerful as a conventional computer — but the raw 7-tuple gets unwieldy fast for anything nontrivial. The rest of this section is a toolkit of three standard tricks for taming that. All three are pure notation: none of them extend what a TM can compute. Every trick below compiles down to an ordinary flat δ table; they just make the design — and its correctness argument — dramatically easier to read and write.

The trick

Let a state be a tuple instead of an atomic symbol: [q, A] is "control position q, remembering data value A." Formally this changes nothing — Q is still just a finite set, it's simply a set of pairs now instead of a set of bare labels — but it lets you describe transitions systematically, as functions of the remembered data, instead of writing out one state per remembered value by hand.

Worked example — 01* + 10*

Build M = (Q, {0,1}, {0,1,B}, δ, [q₀,B], {[q₁,B]}) that remembers the first symbol it reads and rejects if that symbol ever reappears — i.e. accepts exactly 01* ∪ 10*. (A trivially regular language — this is a demonstration of the technique, not a machine that needed a TM's power.)

States: Q = {q₀,q₁} × {0,1,B} — a control component (q₀ "haven't read yet" / q₁ "checking the rest") crossed with a data component (which symbol was first seen, or B if none yet).

#rulemeaning
1δ([q₀,B], a) = ([q₁,a], a, R)read the first symbol a (0 or 1), store it, move right, switch to "checking" mode
2δ([q₁,a], ā) = ([q₁,a], ā, R)ā is the complement of a — skip over every symbol that differs from the stored one
3δ([q₁,a], B) = ([q₁,B], B, R)reached the end cleanly → accepting state [q₁,B]

Notice there is deliberately no rule for δ([q₁,a], a) — encountering the stored symbol a second time has no transition, so the machine halts without accepting. The absence of a rule is doing real work here, exactly as flagged earlier.

Lecture's own trace, input 01111

[q₀,B] 01111
⊢ 0[q₁,0] 1111
⊢ 01[q₁,0] 111
⊢ 011[q₁,0] 11
⊢ 0111[q₁,0] 1
⊢ 01111[q₁,0] B
⊢ 01111B[q₁,B] B   ← accept

09Programming Tricks: Multiple Tracks

The trick

Think of the tape alphabet as tuples: each cell holds a symbol from Γ where Γ itself is a Cartesian product, e.g. Γ = {B,∗} × {0,1,c,B}. Visually, imagine the tape ruled into horizontal "tracks" stacked in the same cell — one track might hold the real data, another might hold nothing but a checkmark. Again: zero extra power. It's exactly the storage-in-state trick, just applied to the tape alphabet instead of the state set.

Worked example — the copy-checker Lwcw

Target language (genuinely not context-free — no PDA can do this one):

Lwcw = { w c w  |  w ∈ {0,1}⁺ }

Strategy: use a second track as a checkmark track. Pick up the leftmost unchecked symbol before the c, remember it (storage-in-state again), skip past the c, find the leftmost unchecked symbol after it, compare, checkmark both if they match, and repeat until everything's checked.

M = (Q, Σ, Γ, δ, [q₁,B], [B,B], {[q₉,B]}) where Γ = {B,∗} × {0,1,c,B} — track 1 is blank-or-checked (B/∗), track 2 is the real symbol.

#rulemeaning
1δ([q₁,B],[B,a]) = ([q₂,a],[∗,a],R)pick up symbol a before c, check it off, remember it, head right
2δ([q₂,a],[B,b]) = ([q₂,a],[B,b],R)skip right, searching for c
3δ([q₂,a],[B,c]) = ([q₃,a],[B,c],R)found c, keep going right
4δ([q₃,a],[∗,b]) = ([q₃,a],[∗,b],R)skip already-checked symbols after c
5δ([q₃,a],[B,a]) = ([q₄,B],[∗,a],L)match found — check it off, drop the stored symbol, reverse
6δ([q₄,B],[∗,a]) = ([q₄,B],[∗,a],L)move left over checked symbols
7δ([q₄,B],[B,c]) = ([q₅,B],[B,c],L)back at c, keep moving left — now must decide what's next
8δ([q₅,B],[B,a]) = ([q₆,B],[B,a],L)symbol left of c is unchecked → more work remains
9δ([q₆,B],[B,a]) = ([q₆,B],[B,a],L)keep sweeping left over unchecked symbols
10δ([q₆,B],[∗,a]) = ([q₁,B],[∗,a],R)found the checked/unchecked boundary → back to q₁, restart cycle
11δ([q₅,B],[∗,a]) = ([q₇,B],[∗,a],R)symbol left of c is already checked → the left half is fully done
12δ([q₇,B],[B,c]) = ([q₈,B],[B,c],R)head back right, past c
13δ([q₈,B],[∗,a]) = ([q₈,B],[∗,a],R)skip checked symbols on the right side too
14δ([q₈,B],[B,B]) = ([q₉,B],[B,B],R)blank reached with nothing unchecked remaining → accept ✓

If step 13 meets a bare (unchecked) 0 or 1 instead of running clean to a blank, there's no rule for it — halt, reject. That's how "the right half had leftover unmatched symbols" gets caught.

Trap: the state does double duty — don't lose track of which branch you're in

States q₅ through q₈ exist purely to resolve one binary question — "is the symbol immediately left of c checked or not?" — and the two answers lead to completely different onward paths (q₆→q₁, a fresh cycle; vs q₇→q₈→q₉, straight to acceptance). It's easy while tracing by hand to forget which of those two branches you're currently walking. Anchor yourself with the plain-English question each state is answering, not just its number.

10Subroutines & The Binary Adder

The trick

Think of a TM as built from interacting components — "subroutines" — the same way you'd decompose a program into functions. A subroutine is a set of states with a designated start state; "calling" it just means transitioning into that start state from wherever you are. The catch: a TM has no call stack. There's no built-in mechanism to remember "where do I return to when I'm done." If the same piece of logic needs to be invoked from several different places and return to different places each time, the fix is blunt but effective: make separate copies of the subroutine's states, one per call site, each copy hard-wired to return to its own caller.

Worked example — binary addition

Tape layout: w₁ c w₂ c, where w₁ and w₂ are equal-length binary numbers written least-significant-bit first (a deliberate convenience — it lets the machine process a carry chain left-to-right, in the same direction it's already scanning). The sum gets written after the second c.

This combines both earlier tricks at once: multiple tracks (a checkmark track, exactly like Lwcw) plus storage in the state — but now storing three values at once: the two bits being added, and the carry. States are 4-tuples [q, a, b, cᵢ].

11Multitape Turing Machines

Every trick in the previous section left the machine model itself untouched — one tape, one head, a flat δ. Now we actually generalize the model: give the machine several tapes, each with its own independent head. Multitape machines are worth knowing for a very practical reason — they make it far easier to see how a TM can simulate a real computer (Section 14) or another TM, compared to constantly threading everything through a single tape. And crucially: the extra tapes add no language-recognizing power at all. That equivalence is the theorem this section proves.

The model

One finite control, k tapes, each with its own head, moving independently. In one move, the machine: enters a new state (function of the current state and all k scanned symbols); writes a symbol on each tape simultaneously; moves each head left, right, or stays put (the S option finally earns its keep here — multitape machines are exactly where "stay stationary" stops being cosmetic and becomes genuinely useful, since a head might have nothing to do on a given tape this step — you'll watch this happen live in the simulator below). The input starts on tape 1 only; every other tape starts entirely blank.

Feel it first: the same language, dramatically easier with two tapes

Section 9 built a 14-rule single-tape machine for Lwcw = {wcw | w ∈ {0,1}⁺} — checkmarks, four sweep-states, a lot of bookkeeping. Here's the closely-related language L = {w#w | w ∈ {0,1}⁺}, done with two tapes instead: copy the first half onto tape 2 as you read it, rewind tape 2, then walk both tapes forward together comparing symbol by symbol. Four states. No checkmarks needed at all — a second tape is the checkmark.

qcopy
read tape 1 left-to-right; copy every 0/1 straight onto tape 2 (both heads move right together). On seeing #: step tape 1's head past it, and start walking tape 2's head back to the left.
qrewind
tape 1's head holds still (the S move) while tape 2's head walks left, back to the start of the copy. The instant tape 2 hits blank, step it one cell right (onto the first copied symbol) and switch to comparing.
qcompare
step both heads right together as long as they agree. A mismatch has no rule to follow → halt-reject. Both heads hitting blank at the same moment → accept.
state: —
What the "fold into one tape" toggle is actually showing you

Flip the toggle mid-run. The folded view takes the exact same computation and repaints it as a single physical tape with four tracks stacked in each column: tape 1's symbol, a marker for where head 1 sits, tape 2's symbol, a marker for head 2. Column-by-column, that's precisely the "2k tracks" construction the proof below describes — you're not watching an analogy, you're watching the actual simulating machine's tape.

Theorem

Every language accepted by a multitape TM is recursively enumerable — i.e. some ordinary one-tape TM accepts it too.

Proof — simulate k tapes on one tape using 2k tracks

Let L be accepted by a k-tape TM M. Build a one-tape TM N whose single tape is organized into 2k tracks (recall: multiple tracks are free — Section 9). Half the tracks hold the literal contents of M's k tapes, one track each — exactly the "data1 / data2" tracks you just toggled into view above. The other half hold nothing but a single position-marker symbol each, recording where the corresponding head of M currently sits — the "marker1 / marker2" tracks.

To simulate one move of M, N must:

1
Sweep across its tape, visiting each of the k head-markers in turn, and record (in its own finite control) which symbol each one sits on. N tracks how many markers are to its left at all times, as a component of its own state, so it never loses its place mid-sweep.
2
Now knowing all k scanned symbols and M's current state (also stored in N's control), N knows exactly which move M would make.
3
Sweep across again, this time actually revisiting each marker, writing the new symbol on that track, and nudging the marker left or right as needed.
4
Update the state-component recording M's state. One move of M is now fully simulated.

N accepts exactly when the simulated M-state it's tracking is one of M's accepting states — so L(N) = L(M).

Theorem — the simulation's cost

The one-tape TM N simulates n moves of the k-tape TM M in O(n²) steps of its own.

Proof sketch

After n moves of M, no head marker can have drifted more than 2n cells from where it started (each move shifts a head by at most one cell). So a single sweep visiting every marker costs O(n) steps of N. Simulating one move of M therefore costs O(n) (plus O(k), a constant, for turning around); doing this for n moves costs O(n)·n = O(n²) total. Since k is fixed (doesn't grow with n), it disappears into the constant.

Trap: "no extra power" ≠ "no extra cost" — say both halves out loud on an exam

Multitape and single-tape TMs recognize exactly the same class of languages — that's the qualitative equivalence. But the quantitative cost of collapsing k tapes into one is real: an O(n)-time multitape algorithm becomes an O(n²)-time single-tape one. This distinction — same computability class, different complexity — is a recurring theme; get comfortable stating both halves of an equivalence result rather than only the "can it be done at all" half.

12Nondeterministic Turing Machines

The model

Same idea as NFA-vs-DFA. Now δ(q,X) returns a set of triples {(q₁,Y₁,D₁), …, (qₖ,Yₖ,Dₖ)} rather than a single one, and the machine may pick any of them at each step. (One constraint: it must pick a triple as a whole — it cannot mix-and-match a state from one option, a written symbol from another, and a direction from a third.) An NTM accepts input w if some sequence of choices leads from the initial configuration to an accepting state — exactly as for NFAs and PDAs, the existence of other, non-accepting branches is simply irrelevant.

Feel it first: a machine that genuinely guesses

Take Σ = {0,1} and the language "contains 11 somewhere." Here's an NTM with a real fork in it — not a disguised deterministic scan:

qs
scanning, looking for the start of a match. On a 0: only one option, keep scanning right. On a 1: two genuine options — either ignore it and keep scanning (this 1 might be a false start), or guess "this is the first half of 11" and jump to qm.
qm
the guess is being checked. If the next symbol really is a 1: confirmed, accept. If it's a 0: the guess was wrong — this branch simply has no rule to follow, and dies right there.

Every branch that guesses wrong dies quietly. The only thing that matters for acceptance is whether at least one branch, anywhere in the tree, survives to qacc. Watch the frontier of live configurations grow and shrink round by round:

What you just watched

Every dashed, struck-through chip is a branch that guessed wrong and quietly died — exactly step 2/3 of the proof below, "make k copies, one per choice," except now you can see the copies pile up and thin out round by round. The moment a green chip appears, that's the deterministic simulator's step 1 firing: "if the state is accepting, stop immediately." Everything else in the frontier at that instant is simply abandoned, unexplored.

Theorem

NTMs accept exactly the same languages as deterministic TMs. Nondeterminism buys convenience of design, not extra power — same story as NFA vs. DFA, once again.

Proof — simulate by breadth-first search over the tree of choices

Given NTM MN, build a deterministic multitape MD (equivalent to a one-tape TM, by the previous section's theorem) that explores every configuration MN could possibly reach, and accepts if any of them is accepting.

One tape of MD holds a queue of configurations (instantaneous descriptions) of MN, separated by a marker symbol, with one of them flagged as "current" — the one whose successors are presently being discovered. To process the current configuration, MD:

1
Reads off the current configuration's state and scanned symbol. If that state is accepting, MD accepts immediately and stops simulating entirely.
2
Otherwise, looks up how many choices MN has from this (state, symbol) pair — say k of them — and makes k copies of the current configuration, appended to the end of the queue.
3
Modifies each of the k copies according to a different one of the k choices.
4
Un-marks the old "current" configuration, marks the next one in the queue as current, and repeats from step 1.
Why a queue, and not a stack

This has to be breadth-first, not depth-first. If MD instead always exhausted one branch before trying the next (a stack / depth-first approach), it could get stuck forever down a single infinite non-accepting branch and never even try a sibling branch that accepts in two steps. A queue guarantees that after some finite amount of work, MD has tried every sequence of up to k moves for every k = 1, 2, 3, … — so if any branch accepts, MD is guaranteed to reach it eventually. In the widget above, that's exactly why we expand every chip in a round together, all at once, rather than chasing one chip all the way down before looking at its neighbors.

The cost of removing nondeterminism

If m is the maximum number of choices MN ever has from a single configuration, then after n moves MN could have reached as many as 1 + m + m² + ⋯ + mⁿ ≤ n·mⁿ distinct configurations. MD may have to explore all of them before finding an accepting one — exponential blowup in the worst case, even though the language recognized is identical.

Hold that number in mind — "removing nondeterminism can cost exponentially more time, even with zero change in what's computable" is one of the load-bearing ideas the rest of the theory course (NP, etc.) is built on.

13Restricted Models — Still Exactly As Powerful

Sections 11–12 generalized the model and found: no extra power. This section goes the other direction — restrict the model in various seemingly-limiting ways, and find the exact same thing: no loss of power. Seeing both directions hammers home how robust the "Turing machine" concept really is; a huge range of superficially different machines all land on the identical class of languages.

Semi-infinite tapes

The restriction

Instead of a tape infinite in both directions, allow the head to move only at-or-right of its initial position — the tape is infinite to the right only, with a hard wall on the left.

Why this loses nothing — the two-track fold trick

Simulate a two-way-infinite tape using a semi-infinite one with two tracks. The upper track holds cells X₀, X₁, X₂, … (the original tape from the initial head position rightward). The lower track holds X₋₁, X₋₂, … in reverse order — effectively, fold the left half of the original tape underneath the right half, like folding a ruler in half at the zero mark. A single marker symbol (∗) on the leftmost cell's lower track acts as an end-stop, so the head never tries to walk off the left edge. Every move on the original two-way tape translates to a move on one of the two tracks of the folded tape, with left/right sometimes swapping depending which track is active — a bookkeeping detail, not a power difference.

Multistack machines

The model

A k-stack machine is a deterministic PDA generalized to k independent stacks, reading input from an input source (not a tape) via its finite control, using one shared finite stack alphabet across all k stacks.

Recall a one-stack machine (an ordinary PDA) is strictly weaker than a TM — it can't do aⁿbⁿcⁿ, exactly Section 1's motivating example. Add a second stack, though, and the picture flips completely:

Theorem

A two-stack machine accepts exactly the recursively enumerable languages — the same class as a full Turing machine.

Feel it first: split the tape at the head

Here's the whole idea in one picture. Take any tape with a head somewhere on it. Everything strictly left of the head, reversed, becomes stack 1 — its top is whatever's immediately left of the head. Everything at-or-right of the head becomes stack 2, unreversed — its top is the currently-scanned symbol itself. The correspondence, stated precisely

A TM move at the head does exactly two things: write a symbol into the scanned cell, then shift the head one way. Translated to two stacks:

  • Write Y, then move right: replace the top of stack 2 with Y, then pop it off stack 2 and push it onto stack 1. Stack 2's new top is what was previously one cell further right.
  • Write Y, then move left: replace the top of stack 2 with Y (as always, the write happens to the currently-scanned cell first), then pop the top of stack 1 and push it onto stack 2. Stack 2's new top is now what used to be immediately left of the head.

One stack alone can't do this because a single stack only ever exposes one side of the head. A TM head needs both sides on tap — which is exactly why one stack tops out at context-free languages, while two recover full TM power.

The intuition, in words (same idea as above, without the widget)

Picture a TM's tape with the head at some cell. Split it there: everything left of the head, reversed, goes on stack 1 (top of stack 1 = cell just left of the head); everything right of the head goes on stack 2 (top of stack 2 = the currently-scanned cell). A left-move pops stack 1 and pushes onto stack 2 (or vice-versa for a right-move) — exactly simulating the tape head sliding one cell, using only push/pop.

Counter machines

The model

Same skeleton as a multistack machine, but each stack is replaced by a counter — a nonnegative integer the machine can increment, decrement (never below zero), and test only for zero-vs-nonzero (it cannot read off the counter's exact value). It's a stack that's forgotten everything except its height, and even that only coarsely.

Theorem

Every recursively enumerable language is accepted by some two-counter machine.

This one is the most surprising result in the section — a counter is an almost absurdly weak-looking piece of memory (no structure at all, just a number, and you can't even read it directly), yet two of them, wired to a finite control, recover full TM power. The construction (not shown here) works by having the counters' values jointly encode, via a clever numbering, a full stack's contents — reducing back to the two-stack result above.

Zooming out — the pattern across this whole section

Multiple tapes: no gain. Nondeterminism: no gain. A tape truncated to one direction: no loss. Stacks replaced by bare counters: no loss (once you have two of them). This is exactly what makes "Turing-machine computable" feel like a robust, natural boundary rather than an arbitrary one — you can push and pull on the model's details in many directions and land on the identical class of languages every time. That robustness is a big part of why the Church–Turing thesis (every reasonable notion of "mechanical computation" coincides with Turing-machine computation) is so widely believed.

14TMs ⟺ Computers

Time to close the loop the whole course has been driving toward. Section 1 opened with "a Turing machine can recognize more than a PDA." This section makes the much stronger claim precise: a Turing machine and an ordinary computer can simulate each other — and, importantly, can do so efficiently (polynomial-time overhead in each direction), not just "eventually, given unlimited time."

Why this needs care, not just a wave of the hand

"A computer can simulate a TM" is the easy direction — a computer program can maintain an array for the tape and a variable for the state, and that's basically it. "A TM can simulate a computer" is the direction worth actually building, since it's the one that turns "Turing machine" from a cute toy model into the foundation for everything complexity theory says about real computation. The argument below is informal by nature (unlike a TM, "a typical computer" isn't a mathematically pinned-down object) — but the construction is concrete enough to extract a real time bound from.

Setting up the simulation

Model a computer as: an unbounded sequence of memory words, each with an integer address 0,1,2,…, no bound on word length, and a stored program made of simple instructions (arithmetic/logic, data movement, control flow — think one MIPS-style instruction each). A multitape TM represents this with five tapes:

1
Memory tape — the entire memory, encoded as alternating (address, contents) pairs in binary, in numerical address order: $ 0*w₀ #1*w₁ #10*w₂ #11*w₃ …. The $ marks the start; * and # are markers separating an address from its contents, and one pair from the next.
2
Instruction counter — one binary integer: which memory address holds the instruction to execute next.
3
Memory address / working value — holds an address being looked up, then (once found) the contents at that address, moved wherever it's needed.
4
Computer's input file — the input the simulated program itself reads.
5
Scratch tape — working space, used e.g. when a value needs more room than was previously allocated for it (see "shifting over," below).

One instruction cycle

a
Search tape 1 from the $ rightward for the address matching the instruction counter (tape 2) — a straightforward left-to-right scan comparing binary strings.
b
Read the instruction's opcode (its first few bits: copy / add / branch / …) and operand address(es) (the remaining bits).
c
If an operand's value is needed, copy that address to tape 3, search tape 1 for it (same scan as step a), and copy its stored value back to tape 3.
d
Execute the instruction using that value; if it's not a jump, increment the instruction counter (tape 2) and loop back to step a.
Sample instruction executions — copy, addition, jump

Copy: locate the destination address on tape 1 (same scan as always) and overwrite its stored value. If the new value needs more room than the old one occupied — or less — use the shifting-over technique: copy everything to the right of the write point onto the scratch tape, write the new value in its correctly-sized slot, then copy the scratch tape's contents back immediately following it. (If the address doesn't exist on tape 1 yet, find the correct sorted insertion point and write both address and value fresh.)

Addition: locate the other operand's address, then perform an ordinary ripple-carry binary addition by scanning both values from their right (least-significant) ends — exactly the carry-propagation idea from the binary-adder TM in Section 10. Shift over if the result needs more space.

Jump: the simplest of the three — just copy tape 3 (the computed target address) onto tape 2 (the instruction counter) and restart the cycle. No search needed at all.

How fast is this simulation?

Theorem — the word-length constraint

Suppose a computer's instructions (i) each grow the length of the longest word on the tape by at most 1 bit, and (ii) each instruction, restricted to words of length k, can itself be carried out by a multitape TM in O(k²) steps or fewer. Then the TM described above simulates n computer-instructions in O(n³) of its own steps.

Proof sketch

After n instructions, no word or address on the simulated tape can exceed c+n bits (c a constant — the length of anything the fixed program itself mentions), and at most d+n distinct addresses can have been created (d another constant — the program's own size), each instruction creating at most one new one. So the whole simulated memory fits in O(n²) TM tape cells (a linear count of entries, each of linear length). Locating an address by linear scan, or carrying out one instruction on O(n)-length words per assumption (ii), each cost O(n²) TM steps; and shifting-over similarly costs at most O(n²), since it moves at most that much data. So one simulated instruction costs O(n²) TM steps, and n of them cost O(n³) total.

Chained with Section 11's O(n²) multitape-to-one-tape conversion, a single-tape TM simulates n computer instructions in O(n⁶) steps. Large-looking, but the point isn't the exact exponent — it's that the overhead is a fixed polynomial, not something that blows up with the size of the computation. That's exactly the property complexity theory needs: "tractable on a real computer" and "tractable on a TM" turn out to be the same notion, up to a polynomial factor, which is precisely why the whole theory of P and NP can be stated in terms of Turing machines without losing any real-world relevance.

Trap: why does the theorem's assumption (i) even need stating — isn't "each instruction adds at most 1 bit" obviously true?

No — and this is the one genuinely subtle wrinkle in the whole argument. Multiplication violates it: multiplying two m-bit numbers can produce a result of length 2m, not m+1. If a computer were allowed a single "multiply" instruction and repeatedly squared a growing word — start with 2, square it n times in a row — the word's length would double every step, reaching roughly 2ⁿ bits after n instructions. A TM simulating that would need exponential time, not polynomial, completely breaking the O(n³) bound above.

The fix used in this course: disallow multiplication as a primitive instruction (only allow instructions — like addition — that grow the longest operand by at most one bit), and instead build multiplication out of a sequence of up to m additions interleaved with left-shifts (exactly the grade-school long-multiplication algorithm). That keeps it computable, and keeps the total time for one multiplication of m-bit numbers proportional to m² — not exponential — restoring the polynomial bound. The moral: when someone hands you a "reasonable" instruction set and asks you to bound simulation time, check each instruction's output size against its input size before trusting a polynomial bound — a single unchecked exponential-growth instruction poisons the whole argument.

15Edge Cases & Traps — Cross-Cutting

A synthesis of the sharpest pitfalls scattered through every section above, gathered in one place for last-minute review. Each one has already been introduced where it belongs; this is the "make sure none of these have faded" pass.

1. δ being undefined is not a bug — it's how rejection is implemented

There is no "reject" instruction in the formalism. Every reject you've engineered across this whole page — the second occurrence of a stored symbol in the 01*+10* machine, a stray unmatched digit in Lwcw, an odd-count string in 0ⁿ1ⁿ — happened by deliberately leaving a (state, symbol) pair out of δ. When you design a machine, always ask explicitly: "what happens on inputs I haven't accounted for?" If the answer is "nothing, it just halts," check that halting there is actually correct rejection, not an accidental gap that lets something wrong slip through un-rejected.

2. Matching a prefix ≠ matching the whole string

The 0ⁿ1ⁿ machine needed state q₃ purely to sweep the tail and confirm nothing extra was left — matching every 0 to a 1 doesn't rule out leftover unmatched 1's (input 001 is the textbook counterexample). The Lwcw machine has the identical concern built into rule 14 (a stray unchecked symbol before the final blank means reject, not accept). Any time your algorithm's main loop terminates because "the first block ran out," ask what happens if the second block still has leftovers — that's usually a separate check you have to build in, not something that falls out for free.

3. Off-by-one errors in cleanup/bookkeeping phases are the single most common construction bug

The monus machine's case-A cleanup is the poster child: optimistically blanking a 0 from the m-block before confirming a partner exists in the n-block means that when no partner turns up, you've over-consumed by exactly one, and the cleanup sweep must explicitly walk back and restore it. This class of bug is invisible on "clean" test cases (m ≫ n, or m ≪ n) and only surfaces at the boundary (m ≈ n, or m = n exactly). When you verify your own TM designs — by hand or in code — deliberately test the boundary cases, not just the comfortable middle.

4. "No extra power" and "no extra cost" are two different claims — an exam wants both

Multitape vs. single-tape TMs: same languages, but O(n²) slower once collapsed to one tape. NTM vs. DTM: same languages, but potentially exponentially slower once determinized. If a question asks you to "discuss the relationship" between two machine models, a complete answer states the equivalence and quantifies the overhead — stopping at "they're equivalent" leaves real content on the table.

5. The pumping-length p is a black box — never assume it has a convenient value or property

This one's technically from the closure-properties/pumping-lemma lecture rather than the TM lectures directly, but it rhymes strongly with trap #3 and #6 here, and it's worth restating in this context: whenever an adversary (or, in the TM world, "the machine's own δ table") hands you a quantity you don't control, your construction has to work for every possible value of it — you don't get to assume it's prime, or even, or anything else convenient.

6. Multiplication silently breaks polynomial simulation bounds — check growth rates before trusting an O(nᵏ) claim

Covered in full in Section 14, but worth restating as a general reflex: any time you're asked to bound how long a TM takes to simulate some other computational process, check whether that process has an instruction whose output size can exceed its input size by more than an additive constant. A single such instruction (multiplication being the standard example) turns a claimed polynomial bound into an actual exponential one.

7. Don't confuse "halts" with "accepts," or "doesn't halt" with "rejects"

Three genuinely distinct outcomes exist for a TM run on a given input: (a) it halts in an accepting state — accept; (b) it halts in a non-accepting configuration because δ is undefined there — reject; (c) it never halts at all — runs forever. Loose exam language sometimes blurs (b) and (c) together as "rejects," but they are not interchangeable, and the distinction becomes load-bearing the moment decidability enters the course: a language where every "no" instance causes case (c) rather than case (b) is a fundamentally different — and weaker — kind of recognizable than one where every "no" instance halts cleanly.

16Practice Problems

Solutions are collapsed — attempt each one on paper (or by sketching a δ table) before revealing.

1. Design a TM (informally — states and the strategy, not a full δ table) that accepts { 0ⁿ1ⁿ2ⁿ | n ≥ 1 } over Σ = {0,1,2}.
Solution

Direct extension of the 0ⁿ1ⁿ strategy to three blocks. Repeatedly: cross off the leftmost remaining 0 (→X), skip right to the leftmost remaining 1 and cross it off (→Y), skip right further to the leftmost remaining 2 and cross it off (→Z), then sweep all the way back left to the boundary and repeat. Once no 0's remain (the head, at the top of the loop, meets a Y instead of a 0), sweep right confirming only Z's remain before the blank — exactly the same "don't just match a prefix" cleanup q₃ performed for two blocks. This is precisely the kind of extension exam questions love: "you've seen the two-block version, now do three" — the state count grows, but the strategy doesn't need a new idea, just one more matching pass per cycle.

2. A TM halts on input w but does not accept it. Is w necessarily not in L(M)? What if the machine runs forever on w instead?
Solution

Halting without reaching an accepting state does mean w ∉ L(M) — L(M) is defined as exactly the strings for which some reachable configuration is accepting, and "halted, not accepting" forecloses that (a deterministic machine has only one run to check). Running forever, though, also means w ∉ L(M) by the same definition — an infinite run never reaches an accepting configuration either. The distinction between the two isn't about membership in L(M) (both are "no"); it's about whether a recognizing procedure for L(M) can ever report the "no" — a machine that runs forever on a non-member gives you no signal to act on, while one that halts-rejects does. That distinction is exactly what separates decidable languages from merely recognizable ones, later in the course.

3. Why can't a single-stack PDA be adapted into a 2-stack machine simply by using one stack for input-matching and leaving the second one unused? What's actually needed to get full TM power from two stacks?
Solution

An unused second stack contributes nothing — you'd just have a PDA with excess baggage, still capped at context-free languages. The power comes specifically from using both stacks together to simulate a TM tape: one stack holds everything left of the head (reversed), the other holds everything at-and-right of the head, and a head move becomes a coordinated pop from one stack paired with a push onto the other. It's the coordination between the two that recovers two-way tape movement — not merely having a second stack available.

4. Trace the monus machine by hand on m=3, n=3 (tape 000 1 000). What's the final tape, and which termination branch (A or B) fires?
Solution

m = n, so the answer should be 0 (an empty/blank tape) — and this exercises branch B specifically, not branch A. Three full cycles pair up all three 0's of the m-block with all three 0's of the n-block (each cycle: blank one m-digit, convert one n-digit to a 1). After the third cycle, the head returns to q₀ looking for a fourth m-block 0 — but there isn't one; the very next symbol is the separator 1. That's exactly branch B's trigger condition (q₀ sees a 1 instead of a 0), which blanks the separator and all three converted 1's, leaving a fully blank tape. Notice branch A never fires here at all — it's specifically the m > n branch, and equality routes through B just like the n > m case does. Load the "custom m,n" box in Section 6's simulator with m=3, n=3 to watch this exact run.

5. True or false, with justification: "Since nondeterministic and deterministic TMs accept the same languages, you never need to think about nondeterminism when analyzing running time."
Solution

False. The languages coincide, but the standard deterministic simulation of an NTM (breadth-first exploration of the configuration tree) can cost exponentially more steps than the nondeterministic machine's own move count — Section 12's bound is n·mⁿ in the worst case. "Same computability class" says nothing about "same complexity class"; this exact gap is the informal seed of the P-vs-NP question later in the theory sequence, where NP is defined via exactly this kind of nondeterministic-polynomial-time machine.

6. A friend claims: "Since a TM can simulate any computer program, and computers can multiply in one instruction, a TM must also be able to multiply two n-bit numbers in O(n) of its own steps." Where's the flaw?
Solution

The flaw is exactly Section 14's trap: the O(n³)/O(n⁶) simulation theorems explicitly assume instructions grow the longest word by at most one bit, which a single "multiply" instruction violates (it can double word length). A computer that's allowed single-instruction multiplication falls outside the theorem's hypotheses, and simulating it can cost exponential TM time (via the repeated-squaring construction from that trap card). To stay inside the polynomial bound, multiplication has to be built from O(m) additions — at which point it costs O(m²), not O(m) — on the TM side too. So the friend's claim silently assumes a computer model the theorem doesn't cover.

L(M) = {w : q₀w ⊢* αpβ, p∈F}. Class of all such languages = recursively enumerable.

Halting

Halt = δ undefined at current (state,symbol). Three outcomes per input: accept / halt-reject / run forever — not the same as each other.

Programming tricks (zero extra power)

Storage in state: state = tuple [q,data]. Multiple tracks: tape symbol = tuple, e.g. {B,∗}×{0,1,c,B}. Subroutines: shared start state, no call stack ⇒ copy states per call site if returning to different places.

Multitape TMs

Same languages as 1-tape. Simulation cost: O(n²) single-tape steps per n multitape moves (2k-track fold, k tape-position markers).

Nondeterministic TMs

Same languages as DTMs. Deterministic simulation (BFS/queue over configuration tree) can cost up to n·mⁿ — exponential worst case.

Restricted / alternate models — all still full TM power

Semi-infinite tape (2-track fold). Two-stack machine. Two-counter machine (increment/decrement/test-zero only).

TM ⟺ computer

n instructions, multitape: O(n³). Single-tape: O(n⁶). Requires instructions grow longest word by ≤1 bit/step — multiplication violates this; build it from O(m) additions instead.

Five-step proof template (design pattern)

1) Strategy in English. 2) States & what each remembers. 3) δ table / rules. 4) Verify: does the tail-cleanup rule out leftover unmatched symbols? 5) Trace at least one boundary case (equal-length blocks, empty block, etc).
