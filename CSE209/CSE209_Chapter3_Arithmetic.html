§3.1 · Introduction

Chapter Roadmap

Everything a CPU does with numbers, in one chapter — from a schoolbook addition to the bit pattern hiding inside every float you've ever written.

Arithmetic looks like the "easy" chapter — you already know how to add and multiply. The real content of Chapter 3 is not arithmetic itself, but how a finite, fixed-width machine is forced to approximate an infinite world of numbers, and what breaks when it does. Every topic below is really a variation on one question: what happens at the edges? — when a sum won't fit, when a product doubles in width, when a real number has infinitely many digits but our register only has 32 or 64 bits to spend.

What this chapter covers

  • Operations on integers — addition and subtraction, and precisely when they silently produce a wrong answer (overflow).
  • Multiplication and division — how a machine builds a wide product from narrow operands, and the hardware evolution from a naive design to an efficient one.
  • Floating-point real numbers — how we represent numbers that aren't integers at all, using a binary cousin of scientific notation, standardized as IEEE 754.

§3.2 · Addition and Subtraction

Integer Addition & Overflow

Binary addition is bit-for-bit identical to the addition you learned in grade school. The only new idea is that the register has a fixed width — and that width can run out.

The mechanics: 7 + 6

MIPS registers are 32 bits wide, but the ripple-carry logic is identical no matter the width, so a short example makes the pattern easy to see:

OperandBinaryDecimal
a0000 01117
b0000 01106
a + b0000 110113

Add bit by bit from right to left, carrying just like decimal addition. No surprises — as long as the true sum fits in the available bits.

What "overflow" actually means

Overflow is not "the answer is wrong." It's a very specific, mechanical event: the true mathematical result cannot be represented in the number of bits available, so the bit pattern that comes out no longer means what it should.

§ The three overflow rules for addition

Adding a positive and a negative operand → never overflows. The true sum's magnitude can only be smaller than the larger operand, so it always fits.

Adding two positive operands → overflow if the result's sign bit is 1. Two positives can never sum to something negative.

Adding two negative operands → overflow if the result's sign bit is 0. Two negatives can never sum to something non-negative.

Notice the pattern: overflow is only possible when both operands share a sign, and it is detected by comparing that shared sign to the sign of the result. If the result's sign doesn't match what both operands agree it should be, the machine ran out of room.

⚠ Exam trap — overflow ≠ carry-out

Students routinely conflate signed overflow with unsigned carry-out of the most-significant bit. They are different flags checking different things: carry-out matters for unsigned arithmetic; the sign-bit-mismatch rule above matters for signed, two's-complement arithmetic. A calculation can carry out with no signed overflow, or overflow with no carry-out. If a question says "unsigned," throw out everything above and just watch the carry out of bit 31.

Worked overflow check — is 4-bit 0110 + 0101 safe?
0110 (+6)
+
0101 (+5)
↓
1011
Both operands positive, but the result's sign bit is 1 (interpreted as −5). Two positives summing to a negative is impossible → overflow. (True sum is +11, which needs 5 bits and can't fit in a 4-bit signed field whose range is −8…+7.)
Self-test: Does 4-bit 1000 + 1001 overflow? +

1000 = −8, 1001 = −7. Both negative. Sum = 1 0001 → truncate to 4 bits → 0001 (+1). The result's sign bit is 0, but both operands were negative — by the rule, that's overflow. Correct: −8 + (−7) = −15, which cannot be represented in a 4-bit signed range of −8…+7.

Self-test: Does 4-bit 0011 + 1101 overflow? +

0011 = +3, 1101 = −3. One positive, one negative — overflow is impossible by rule one, no need to even compute. (Sum is 10000 → truncates to 0000 = 0, which is correct: 3 + (−3) = 0.)

§3.2 · Addition and Subtraction

Integer Subtraction & Overflow

The single best design decision in this whole chapter: the machine never learns to subtract. It only ever adds.

The trick: negate, then add

Two's-complement representation makes a − b exactly equal to a + (−b), where negation is "invert every bit, then add 1." This means the same adder circuit used for addition handles subtraction too — just feed it the negated second operand. No separate subtractor hardware is needed.

Worked example: 7 − 6

StepValueBinary (8-bit)
Minuend+70000 0111
Subtrahend, negated−61111 1010
Sum (= 7 − 6)+10000 0001

To get 1111 1010 from 0000 0110 (+6): flip every bit → 1111 1001, then add 1 → 1111 1010. Add that to 0000 0111 and the carry out of the top bit is simply discarded (registers only keep the bits that fit), leaving 0000 0001 = +1. Exactly right.

§ The three overflow rules for subtraction

Subtracting two operands of the same sign → never overflows. (Positive − positive, or negative − negative.)

Subtracting a positive from a negative (neg − pos) → overflow if the result's sign bit is 0. A negative number minus a positive number must get more negative; if the sign flips to positive, something didn't fit.

Subtracting a negative from a positive (pos − neg) → overflow if the result's sign bit is 1. A positive number minus a negative number must get more positive; if the sign flips to negative, it overflowed.

✎ Don't memorize two rulebooks — derive one from the other

Subtraction overflow is not a new set of rules to memorize. It's the addition rule applied to a + (−b). "Negative minus positive" is really "negative plus negative" once you negate b — so of course it follows the addition rule for two negative operands. Internalizing this one substitution cuts your memorization load in half and is exactly the kind of insight professors like to test with a "why" question rather than a "what" question.

Self-test: 4-bit signed. Does 1000 − 0001 (−8 − 1) overflow? +

This is negative − positive. True result is −9, outside the 4-bit signed range (−8…+7). Negate 0001 → 1111, add: 1000 + 1111 = 1 0111 → truncate → 0111 (+7). The result's sign bit is 0, and by the neg−pos rule, overflow occurs exactly when the result's sign is 0. Confirmed: overflow, and the wrong-looking answer (+7 instead of −9) is the telltale symptom.

A quick bridge to division

The original topic list also names division, which this slide deck doesn't walk through in detail — but you should still know the shape of it for MIPS, since it reuses ideas from multiplication (a shift-based, cycle-by-cycle hardware algorithm) that we'll see next.

✎ MIPS division, briefly

div rs, rt and divu rs, rt compute signed/unsigned division, placing the quotient in LO and the remainder in HI — retrieved afterward with mflo / mfhi, the same register pair multiplication uses. MIPS division hardware does not detect overflow or divide-by-zero automatically; software must check for a zero divisor itself.

§3.3 · Multiplication

Long Multiplication

Before building hardware, build intuition with the same pencil-and-paper method you learned for decimal multiplication — it transfers to binary with zero modification.

The grade-school method, in binary

Multiply the multiplicand by each bit of the multiplier, shifting each partial product one position further left, then add every partial product together. In binary this is even simpler than decimal, because every partial product is either the multiplicand itself (multiplier bit = 1) or all zeros (multiplier bit = 0) — no multiplication table to memorize, ever.

Worked example: 1000₂ × 1001₂ (8 × 9)

Source bitPartial productShift
multiplier bit 0 = 11000× 2⁰
multiplier bit 1 = 00000× 2¹
multiplier bit 2 = 00000× 2²
multiplier bit 3 = 11000× 2³
Sum of partial products0100 1000₂ = 72₁₀

Check: 8 × 9 = 72. ✓ — and 72 in binary is indeed 1001000, padded to 8 bits as 01001000.

§ Key structural fact

The length of the product is the sum of the operand lengths. Multiplying two n-bit numbers can require up to 2n bits to hold the result without overflow — a 4-bit × 4-bit multiply needs up to 8 bits; a 32-bit × 32-bit multiply needs up to 64 bits. This single fact is the reason MIPS multiplication hardware uses a double-width product register, which drives everything in the next two sections.

Self-test: Compute 1011₂ × 0110₂ by long multiplication. +

1011 = 11, 0110 = 6 → expect 66.

Multiplier bits, LSB first: 0,1,1,0. Partial products: bit0=0 → 0000; bit1=1 → 1011 shifted left 1 → 10110; bit2=1 → 1011 shifted left 2 → 101100; bit3=0 → 0.

Sum: 010110 + 101100 = 1000010₂ = 66₁₀. ✓

§3.3 · Multiplication

Multiplication Hardware (Version 1)

Turning the paper method into a circuit: instead of writing every partial product on its own line and adding them all at once, add them one at a time, into a running total.

The building blocks

Multiplicand register — 64 bits
shifted left by 1 each cycle
↓ feeds
64-bit ALU
↓ result added into
Product register — 64 bits
initially 0
Multiplier register — 32 bits, shifted right each cycle. Its LSB is tested by Control.
Control logic tests the multiplier's current LSB each cycle: if 1, add the (shifted) multiplicand into the product; either way, shift the multiplicand left and the multiplier right, and repeat for 32 cycles.

The algorithm, cycle by cycle

  1. Test bit 0 of the Multiplier register.
  2. If it's 1, add the (currently shifted) Multiplicand into the Product register; if it's 0, do nothing this cycle.
  3. Shift the Multiplicand register left by one bit (making it "line up" with the next partial product's position).
  4. Shift the Multiplier register right by one bit (bringing the next bit to test into position 0).
  5. Repeat for as many cycles as there are bits in the multiplier (32, for MIPS).
⚠ Why this "obvious" design is wasteful

Three inefficiencies to be able to name on an exam: (1) the Multiplicand register has to be as wide as the Product register (64 bits) purely to accommodate left-shifting, even though the multiplicand's actual value only ever needs 32 bits. (2) Half the bits of the ALU are doing nothing on any given cycle where the low bits of the product are already settled. (3) It takes one full clock cycle per multiplier bit regardless of whether that cycle actually performs an addition — a lot of cycles spent shifting with nothing added. Version 2, next, fixes the first two problems directly.

Self-test: Why does the Multiplicand register need to be 64 bits wide, not 32? +

Because it gets shifted left up to 31 times over the course of the multiplication (once per remaining multiplier bit). A 32-bit value shifted left by 31 positions needs up to 63 bits to hold its significant digits without losing them off the top — so the register is sized at 64 bits to have room to grow into as the algorithm proceeds.

§3.3 · Multiplication

Optimized Multiplier (Version 2)

One clever change — shift the product instead of the multiplicand — removes the oversized register and halves the ALU width, with no loss of correctness.

The key idea

Instead of shifting the multiplicand left to align it with each partial product, keep the multiplicand fixed at 32 bits and instead shift the product register right after each addition. This has the same aligning effect, but now:

  • The Multiplicand register only ever needs to be 32 bits (it never grows).
  • The ALU only needs to be 32 bits wide, not 64 — it only ever adds into the upper half of the product.
  • The Multiplier register can be eliminated entirely and packed into the lower half of the Product register itself, since bits are shifted out of the multiplier exactly as fast as they're shifted into the product — the two halves share one 64-bit register.

Worked example: 1000₂ × 1001₂ (8 × 9), shift-and-add

The 64-bit Product register is split conceptually into a left half (running accumulator) and a right half (remaining multiplier bits, shrinking each cycle as it's consumed).

CycleTest bit (LSB)ActionProduct after step
Start—Load multiplier into lower half0000 · 1001
11Add multiplicand (1000) to upper half → 0000+1000=1000; shift right 10100 · 0100
20No add; shift right 10010 · 0010
30No add; shift right 10001 · 0001
41Add multiplicand (1000) to upper half → 0001+1000=1001; shift right 10100 · 1000

Final 8-bit Product = 01001000 = 72₁₀. Identical answer to the long-multiplication method — same math, far leaner hardware.

§ Version 1 vs. Version 2, at a glance

Version 1: Multiplicand shifts left (64-bit register), Product accumulates in place, 64-bit ALU.

Version 2: Multiplicand stays put (32-bit register), Product shifts right after each add, 32-bit ALU, Multiplier register folded into Product's lower half.

Self-test: In Version 2, why does shifting the Product right achieve the same alignment as shifting the Multiplicand left in Version 1? +

Alignment is relative — what matters is the position of the multiplicand relative to the accumulating sum, not which register physically moves. Shifting the multiplicand left by one bit each cycle and shifting the (fixed) product right by one bit each cycle produce the same relative offset between them; the second approach just achieves it by moving the (already-settled) low bits of the product out of the way instead of growing the multiplicand upward. It's the arithmetic equivalent of "does the train move past the platform, or the platform move past the train" — the relative motion is identical.

§3.3 · Multiplication

MIPS Multiply Instructions

Real MIPS hardware carries a dedicated pair of 32-bit registers just to hold results too wide for the normal register file — because, as we established, a product can be twice as wide as either operand.

HI and LO: the special product registers

HI
most-significant 32 bits
LO
least-significant 32 bits
Together, HI:LO hold the full 64-bit product of two 32-bit operands.
InstructionEffect
mult rs, rtSigned multiply; full 64-bit product placed in HI (upper) / LO (lower).
multu rs, rtUnsigned multiply; same 64-bit split into HI / LO.
mul rd, rs, rtOnly the least-significant 32 bits of the product are kept, written directly to a normal register rd.
mfhi rd / mflo rdCopy HI or LO into a general-purpose register — the only way to retrieve results from mult/multu.
⚠ Exam trap — mult vs. mul are not interchangeable

mult/multu preserve the entire mathematically correct 64-bit product — nothing is lost, but you must follow up with mflo (and mfhi, if you need the upper half) to actually use the result in a normal register. mul is convenient — one instruction, one destination register — but it silently discards the upper 32 bits. If the true product doesn't fit in 32 bits, mul gives you a truncated, wrong answer with no warning flag at all. This is a favorite "spot the bug" exam question: code that uses mul where products might exceed 32 bits is quietly broken.

Self-test: You need the full, correct 64-bit product of two large 32-bit values and must store both halves in $t0 and $t1. What instruction sequence works? +

mult $t2, $t3 (or multu if unsigned) to compute the product into HI/LO, then mflo $t0 to grab the low 32 bits and mfhi $t1 to grab the high 32 bits. mul alone cannot do this — it never populates HI at all.

§3.5 · Floating Point

Why Floating Point?

Everything so far has assumed we're representing whole numbers. But most of the interesting quantities in science, graphics, and engineering aren't integers at all.

The problem integers can't solve

Integer representation gives every bit pattern equal, fixed "weight" — bit i is always worth 2i. That's perfect for counting things, but useless for representing very large numbers (like Avogadro's number), very small numbers (like the mass of an electron in kilograms), or anything with a fractional part. We need something that behaves like scientific notation.

±1.xxxxxxx₂ × 2^yyyy

Just as decimal scientific notation writes a number as a small significand times a power of ten, floating point writes a binary number as a significand (between 1 and 2) times a power of two. Two data types in C map directly onto this idea: float (single precision) and double (double precision).

Normalized vs. not normalized

A scientific-notation number is normalized when there is exactly one non-zero digit to the left of the point. Compare three decimal examples:

ExampleDigits left of pointNormalized?
−2.34 × 10⁵⁶one non-zero digit ("2")Yes
+0.002 × 10⁻⁴leading zero — not 1–9No
+987.02 × 10⁹three digits before the pointNo

Binary has it even easier: the only non-zero digit possible in a single bit position is 1. So a normalized binary float always has the form 1.xxxxx × 2^y — the leading digit is guaranteed to be 1 whenever the number is normalized. That guarantee is exactly what IEEE 754 exploits next, with the "hidden bit" trick.

Self-test: Is 0.5 × 2⁴ normalized? If not, what's the normalized form? +

Not normalized — 0.5 in binary is 0.1₂, so the significand starts with a 0, not a 1. Rewriting: 0.5 × 2⁴ = 8, and 8 in normalized binary scientific notation is 1.0 × 2³.

§3.5 · Floating Point

IEEE 754 Bit Format

Before 1985, every manufacturer had its own floating-point format — meaning the exact same program could produce different answers on different machines. IEEE Std 754-1985 ended that.

Single vs. double precision

IEEE 754 defines two widths: single precision (32 bits, C's float) and double precision (64 bits, C's double). Both share the same three-field layout, just with different field widths:

Single1 bit8 bits23 bits32 bits

The three fields, decoded

  • S (sign): 0 = non-negative, 1 = negative. Note this applies only to the significand's sign — it is not two's complement.
  • Fraction: the bits after the binary point of the normalized significand. Since normalized binary always starts with an implicit 1, that leading "1." is never stored — it's the hidden bit. To reconstruct the true significand, restore it yourself: significand = 1.Fraction.
  • Exponent: stored in biased (excess) notation — the stored value is the actual exponent plus a bias. Bias = 127 for single, 1023 for double.
§ Why a biased exponent instead of two's complement?

Biasing guarantees the stored exponent field is always non-negative (unsigned). That, combined with placing the exponent field directly after the sign bit, means two floating-point numbers can be compared for magnitude using an ordinary unsigned integer comparator on their raw bit patterns — larger bit pattern really does mean larger floating-point value (for same-signed numbers). This is a genuinely elegant design choice and a favorite "why" exam question.

⚠ Exam trap — the hidden bit is the #1 decoding mistake

Forgetting to restore the implicit leading "1." before the fraction bits is the single most common error when decoding an IEEE-754 pattern by hand. The stored Fraction field is not the significand — it's the significand minus its leading 1. Always write "significand = 1." then append the fraction bits, before doing anything else.

Self-test: What is the stored (biased) single-precision exponent for an actual exponent of −5? +

Stored = actual + bias = −5 + 127 = 122 = 01111010₂ (8 bits).

§3.5 · Floating Point

Precision Ranges

How large, and how small, can a float actually get? The answer hides two reserved exponent patterns that don't behave like the rest.

⚠ Two exponent patterns are off-limits

The all-zero exponent field and the all-one exponent field are reserved, not part of the normal range. All-zero represents zero and denormalized (subnormal) numbers; all-one represents infinity and NaN ("not a number"). Every range calculation below therefore uses the second-smallest and second-largest exponent field values, not the true extremes of the field.

Single precision (8-bit exponent field)

Largest11111110254 − 127 = +127≈2.0 (fraction all 1)≈ ±3.4 × 10⁺³⁸

Double precision (11-bit exponent field)

Notice how much range 11 extra bits of exponent buys: double precision's largest magnitude is roughly 270 orders of magnitude beyond single precision's — a direct consequence of the exponent field width, not the fraction width.

Self-test: Why is the "largest value" significand only ≈2.0, never exactly 2.0? +

The normalized significand form is 1.fraction, and the maximum fraction (all 1s) is 1 − 2⁻²³ (single) or 1 − 2⁻⁵² (double) — infinitesimally short of 1.0, so 1 + that fraction is infinitesimally short of 2.0. It can get arbitrarily close to 2.0 but, with a finite number of fraction bits, can never reach it exactly.

§3.5 · Floating Point

Precision & Significant Digits

Range tells you how big a number can be. Precision tells you how many digits of that number you can actually trust.

Relative precision

Every fraction bit is significant, so precision is governed purely by how many fraction bits exist — not by the exponent at all. This is a crucial distinction: a huge number and a tiny number represented in the same format carry the same number of significant digits, just applied at different scales.

Fraction bitsRelative precision≈ Decimal digits
Single232⁻²³23 × log₁₀2 ≈ 23 × 0.301 ≈ 6
Double522⁻⁵²52 × log₁₀2 ≈ 52 × 0.301 ≈ 16
§ Where the log₁₀2 conversion comes from

Each binary fraction bit doubles your resolving power, but decimal digits require a factor of 10 improvement each. Converting "how many bits" into "how many decimal digits of equivalent resolution" is a base-conversion: digits ≈ bits × log₁₀(2), since log₁₀(2) ≈ 0.301 tells you how many decimal digits one extra bit is "worth."

⚠ Exam trap — "6 digits" and "16 digits" are approximate, not exact

These numbers are commonly memorized as exact facts, but they're a rounded consequence of a formula. If a question changes the fraction width (e.g., asks about a hypothetical 10-bit fraction format), you're expected to redo the multiplication yourself: 10 × 0.301 ≈ 3 decimal digits — not recall a memorized constant.

Self-test: A hypothetical "half precision" float has 10 fraction bits. Roughly how many decimal digits of precision does it carry? +

10 × log₁₀2 ≈ 10 × 0.301 ≈ 3.0 decimal digits. (This matches real IEEE 754 half precision, which does use a 10-bit fraction and is indeed cited as having about 3 decimal digits of precision.)

§3.5 · Floating Point

Encoding & Decoding — Worked Examples

The best way to internalize the IEEE-754 format is to run the conversion by hand, both directions, until it's automatic.

Encode: represent −0.75

5.0 = 101₂ = 1.01₂ × 2². S = 0. Fraction = 01000…0 (23 bits). Exponent = 2 + 127 = 129 = 10000001₂.

Self-test: What single-precision value has S=0, Exponent=01111111, Fraction=all zeros? +

Exponent field 01111111 = 127 (decimal) → actual exponent = 127 − 127 = 0. Significand = 1.0 (fraction all zero). Value = (−1)⁰ × 1.0 × 2⁰ = 1.0. (Bias 127 exists precisely so that "actual exponent 0" lands at the field's midpoint, 127 — a nice sanity check that your bias arithmetic is right.)

§3.5 · Floating Point

Floating-Point Addition Algorithm

Unlike integer addition, you cannot just add two floats bit-for-bit — their binary points aren't lined up unless the exponents already match. Four steps fix that.

§ The four-step algorithm

1. Align — shift the significand of the operand with the smaller exponent right, until both exponents match.
2. Add — add the two (now-aligned) significands.
3. Normalize — shift the sum so it's back in the form 1.xxx × 2^y, adjusting the exponent to compensate; check for overflow/underflow of the exponent.
4. Round — trim (or round) the significand back down to the available number of fraction bits, and renormalize again if rounding produced a carry-out.

Worked example (decimal, 4 significant digits): 9.999 × 10¹ + 1.610 × 10⁻¹

StepResult
1. Align (shift the smaller exponent's number)9.999×10¹ + 0.016×10¹
2. Add significands9.999 + 0.016 = 10.015 → 10.015×10¹
3. Normalize (shift right 1, exponent +1)1.0015×10²
4. Round to 4 digits1.002×10²

Worked example (binary, 4 significant bits): 1.000₂×2⁻¹ + (−1.110₂×2⁻²)

In decimal, this is 0.5 + (−0.4375) = 0.0625 — keep that target in mind as a sanity check.

StepResult
1. Align (2⁻² is smaller; shift its significand right 1, exponent → −1)1.000×2⁻¹ + (−0.111×2⁻¹)
2. Add significands1.000 − 0.111 = 0.001 → 0.001×2⁻¹
3. Normalize (shift left 3, exponent −3)1.000×2⁻⁴ — no over/underflow
4. Roundno change needed → 1.000×2⁻⁴ = 0.0625

Matches the sanity check exactly: 0.5 − 0.4375 = 0.0625. ✓

⚠ Exam trap — align, don't just "add the exponents"

A common instinct carried over from multiplication (where exponents do add) is to try the same shortcut for addition. It's wrong: addition requires the significands to represent the same power of two before their bits can be meaningfully summed. Skipping the alignment step and adding mismatched significands directly produces a number with no mathematical meaning.

✎ A famous consequence: floating-point addition isn't associative

Because every addition ends with a rounding step, (a + b) + c can give a genuinely different bit pattern than a + (b + c) for the same three floats. This is a real, well-known property of floating-point arithmetic (not a bug) — compilers are generally forbidden from silently reordering floating-point sums for this exact reason, and it's a great example to cite if a professor asks you to justify why floating-point math needs special care in numerical code.

Self-test: When aligning, which operand's exponent "wins" and stays unchanged? +

The operand with the larger exponent stays fixed; the operand with the smaller exponent has its significand shifted right (losing precision off the bottom, potentially) until its exponent catches up to match.

§3.5 · Floating Point

FP Adder Hardware

The four-step algorithm from the last section isn't just a paper method — it maps directly onto four stages of real hardware.

Why it's slower than an integer adder

An integer adder is simple enough to finish in a single clock cycle. A floating-point adder has to run the small ALU (for exponent comparison), a shifter (for alignment), the big ALU (for the significand addition), and another shifter plus rounding logic (for normalization) — doing all of that in one cycle would force the clock to slow down for every instruction, not just floating-point ones. So FP adders are instead built to take several clock cycles, keeping the clock fast, and are typically pipelined so a new pair of operands can start through the adder before the previous pair has finished.

↓
Step 4 — Normalize & Round
re-normalize the sum, adjust the exponent, round to fit, renormalize again if rounding overflowed

Line these four hardware stages up against the four algorithm steps from the previous section and they match exactly: Step 1 ↔ Align's exponent comparison, Step 2 ↔ Align's shift, Step 3 ↔ Add, Step 4 ↔ Normalize + Round. The hardware is nothing more than the algorithm, wired directly into silicon.

✎ Pipelining intuition

Even though any single floating-point add still takes multiple cycles to finish (higher latency), a pipelined design can accept a brand-new pair of operands every single cycle — while an earlier pair is still working through a later stage. Latency per operation stays the same or even grows slightly, but throughput (results completed per cycle, once the pipeline is full) approaches one per cycle. This is the same idea you'll see formalized later in the course when pipelining is covered on its own.

Self-test: Why does Step 1 use a separate "small" ALU rather than reusing the big significand ALU from Step 3? +

The exponent fields are much narrower than the significand fields (8 or 11 bits vs. 23 or 52 bits), so a dedicated small ALU sized just for exponent subtraction is cheaper and faster than routing that work through the wide significand ALU. It also lets exponent comparison (Step 1) run in parallel/pipeline-overlap with other stages rather than contending for the same hardware the significand addition needs.

Exam Traps & Quick Reference

Every trap called out earlier in this guide, collected in one place, plus the formulas worth having cold before you walk into the exam.

The trap list

⚠ Trap 1

Signed overflow ≠ unsigned carry-out. They're separate flags for separate representations.

⚠ Trap 2

Overflow is only possible when both addition operands share a sign (equivalently, when subtraction operands have opposite signs).

⚠ Trap 3

Subtraction overflow rules aren't a second rulebook — derive them from addition's rules via a − b = a + (−b).

⚠ Trap 4

mult/multu keep the full 64-bit product in HI:LO; mul silently truncates to the low 32 bits with no overflow warning.

⚠ Trap 5

The IEEE-754 hidden bit ("1.") is never stored — restore it before doing anything with a decoded Fraction field.

⚠ Trap 6

All-0 and all-1 exponent fields are reserved (zero/denormals, and infinity/NaN) — exclude them from normal range calculations.

⚠ Trap 7

"~6 digits" and "~16 digits" of precision are derived from bits × log₁₀2, not memorized constants — be ready to redo the arithmetic for a different fraction width.

⚠ Trap 8

FP addition aligns exponents by shifting significands — it does not add exponents the way multiplication does.

Part IV · Review

Practice Problem Set

Ten problems spanning the whole chapter. Work each one on paper before revealing the answer.

1. (4-bit signed) Does 0111 + 0001 overflow? What's the stored result? +

0111(+7) + 0001(+1) = 1000. Both positive, result sign bit = 1 → overflow. (True sum +8 is outside the 4-bit range of −8…+7.) Stored bit pattern reads as −8, which is wrong.

2. (4-bit signed) Compute 0010 − 1110 and state whether it overflows. +

0010(+2) − 1110(−2) is pos − neg = +2 + 2 = +4. Negate 1110 → 0010, add: 0010+0010=0100 (+4). Result sign = 0, matches the pos−neg rule (overflow only if sign is 1) → no overflow. Correct: 2−(−2)=4.

3. Multiply 0101₂ × 0011₂ using long multiplication. +

0101=5, 0011=3 → expect 15. Bits of multiplier LSB-first: 1,1,0,0. Partial products: 0101, 01010, 0, 0. Sum: 0101+01010 = 01111₂ = 15. ✓

4. In Multiplier Hardware Version 1, how many clock cycles does a 32-bit × 32-bit multiply take, and why? +

32 cycles — one per bit of the 32-bit Multiplier register, since exactly one shift (and conditional add) happens per cycle regardless of the bit's value.

5. What does mul $t0, $t1, $t2 do if the true product of $t1 and $t2 needs 40 bits to represent? +

$t0 receives only the low 32 bits of the true product — the upper 8 bits that don't fit are silently discarded, with no overflow indication. The value in $t0 is not the mathematically correct product.

6. Normalize the binary number 0.0011₂ × 2⁵ into the form 1.xxx × 2^y. +

Shift the significand left until the leading digit is 1, decreasing the exponent by 1 for each shift (to keep the value unchanged): 0.0011 → 0.011 (shift 1, exp 5→4) → 0.11 (shift 2, exp 4→3) → 1.1 (shift 3, exp 3→2). Result: 1.1₂ × 2². Check: 0.0011₂ = 0.1875, and 0.1875 × 2⁵ = 6.0; 1.1₂ × 2² = 1.5 × 4 = 6.0. ✓ Matches.

7. Encode +0.25 in single-precision IEEE 754. +

0.25 = 0.01₂ = 1.0₂ × 2⁻². S=0. Exponent = −2+127=125=01111101. Fraction = 000…0 (23 bits). Full: 0 01111101 00000000000000000000000.

8. Decode single-precision pattern: S=0, Exponent=10000010, Fraction=1000000... (23 bits). +

Exponent field = 10000010₂ = 130 → actual = 130−127=3. Significand = 1 + 0.5 (first fraction bit worth 2⁻¹) = 1.5. Value = (−1)⁰ × 1.5 × 2³ = 1.5×8 = 12.0.

9. Add 1.010₂×2² + 1.100₂×2⁰ using the 4-step FP addition algorithm (4 significant bits). +

Align: the smaller exponent (0) shifts right 2 to match exponent 2: 1.100×2⁰ = 0.011×2² (exact — the bits shifted out were both zero, so nothing is lost here). Add: 1.010 + 0.011 = 1.101 → 1.101×2². Normalize: already normalized (leading digit 1), no change needed. Round: fits in 4 significant bits already, no change. Result: 1.101₂ × 2² = (1 + 0.5 + 0.125) × 4 = 1.625 × 4 = 6.5. Check against the un-aligned inputs: 1.010₂×2² = 1.25×4 = 5.0, and 1.100₂×2⁰ = 1.5; 5.0 + 1.5 = 6.5. ✓ Exact match — this particular pair happened to align with no bits lost, so the four-step algorithm reproduces the true sum precisely.

10. Conceptual: name the two design decisions that let Multiplier Version 2 use a 32-bit ALU instead of Version 1's 64-bit ALU. +

(1) The multiplicand is kept fixed at 32 bits rather than growing via left-shifts, so the ALU only ever adds two 32-bit quantities. (2) Alignment is instead achieved by shifting the product register right after each add, which only requires wiring a shifter onto the product register — not widening the adder itself.
