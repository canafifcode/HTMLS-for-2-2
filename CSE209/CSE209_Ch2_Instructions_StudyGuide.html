§2.1 Introduction

Instruction Sets & the MIPS ISA

Before we touch a single MIPS instruction, we need to agree on what an "instruction set" even is — it's the contract between software and hardware, and everything else in this chapter is us learning to read and write in that contract's language.

What is an Instruction Set?

An instruction set is the complete repertoire of instructions a particular computer's hardware understands and can execute directly. Think of it as a vocabulary — every processor architecture (MIPS, x86, ARM, RISC-V) has its own vocabulary, but historically, most instruction sets share a surprising amount of common structure: arithmetic, memory access, and control flow always show up in some form.

Early computers were built with very simple instruction sets. This wasn't a limitation of ambition — it was a deliberate simplification that made the hardware implementation dramatically easier to build correctly. That lesson never went away: many of today's most successful modern processors (and certainly the one we're about to study) still lean hard into simplicity.

💡 The Big Idea

The Instruction Set Architecture (ISA) is an abstract interface — it says nothing about how the hardware actually implements each instruction internally. Two completely different physical chips can implement the exact same ISA (say, MIPS) using totally different internal designs, pipeline depths, or clock speeds, and yet run the exact same compiled binary correctly. This separation of "what" (ISA) from "how" (microarchitecture) is one of the most powerful ideas in computer science.

Why MIPS?

This course (like the textbook) uses MIPS as its running example throughout. A few reasons this is a great teaching choice:

  • It originated as the Stanford MIPS project and was commercialized by MIPS Technologies.
  • It has historically held a large share of the embedded core market — think consumer electronics, network/storage equipment, cameras, printers.
  • Above all: it's typical of many modern ISAs. The regularities you learn here transfer almost directly to how you'd reason about ARM or RISC-V.

Reference: MIPS Reference Data tear-out card, and Appendixes B and E of the textbook.

Self-TestWhy did early computer designers favor simple instruction sets, and why does that reasoning still matter today?

Answer: Simple instruction sets are dramatically easier to implement correctly in hardware. Fewer, more regular instructions mean less complex control logic, which directly enables higher performance at lower cost — this is exactly Design Principle #1 ("Simplicity favors regularity"), which you'll meet formally in the next section, and it still drives modern RISC-style ISA design (ARM, RISC-V) today.
§2.2 Operations of the Computer Hardware

Arithmetic Operations

Every MIPS arithmetic instruction obeys one rigid shape. Once you internalize that shape, translating C expressions into MIPS becomes mechanical.

The Three-Operand Rule

MIPS add and subtract always take exactly three operands: two sources and one destination.

add a, b, c   # a gets b + c

Every arithmetic instruction in MIPS has this form. There is no version of add that takes two operands, or four. This rigidity is not an accident.

⚙️ Design Principle #1 — Simplicity favors regularity

Forcing every arithmetic instruction into the identical 3-operand shape makes the hardware that decodes and executes it dramatically simpler. Regularity in the instruction format directly translates into simpler control logic, which enables higher performance at lower cost. You'll see this principle resurface constantly through the chapter — it's the single most important idea in MIPS's design.

Worked Example: Translating a C Expression

C code:

f = (g + h) - (i + j);

This expression has two operations nested together — but a MIPS instruction can only perform one operation. The compiler must break this into a sequence of simple three-operand instructions, using temporary registers to hold intermediate results.

Compiled MIPS code:

add t0, g, h   # temp t0 = g + h
add t1, i, j   # temp t1 = i + j
sub f,  t0, t1 # f = t0 - t1
C sub-expressionMIPS lineWhat's happening
(g + h)add t0, g, hComputes g+h once, stashes it in a scratch register t0 since it will be needed again in the next line.
(i + j)add t1, i, jComputes i+j into a second scratch register t1 — MIPS can't nest expressions, so this has to be its own instruction.
… - …sub f, t0, t1Only now, with both partial sums ready in registers, can the subtraction happen — and it writes directly into f.
⚠️ Exam Trap

Operand order matters for subtract! sub d, s, t means d = s − t, not t − s. Students under exam pressure frequently flip this. Always read subtract operands left-to-right exactly like the C expression they came from.

⚠️ Exam Trap

You cannot write a single instruction like add f, g, h, i, j — MIPS arithmetic instructions perform exactly one operation on exactly two source operands. Any C expression with more than one operator needs one MIPS instruction per operator, chained together with temporary registers.

Self-TestTranslate x = (a - b) + (c - d); into MIPS, using t0 and t1 as temporaries.

sub t0, a, b   # t0 = a - b
sub t1, c, d   # t1 = c - d
add x,  t0, t1 # x = t0 + t1
Same pattern as the worked example: compute each parenthesized sub-expression into its own temp register first, then combine them in the final instruction.
§2.3 Operands of the Computer Hardware

Operands: Registers, Memory & Immediates

MIPS arithmetic instructions never touch memory directly — this single fact shapes almost everything else in this section.

Register Operands

Arithmetic instructions operate exclusively on register operands. MIPS provides a 32 × 32-bit register file: 32 registers, numbered 0–31, each holding a 32-bit "word." These are reserved for the hardware's most frequently accessed data.

⚙️ Design Principle #2 — Smaller is faster

Compare 32 registers to main memory's millions of locations. A smaller storage structure can be built with faster access circuitry. This is exactly why the register file is capped at 32 — enough to hold the hot working set of a typical computation, small enough to stay blazingly fast.

Assembler Register Names

NamePurpose
$t0 – $t9Temporary values
$s0 – $s7Saved variables

Worked Example

C: f = (g + h) - (i + j); with f…j mapped to $s0…$s4

add $t0, $s1, $s2
add $t1, $s3, $s4
sub $s0, $t0, $t1

Identical structure to the arithmetic example from §2.2 — we've simply swapped in real register names.

Memory Operands

Registers are great for scalars, but composite data — arrays, structs, anything dynamically sized — lives in main memory. To operate on it arithmetically, MIPS must first load the value from memory into a register, compute, then optionally store the result back.

  • Memory is byte-addressed: every address identifies one 8-bit byte.
  • A word is 4 bytes = 32 bits, and words must be aligned: a word's address must be a multiple of 4.
  • MIPS is Big-Endian: the most-significant byte sits at the lowest address of a word (the opposite of x86's Little-Endian, where the least-significant byte comes first).
⚠️ Exam Trap — the #1 pitfall of this whole chapter

Sequential words are NOT at sequential addresses. Because each address is a byte, consecutive words sit at addresses 0, 4, 8, 12, … — not 0, 1, 2, 3. If you're walking a word array with a pointer, you increment by 4, never by 1. The textbook flags this explicitly as a "pitfall" (§2.19) precisely because so many students get burned by it.

Worked Example 1 — Load then Add

C: g = h + A[8]; — g in $s1, h in $s2, base address of A in $s3

Index 8 needs a byte offset of 8 × 4 bytes/word = 32.

lw $t0, 32($s3)   # load word: t0 = A[8]
add $s1, $s2, $t0 # g = h + A[8]

Worked Example 2 — Load, Compute, Store

C: A[12] = h + A[8]; — h in $s2, base of A in $s3

Index 8 → offset 32. Index 12 → offset 48.

lw $t0, 32($s3)   # load word: t0 = A[8]
add $t0, $s2, $t0 # t0 = h + A[8]
sw $t0, 48($s3)   # store word: A[12] = t0
⚠️ Exam Trap

Never use an array index directly as the byte offset. Always multiply the index by the element's byte size (4 for a word-sized int). Index 8 is offset 32, not 8 — this scaling step is the single most common arithmetic slip on memory-operand exam problems.

Registers vs. Memory

Registers are always faster to access than memory. Operating on memory-resident data costs extra load/store instructions, so a good compiler keeps as many variables in registers as it can, only "spilling" the least-frequently-used ones to memory. Register allocation is one of the most heavily studied problems in compiler design for exactly this reason.

Immediate Operands

Sometimes the second operand isn't a variable at all — it's a constant baked right into the instruction:

addi $s3, $s3, 4

There's no separate "subtract immediate" instruction — you just addi a negative constant:

addi $s2, $s1, -1
⚙️ Design Principle #3 — Make the common case fast

Small constants show up constantly in real programs — loop counters, array index bumps, small offsets. Giving them a direct, single-instruction path (rather than forcing a separate load of the constant into a register first) is a textbook example of optimizing for the common case.

The Constant Zero

Register $zero (register 0) is hardwired to the value 0 and cannot be overwritten — any write to it is silently discarded. It's surprisingly useful, e.g. for moving a value between registers:

add $t2, $s1, $zero   # t2 = s1 + 0, i.e. t2 = s1

Keep this in the back of your mind — it resurfaces in §2.12 as exactly how the move pseudoinstruction is implemented.

Self-TestWhy can't MIPS have an instruction like x86's "add memory-to-memory" (adding two values that both live in RAM, with no registers involved)?

MIPS is a strict load/store architecture: lw/sw are the only instructions permitted to touch memory; every arithmetic instruction only ever reads/writes registers. This is Design Principle #1 (regularity) again — keeping arithmetic instructions memory-free means the hardware datapath for "compute" never has to also handle a slow, unpredictable-latency memory access, which simplifies and speeds up the common arithmetic path.

Self-TestGiven a word array, what byte offset reaches element A[20]?

20 × 4 bytes = 80. Instruction: lw $t0, 80($s3) (assuming base of A is in $s3).
§2.4 Signed and Unsigned Numbers

Signed & Unsigned Numbers

The exact same 32 bits mean two completely different numbers depending on whether you interpret them as signed or unsigned. Nearly every trap in this section comes from forgetting that.

Unsigned Binary Integers

For an n-bit unsigned number, the range is 0 to 2ⁿ − 1. For 32 bits: 0 to 4,294,967,295.

0000 0000 0000 0000 0000 0000 0000 10112
= 1×23 + 0×22 + 1×21 + 1×20
= 8 + 0 + 2 + 1 = 1110

2's-Complement Signed Integers

For an n-bit signed number, the range is −2ⁿ⁻¹ to +2ⁿ⁻¹ − 1. For 32 bits: −2,147,483,648 to +2,147,483,647.

1111 1111 1111 1111 1111 1111 1111 11002
= −1×231 + 1×230 + … + 1×22 + 0×21 + 0×20
= −2,147,483,648 + 2,147,483,644 = −410

Note the trick: bit 31 is weighted negatively (−2³¹); every other bit keeps its normal positive weight. That single negative weight on the top bit is the entire mechanism of 2's-complement.

Key Facts

  • Bit 31 is the sign bit: 1 → negative, 0 → non-negative.
  • Non-negative numbers have identical bit patterns under unsigned and 2's-complement interpretation — they only diverge once the sign bit is set.
  • Landmark patterns:
ValueBit Pattern
00000 0000 … 0000
−11111 1111 … 1111
Most-negative1000 0000 … 0000
Most-positive0111 1111 … 1111
⚠️ Exam Trap — a favorite trick question

−(−2ⁿ⁻¹) cannot be represented! The most-negative number (1000…0) has no positive counterpart in n-bit 2's-complement — negating it "wraps around" back to itself. In 32-bit MIPS, that means you cannot represent +2,147,483,648.

Signed Negation

To negate a 2's-complement number: complement every bit, then add 1. (Complement = flip each bit: 1→0, 0→1.)

Worked example — negate +2:

+2  = 0000 0000 … 00102
complement → 1111 1111 … 11012
+ 1            → 1111 1111 … 11102  = −2

Sign Extension

Sign extension widens a number to more bits while preserving its numeric value. For signed values, you replicate the sign bit leftward. MIPS instructions that sign-extend include:

  • addi — extends the immediate value
  • lb, lh — extend the loaded byte/halfword
  • beq, bne — extend the branch displacement

Unsigned values, by contrast, extend with 0s (that's exactly what lbu/lhu do).

Worked example — 8-bit to 16-bit:

+2:  0000 0010  →  0000 0000 0000 0010
−2:  1111 1110  →  1111 1111 1111 1110
⚠️ Exam Trap

Mixing up sign-extend vs. zero-extend is one of the classic exam gotchas — especially lb (sign-extends) vs. lbu (zero-extends). Ask yourself: "does this instruction care about signedness?" If the loaded value is being used as a raw byte/character (like in strcpy, later in §2.9), zero-extension via lbu is correct even though the value is technically "unsigned" — you don't want a high-bit-set character byte accidentally turning negative.

🔍 Beyond the Slides — the "u" suffix trap

MIPS also has addu, addiu, subu. Despite the "u," these do not mean "treat operands as unsigned" — the arithmetic bit pattern produced is identical either way in 2's-complement. What "u" actually means is: don't trigger an overflow exception. Crucially, addiu still sign-extends its 16-bit immediate, exactly like addi. This is a genuinely common point of confusion worth knowing even if your slides don't dwell on it.

Self-TestWhat is the 2's-complement decimal value of 1111 1111 1111 1111 1111 1111 1111 1111? What is its unsigned decimal value?

Signed: −1 (all-1s is always −1 in 2's-complement). Unsigned: 4,294,967,295 (2³² − 1). Same bits, two entirely different numbers — this exact pair reappears in the slt vs sltu worked example in §2.7.
§2.5 Representing Instructions in the Computer

Representing Instructions

Every MIPS instruction is a rigid 32-bit binary word — this section is where "regularity" stops being an abstract slogan and becomes a literal bit layout you can hand-decode.

Instructions are encoded in binary — called machine code. MIPS instructions are always exactly 32 bits, using a small number of formats that encode an operation code (opcode), register numbers, and so on. Regularity, again.

Register Numbers

NameRegister #
$t0 – $t78 – 15
$s0 – $s716 – 23
$t8 – $t924 – 25
⚠️ Exam Trap

$t8/$t9 are not contiguous with $t0–$t7! They jump to register numbers 24–25 (after the $s registers), not 16–17. This numbering gap is a favorite "decode this instruction by hand" exam trick.

MIPS R-format Instructions

Used for register-to-register arithmetic (like add, sub, and, or, shifts).

op6 bits
rs5 bits
rt5 bits
rd5 bits
shamt5 bits
funct6 bits
  • op — operation code (opcode); for all R-format instructions this is 0 ("special")
  • rs — first source register number
  • rt — second source register number
  • rd — destination register number
  • shamt — shift amount (00000 unless the instruction is a shift)
  • funct — function code; since op is always 0 for R-format, funct is what actually distinguishes add from sub from and…

Worked Example: add $t0, $s1, $s2

⚠️ Exam Trap — the #1 encoding mistake

In assembly text, the order is add rd, rs, rt (destination first). But in the binary encoding, the field order is rs, rt, rd — destination sits in the middle! When hand-encoding or hand-decoding an R-format instruction, this mismatch between assembly order and bit-field order trips up almost everyone the first time.

Hexadecimal

Base 16 — a compact way to write bit strings, since 4 bits map exactly to 1 hex digit.

0 = 00004 = 01008 = 1000c = 1100
1 = 00015 = 01019 = 1001d = 1101
2 = 00106 = 0110a = 1010e = 1110
3 = 00117 = 0111b = 1011f = 1111

Example: eca8 642016 = 1110 1100 1010 1000 0110 0100 0010 00002

MIPS I-format Instructions

Used for immediate arithmetic (addi) and load/store (lw, sw).

op6 bits
rs5 bits
rt5 bits
constant or address16 bits
  • rt here is a destination or source register, depending on the instruction.
  • The 16-bit field is either a constant (range −2¹⁵ to +2¹⁵ − 1, because it's sign-extended) or, for loads/stores, an address offset added to the base register in rs.
⚙️ Design Principle #4 — Good design demands good compromises

Having two formats (R and I) complicates instruction decoding slightly compared to having just one — but keeping the formats as similar as possible (op always in the same bit position, rs/rt always in the same place) balances the flexibility of a 16-bit immediate field against the cost of extra decode logic. This principle is the "grown-up" answer to almost every "why didn't MIPS just do X instead" question in this chapter.

Self-TestWhy does the R-format need a separate funct field at all — why not just use more opcode bits?

All R-format instructions share the same 6-bit opcode (0, "special") so that they can also share the exact same field layout as each other (rs/rt/rd/shamt/funct in fixed positions) — this is the regularity principle again. The funct field then does the job of distinguishing add/sub/and/or/etc. within that shared format, rather than forcing every R-type operation to have a unique opcode (which would break the uniform layout).

Self-TestDecode: op=0, rs=9($t1), rt=10($t2), rd=11($t3), shamt=0, funct=34 (sub). Write the assembly instruction.

sub $t3, $t1, $t2 — remember: rd (destination) comes first in assembly text, even though it sits in the middle of the bit encoding.
§2.6 Logical Operations

Logical Operations

These instructions manipulate individual bits rather than whole numeric values — masking, setting, inverting, and shifting.

OperationCJavaMIPS
Shift left<<<<sll
Shift right>>>>>srl
Bitwise AND&&and, andi
Bitwise OR||or, ori
Bitwise NOT~~nor

These are useful whenever you need to extract or insert specific groups of bits within a word — flags, packed fields, character manipulation, and so on.

Shift Operations

The shamt field says how many bit positions to shift.

  • Shift left logical (sll) — shifts left, filling with 0s on the right. Shifting left by i bits multiplies by 2ⁱ.
  • Shift right logical (srl) — shifts right, filling with 0s on the left. Shifting right by i bits divides by 2ⁱ, but only for unsigned values.
op6 bits
rs5 bits
rt5 bits
rd5 bits
shamt5 bits
funct6 bits
⚠️ Exam Trap

srl fills the vacated high bits with 0, no matter what. If you use it to "divide" a negative signed number by a power of 2, you'll destroy the sign bit and get garbage. MIPS actually provides sra (shift right arithmetic) which replicates the sign bit instead, for correct signed division-by-power-of-2. If your exam asks you to halve a signed value via shifting, reach for sra, not srl.

AND — Masking Bits

Useful to select some bits, clear the rest to 0. A result bit is 1 only where both operand bits are 1.

and $t0, $t1, $t2

$t1  0000 0000 0000 0000 0000 1101 1100 0000
$t2  0000 0000 0000 0000 0011 1100 0000 0000
─────────────────────────────────────────────
$t0  0000 0000 0000 0000 0000 1100 0000 0000

Wherever $t2 has a 0, the result is forced to 0 regardless of $t1 — that's the "masking" behavior in action.

OR — Setting Bits

Useful to include bits: set some bits to 1 while leaving others unchanged.

or $t0, $t1, $t2

$t1  0000 0000 0000 0000 0000 1101 1100 0000
$t2  0000 0000 0000 0000 0011 1100 0000 0000
─────────────────────────────────────────────
$t0  0000 0000 0000 0000 0011 1101 1100 0000

NOT via NOR

MIPS has no direct NOT instruction. Instead it provides a 3-operand nor, and a NOR b == NOT(a OR b). OR-ing any value with $zero leaves it unchanged, so NOR-ing with $zero gives you a clean bitwise NOT:

nor $t0, $t1, $zero

$t1  0000 0000 0000 0000 0011 1100 0000 0000
$t0  1111 1111 1111 1111 1100 0011 1111 1111
🤔 Why NOR and not a dedicated NOT?

Adding a whole new instruction (and thus a whole new opcode/funct combination and possibly a new instruction format for a single-operand op) would break the clean 3-operand regularity every other R-format instruction shares. Instead, MIPS reuses the existing 3-operand shape and gets NOT "for free" by NOR-ing with the always-zero register. Regularity wins again.

Self-TestGiven $t1 = 1010 1010 and $t2 = 0000 1111 (8-bit for simplicity), compute and $t0,$t1,$t2, or $t0,$t1,$t2, and nor $t0,$t1,$zero.

AND: 1010 1010 & 0000 1111 = 0000 1010
OR: 1010 1010 | 0000 1111 = 1010 1111
NOR with $zero (= NOT $t1): ~(1010 1010) = 0101 0101
§2.7 Instructions for Making Decisions

Making Decisions

This is where MIPS starts to feel like a real programming language — if-statements and loops both compile down to the same handful of branch instructions.

The Three Core Instructions

  • beq rs, rt, L1 — if (rs == rt) branch to the instruction labeled L1
  • bne rs, rt, L1 — if (rs != rt) branch to the instruction labeled L1
  • j L1 — unconditional jump to L1

If the condition is false, execution just falls through to the next sequential instruction.

Compiling If Statements

C code:

if (i == j) f = g + h;
else        f = g - h;

f, g, i, j mapped to $s0, $s1, $s3, $s4 respectively (h in $s2).

CMIPSPurpose
if (i == j)bne $s3, $s4, ElseInverted condition! If i≠j, jump straight to the "else" branch, skipping the "then" code entirely.
f = g + h;add $s0, $s1, $s2The "then" body — only reached if we didn't branch away above.
(end of if)j ExitHaving run the "then" branch, we must jump over the "else" branch to avoid falling into it.
else f = g - h;Else: sub $s0, $s1, $s2The "else" body, landed on directly by the bne above.
(after if/else)Exit: …Both paths converge here.
⚠️ Exam Trap — the single most common if/else mistake

Compilers branch on the opposite (negated) condition of the C source, then let the "true" case simply fall through. C says if (i == j), but the MIPS uses bne, not beq! Students under time pressure instinctively reach for the branch that matches the C keyword literally and get it backwards. Always ask: "what condition sends me away from the code I'm currently looking at?"

Compiling Loop Statements

C code:

while (save[i] == k) i += 1;

i in $s3, k in $s5, address of save in $s6.

MIPSPurpose
Loop: sll $t1, $s3, 2t1 = i × 4 (scale the index into a byte offset — save[] is a word array, so each element is 4 bytes; this is the exact same "×4" idea from the memory-operand examples in §2.3, just done via a shift instead of multiplication).
add $t1, $t1, $s6t1 = address of save[i] (base address + scaled offset).
lw $t0, 0($t1)t0 = save[i] — load the actual array element.
bne $t0, $s5, ExitInverted condition again! C says "while equal, keep looping" — MIPS says "the moment they're not equal, exit."
addi $s3, $s3, 1i += 1 — only reached if we didn't exit above.
j LoopJump back to re-check the condition — this is what makes it a loop rather than a one-shot if.
Exit: …Landed on directly by the bne once the condition goes false.

Basic Blocks

A basic block is a maximal sequence of instructions with no embedded branches (except possibly at the very end) and no branch targets (except possibly at the very beginning). Compilers identify basic blocks as the fundamental unit for optimization, and advanced processors can accelerate execution across a whole basic block at once since control flow within it is fully predictable.

More Conditional Operations: slt

beq/bne can only test equality — for <, >, ≤, ≥ we need help:

  • slt rd, rs, rt — if (rs < rt) rd = 1; else rd = 0;
  • slti rt, rs, constant — if (rs < constant) rt = 1; else rt = 0;

Combine with beq/bne to build any comparison:

slt $t0, $s1, $s2   # t0 = 1 if s1 < s2
bne $t0, $zero, L    # branch to L if s1 < s2 was true
🤔 Why isn't there a direct blt or bge instruction?

The hardware comparators for < and ≥ are inherently slower than those for = and ≠. Folding a slow comparison directly into a branch instruction means every branch — including the far more common equality checks — would be limited by that slower comparator's timing, since the whole CPU shares one clock speed. So MIPS keeps beq/bne fast and common, and makes </≥ comparisons a deliberate two-instruction combo. This is Design Principle #4 (good compromises) in action: a real cost (extra instruction) accepted for a real benefit (a faster clock for everyone).

Signed vs. Unsigned Comparison

Signed comparison: slt, slti. Unsigned comparison: sltu, sltui.

Worked example — this single example is arguably the highest-yield trap in the entire chapter:

$s0 = 1111 1111 1111 1111 1111 1111 1111 1111
$s1 = 0000 0000 0000 0000 0000 0000 0000 0001

slt  $t0, $s0, $s1   # signed:   −1 < +1  → $t0 = 1
sltu $t0, $s0, $s1   # unsigned: 4,294,967,295 > 1 → $t0 = 0

Identical bit patterns, opposite comparison results — purely because of how the instruction chose to interpret the sign bit. This is exactly the same $s0 pattern from the §2.4 self-test.

⚠️ Exam Trap

Always check the problem statement for whether values should be treated as signed or unsigned before picking slt vs sltu. Using the wrong one silently produces a "valid-looking" but completely wrong answer — there's no error, no crash, just a flipped comparison. This is a favorite way to write a subtle, hard-to-catch exam question.

Self-TestTranslate: if (a >= b) x = 1; else x = 0; (signed a, b) into MIPS using slt.

slt $t0, $a, $b     # t0 = 1 if a < b
bne $t0, $zero, Else # if a < b, we do NOT have a>=b
addi $x, $zero, 1    # a >= b case: x = 1
j Exit
Else: addi $x, $zero, 0
Exit: …
Notice we still negate: we test the opposite of "a≥b" (i.e. "a<b") to decide when to jump away from the true-case code — same pattern as the if/else walkthrough above.
§2.8 Supporting Procedures in Computer Hardware

Procedures & the Stack

Procedure calls are where every idea so far — registers, memory operands, branches — comes together into one coordinated protocol. This section is dense; take it slow.

Six Steps of a Procedure Call

  1. Place parameters in registers
  2. Transfer control to the procedure
  3. Acquire storage for the procedure
  4. Perform the procedure's operations
  5. Place the result in a register for the caller
  6. Return to the place of call

This exact 6-step list is a favorite short-answer recall question — worth memorizing verbatim.

⚠️ Exam Trap — caller-saved vs. callee-saved

$t registers can be freely overwritten by any procedure you call — if you need a $t value to survive a call, you (the caller) must save it yourself before the call. $s registers are the opposite: if a procedure wants to use an $s register, it must save the caller's old value first and restore it before returning. Mixing these up is one of the most-tested ideas in this whole chapter — expect a question that asks "which registers does this procedure need to save, and why?"

Call and Return Instructions

jal ProcedureLabel   # $ra = address of next instruction; jump to ProcedureLabel
jr  $ra              # PC = $ra  (return)

jal ("jump and link") is how a call happens — it's a single instruction that does two things atomically: stash the return address, then jump. jr $ra ("jump register") is how a procedure returns — and note it's more general than just "return": since it can jump to any address held in a register, it's also used for computed jumps, e.g. implementing a switch/case statement via a jump table.

Memory Layout

High addressesStack (grows ↓)
…unused space
grows ↑Dynamic data (heap)
Static data
Low addressesText (program code)
  • Text — the program's compiled instructions.
  • Static data — global variables, e.g. C static variables, constant arrays/strings. $gp is initialized to point into this segment so it can reach nearby data with small ± offsets.
  • Dynamic data (heap) — e.g. malloc in C, new in Java. Grows upward as more is allocated.
  • Stack — automatic (local) storage, grows downward from high addresses as procedures are called.

Leaf Procedure Walkthrough

A leaf procedure calls no other procedures — the simplest case.

C code:

int leaf_example (int g, h, i, j) {
    int f;
    f = (g + h) - (i + j);
    return f;
}

Arguments g…j arrive in $a0…$a3; f is placed in $s0 (which means we must save/restore $s0, since it's callee-saved); result returns in $v0.

CMIPSLine-by-line explanation
(prologue)addi $sp, $sp, -4Grow the stack by 4 bytes (one word) to make room — remember, the stack grows downward, so "growing" means subtracting from $sp.
sw $s0, 0($sp)Save the caller's old $s0 value onto the newly-reserved stack slot, since we're about to overwrite $s0 with our own local variable f — this is the callee-saved obligation in action.
f = (g+h)-(i+j);add $t0, $a0, $a1t0 = g + h. Note we use a $t register here — it's purely a scratch value local to this procedure, nothing to save.
add $t1, $a2, $a3t1 = i + j.
sub $s0, $t0, $t1f = t0 − t1, stored into $s0 (our local variable f).
return f;add $v0, $s0, $zeroCopy f into the return-value register $v0 (recall from §2.3 — adding $zero is exactly how "move between registers" works).
(epilogue)lw $s0, 0($sp)Restore the caller's original $s0 value from the stack — fulfilling our callee-saved promise.
addi $sp, $sp, 4Shrink the stack back down by 4 bytes, releasing the slot we reserved.
jr $raReturn control to the caller, at the address saved when we were called via jal.

Non-Leaf Procedures

A procedure that itself calls other procedures is non-leaf. Before making a nested call, the caller must additionally save on the stack:

  • Its return address ($ra) — because the nested call's own jal will overwrite $ra!
  • Any arguments or temporaries it still needs after the call — because $t registers and $a registers are not guaranteed to survive a call.

...then restore all of this from the stack after the nested call returns.

Non-Leaf Walkthrough: Recursive Factorial

C code:

int fact (int n) {
    if (n < 1) return f;
    else return n * fact(n - 1);
}

Argument n in $a0; result in $v0.

MIPSLine-by-line explanation
fact:Entry label — where jal fact lands.
addi $sp, $sp, -8Reserve 2 words (8 bytes) on the stack: one for $ra, one for the argument n — both are at risk of being clobbered by the recursive call about to happen.
sw $ra, 4($sp)Save the return address — critical, because the recursive jal fact below will overwrite $ra with a new return address.
sw $a0, 0($sp)Save the current n — because $a0 will be reused (with a new value) for the recursive call's own argument.
slti $t0, $a0, 1t0 = 1 if n < 1, else 0 — testing the base case.
beq $t0, $zero, L1Inverted condition again (§2.7 pattern): if n is NOT < 1, skip the base-case return and fall through to L1 for the recursive case.
addi $v0, $zero, 1Base case: result = 1.
addi $sp, $sp, 8Base case: pop our 2 saved words — no recursive call happened, so nothing else to restore.
jr $raBase case: return.
L1: addi $a0, $a0, -1Recursive case: compute n−1 as the argument for the recursive call.
jal factRecursive case: call fact(n−1) — this overwrites $ra and $a0, which is exactly why we saved copies above.
lw $a0, 0($sp)Restore our own original n (needed for the multiply below) — the recursive call's $a0 usage is now done.
lw $ra, 4($sp)Restore our own return address — we're about to return ourselves, and need the caller's address back, not the recursive call's leftover value.
addi $sp, $sp, 8Pop our 2 saved words.
mul $v0, $a0, $v0result = n × fact(n−1) — $v0 already holds the recursive call's returned result at this point.
jr $raReturn to whoever called us (either the original caller, or — one level up — our own recursive parent call).
📈 Visualizing fact(3)

fact(3) calls fact(2), which calls fact(1), which calls fact(0) — the base case. Each call pushes its own 2-word stack frame (saved $ra, saved n) before descending further, so at the deepest point there are 4 stack frames stacked up. Unwinding happens in reverse: fact(0) returns 1 → fact(1) computes 1×1=1 → fact(2) computes 2×1=2 → fact(3) computes 3×2=6. Each frame's saved $ra is what lets that specific call resume exactly where it left off, multiplying by its own n.

⚠️ Exam Trap

Forgetting to save $ra before a nested call is the classic non-leaf-procedure bug — without it, the moment the inner call returns, your outer jr $ra jumps to the wrong place (or infinite-loops back into the callee), because $ra now holds the inner call's return address instead of yours.

Local Data & Activation Records

Local (automatic) data that a callee allocates for itself — C automatic variables, for instance — together with saved registers, forms that call's procedure frame (a.k.a. activation record). Some compilers use $fp to give this frame a stable reference point even while $sp moves around within the procedure body.

Self-TestWhy does fact need to save $a0 on the stack, but the earlier leaf_example did not need to save any $a registers?

leaf_example never calls another procedure, so nothing can overwrite its $a0–$a3 mid-execution — it's safe to read them any time before returning. fact, being non-leaf, issues its own jal fact, and that recursive call will reuse $a0 for its own argument (n−1). Since the outer call still needs its original n after the recursive call returns (to compute n * fact(n-1)), it must stash that value somewhere the recursive call can't touch — the stack.
§2.9 Communicating with People

Character Data

Text is just bytes with an agreed-upon meaning — and it's also the perfect place to see signed-vs-unsigned and stack conventions fuse into one realistic example: a hand-rolled strcpy.

Byte / Halfword Load-Store

You could do character manipulation with pure bitwise operations on word-aligned data, but string processing is common enough that MIPS gives it dedicated instructions:

lb  rt, offset(rs)   # load byte, sign-extend to 32 bits
lh  rt, offset(rs)   # load halfword, sign-extend to 32 bits
lbu rt, offset(rs)   # load byte, zero-extend to 32 bits
lhu rt, offset(rs)   # load halfword, zero-extend to 32 bits
sb  rt, offset(rs)   # store just the rightmost byte of rt
sh  rt, offset(rs)   # store just the rightmost halfword of rt

This is a direct callback to §2.4's sign-extension rules — now you see exactly where lbu's zero-extension matters in practice.

Walkthrough: strcpy

C code (naïve, null-terminated string copy):

void strcpy (char x[], char y[]) {
    int i;
    i = 0;
    while ((x[i]=y[i]) != '\0')
        i += 1;
}

Addresses of x, y arrive in $a0, $a1; i lives in $s0.

CMIPSLine-by-line explanation
(prologue)addi $sp, $sp, -4Reserve 1 word on the stack.
sw $s0, 0($sp)Save the caller's $s0 — callee-saved obligation, exactly as in §2.8.
i = 0;add $s0, $zero, $zeroi = 0 (adding $zero + $zero is a clean way to zero a register — same "add with $zero" trick from §2.3, applied twice).
while loop bodyL1: add $t1, $s0, $a1t1 = address of y[i]. No ×4 scaling here — unlike the earlier int-array examples, chars are exactly 1 byte, so the byte offset equals the index directly.
lbu $t2, 0($t1)t2 = y[i], loaded as an unsigned byte and zero-extended — we want the raw character value, not a sign-extended (potentially negative) one.
add $t3, $s0, $a0t3 = address of x[i] (again, no scaling — 1 byte per char).
sb $t2, 0($t3)x[i] = y[i] — store just the low byte of t2 into x[i]. This is literally the C statement x[i]=y[i].
beq $t2, $zero, L2If the character we just copied was the null terminator ('\0' = 0), exit the loop — this is the C while-condition test, done inline right after the assignment, matching how C's (x[i]=y[i]) != '\0' evaluates the assignment's value.
addi $s0, $s0, 1i += 1 — only reached if we didn't just copy the terminator.
j L1Loop back to copy the next character.
(epilogue)L2: lw $s0, 0($sp)Restore the caller's $s0.
addi $sp, $sp, 4Pop the stack slot.
jr $raReturn (strcpy is a leaf procedure — it calls nothing else, so no $ra save was needed).
⚠️ Exam Trap

Compare this to the earlier save[i] / A[8] examples: there, addresses required sll $t1,$s3,2 (×4) because the arrays held 4-byte words. Here, with char arrays, there is no scaling at all — the byte offset equals the index. On an exam, always check the element size of the array in the problem before deciding whether (and by how much) to scale the index.

Self-TestWhy does strcpy use lbu rather than lb to load each character?

Character bytes with the high bit set (e.g. extended ASCII/Latin-1 values 128–255) would be sign-extended into a negative 32-bit number by lb — which is meaningless for character data and would also break the beq $t2,$zero,L2 null-check logic if a comparison against a signed interpretation were ever needed elsewhere. lbu zero-extends, preserving the character's raw unsigned byte value in the low 8 bits with the upper 24 bits cleanly zeroed.
§2.10 MIPS Addressing for 32-Bit Immediates and Addresses

32-bit Addressing

The 16-bit immediate field is a tight squeeze — this section covers the three ways MIPS stretches past it: for constants, for branches, and for jumps.

32-bit Constants

Most constants fit comfortably in the 16-bit immediate field. For the rare 32-bit constant, MIPS builds it in two steps:

lui rt, constant   # copies the 16-bit constant into the LEFT (upper) 16 bits of rt, clears the right 16 bits to 0

Worked example:

lhi $s0, 61          # $s0 = 0000 0000 0111 1101 0000 0000 0000 0000
ori $s0, $s0, 2304   # $s0 = 0000 0000 0111 1101 0000 1001 0000 0000

Step 1 places the upper bits; step 2 bitwise-ORs in the lower bits — since the lower 16 bits were just cleared to 0 by step 1, ORing in the new value cleanly merges them without disturbing the upper half.

⚠️ Exam Trap — why ori, not addi?

If the lower 16-bit value's most-significant bit happens to be 1, addi would sign-extend it before adding — potentially corrupting (subtracting from) the upper bits you just carefully placed with lui. ori performs a pure bitwise OR with no sign-extension surprises, so it's always the safe choice for merging in the lower half of a 32-bit constant.

Branch Addressing

op6 bits
rs5 bits
rt5 bits
constant or address16 bits

Branch instructions encode an opcode, two registers, and a 16-bit target field. Since most branch targets are near the branch itself (forward or backward), MIPS uses PC-relative addressing:

target address = PC + offset × 4
🔍 Subtle but frequently tested

The ×4 is there because the 16-bit field stores a word offset, not a byte offset — since instructions are always word-aligned, this effectively quadruples the reachable range for the same 16 bits. Also: the PC has already been incremented by 4 (to point at the next sequential instruction) by the time this offset is added — so the offset is relative to the instruction after the branch, not the branch itself. This detail matters again later in the course when you study the pipelined datapath.

Jump Addressing

op6 bits
address26 bits

j and jal targets could be anywhere in the text segment, so their address is encoded directly (no offset math relative to the current instruction):

target address = PC[31...28] : (address × 4)

This is called (pseudo)direct addressing — "pseudo" because the top 4 bits aren't actually stored in the instruction at all; they're borrowed from the current PC's upper bits at jump time.

⚠️ Exam Trap

Because it reuses the current PC's top 4 bits rather than storing a truly absolute address, a jump cannot reach an arbitrary 32-bit address if that address falls outside the current 256 MB-aligned region (defined by those same top 4 bits). This is exactly why it's called pseudodirect rather than direct addressing — a great "why pseudo" short-answer question.

Worked Target-Addressing Example

Reusing the loop code from §2.7, assume Loop: sits at memory location 80000:

AddressInstructionEncoded (op, fields…)
80000Loop: sll $t1, $s3, 20, 0, 19, 9, 4, 0
80004add $t1, $t1, $s60, 9, 22, 9, 0, 32
80008lw $t0, 0($t1)35, 9, 8, 0
80012bne $t0, $s5, Exit5, 8, 21, 2
80016addi $s3, $s3, 18, 19, 19, 1
80020j Loop2, 20000
80024Exit: …

The j Loop instruction at address 80020 needs to encode target 80000. The jump field stores the target divided by 4: 80000 ÷ 4 = 20000 — which is exactly the encoded value shown above.

Branching Far Away

If a branch target is too far away to fit in the signed 16-bit offset (×4), the assembler automatically rewrites the code using an inverted branch plus an unconditional jump:

beq $s0, $s1, L1
      ↓  (assembler rewrite)
bne $s0, $s1, L2
j   L1
L2: …

This is the assembler synthesizing an "escape hatch" for the rare far-branch case, while keeping the common near-branch case fast and compact — Design Principle #4 (good compromises) showing up yet again.

Addressing Mode Summary

Register addressing

Operand is a register itself. Used by nearly every R-format instruction.

Base/displacement addressing

Operand is at Memory[reg + offset]. Used by lw/sw.

Immediate addressing

Operand is a constant embedded in the instruction. Used by addi.

PC-relative addressing

Target = PC + offset×4. Used by branches (beq/bne).

Pseudodirect addressing

Target = upper 4 bits of PC + address×4. Used by j/jal.

Self-TestA j instruction sits at address 4096 and must jump to address 4864. What value is encoded in its 26-bit address field?

4864 ÷ 4 = 1216. Note the current instruction's own address (4096) is irrelevant to this calculation — unlike branch addressing, jump addressing never uses PC-relative arithmetic; it only divides the absolute target by 4.
§2.11 Parallelism and Instructions: Synchronization

Synchronization

The moment two processors share memory, correctness depends on more than just correct arithmetic — it depends on the order of accesses being controlled.

Why We Need It

Suppose two processors share an area of memory: P1 writes, then P2 reads. If P1 and P2 don't synchronize, you get a data race — the result depends on the order accesses happen to interleave, which is exactly the kind of nondeterministic bug that's brutal to debug.

The fix requires hardware support for an atomic read/write memory operation: no other access to that location is allowed to sneak in between the read and the write. This can be either:

  • A single atomic instruction (e.g., an atomic swap of register ↔ memory), or
  • An atomic pair of instructions.

MIPS takes the second approach.

Synchronization in MIPS: ll / sc

ll rt, offset(rs)   # load linked
sc rt, offset(rs)   # store conditional
  • sc succeeds (writes memory, returns 1 in rt) only if the memory location has not changed since the matching ll.
  • sc fails (memory left untouched, returns 0 in rt) if the location was changed by something else in between.

Worked Example: Atomic Swap (Lock Acquisition)

try: add $t0, $zero, $s4    # copy exchange value
     ll  $t1, 0($s1)        # load linked
     sc  $t0, 0($s1)        # store conditional
     beq $t0, $zero, try    # branch back if store failed
     add $s4, $zero, $t1    # put loaded value in $s4
MIPS lineWhat's happening
add $t0, $zero, $s4Copy the value we want to write into the lock location — $t0 now holds our "new" value.
ll $t1, 0($s1)Atomically begin the read: load the current lock value into $t1, and mark this address as being "watched" by the hardware.
sc $t0, 0($s1)Attempt to write $t0 back to the lock location — but only if nothing else touched it since the ll. On success, $t0 is overwritten with 1; on failure, $t0 becomes 0.
beq $t0, $zero, tryIf the store failed (t0 == 0, meaning someone else raced us), jump back to try and redo the whole sequence from scratch.
add $s4, $zero, $t1Success! Place the old lock value (captured by ll, into $t1) into $s4 for the caller to inspect.
⚠️ Exam Trap

sc failing is not an error or exception — it's an expected, designed-for outcome under contention. Code using ll/sc must always wrap the pair in a retry loop (as shown above). Forgetting the retry loop is a classic "why doesn't my lock work" bug that shows up constantly once students move from this chapter into systems/OS coursework.

Self-TestWhy does MIPS use a pair of instructions (ll/sc) instead of one atomic swap instruction?

The slides present this as a genuine design choice with two valid options — MIPS opted for the ll/sc pair, which is more flexible: the same primitive can be used to build not just atomic swap, but also compare-and-swap, atomic increment, and other read-modify-write patterns, all without needing a dedicated hardware instruction for each one. The cost is that software must handle the retry loop itself.
§2.12 Translating and Starting a Program

Translation, Linking & Loading

How does a .c file on disk turn into a running process? This section is the "software supply chain" of the whole course — a picture worth memorizing cold.

C source → Compiler → Assembly → Assembler → Object module(s) → Linker → Executable → Loader → Running program

Many compilers today produce object modules directly (skipping a separate textual assembly step), but conceptually all four stages — compile, assemble, link, load — still occur.

Assembler Pseudoinstructions

Most assembly instructions map one-to-one onto real machine instructions. Pseudoinstructions are the exception — "figments of the assembler's imagination" that get expanded into one or more real instructions.

move $t0, $t1     →   add $t0, $zero, $t1

blt $t0, $t1, L   →   slt $at, $t0, $t1
                       bne $at, $zero, L

$at (register 1, "assembler temporary") exists specifically to give the assembler scratch space for these multi-instruction expansions — space guaranteed not to collide with any register the programmer is actively using.

🤔 Why do we even need $at?

The blt expansion needs to compute a comparison result before it can branch — and that intermediate result has to live somewhere. If the assembler grabbed, say, $t0 for this, it could silently clobber a value the programmer was actively relying on. Reserving $at exclusively for the assembler's own use avoids that entire class of bug.

Producing an Object Module

The assembler (or compiler) translates a program into machine instructions, plus everything needed to later assemble a complete program from multiple pieces:

Header

Describes the contents of the object module.

Text segment

The translated instructions.

Static data segment

Data allocated for the program's whole lifetime.

Relocation info

Flags content that depends on the absolute location of the loaded program.

Symbol table

Global definitions and external references.

Debug info

Associates machine code back with source code.

Linking Object Modules

The linker produces an executable image in three steps:

  1. Merge segments from all the object modules being combined.
  2. Resolve labels — determine the final address of every symbol.
  3. Patch location-dependent and external references now that real addresses are known.

Historically this could leave some location-dependencies for a relocating loader to fix up at load time — but with virtual memory, that's usually unnecessary: every program can simply be loaded starting at the same absolute location within its own virtual address space.

Loading a Program

  1. Read the header to determine segment sizes.
  2. Create a virtual address space.
  3. Copy text and initialized data into memory (or set up page table entries so they fault in lazily instead).
  4. Set up arguments on the stack.
  5. Initialize registers — including $sp, $fp, $gp.
  6. Jump to a startup routine that copies arguments into $a0, … and calls main. When main returns, the runtime performs an exit syscall.

Dynamic Linking

Instead of linking every library at build time, dynamic linking defers linking/loading a library procedure until it is actually called at runtime. This requires the procedure code to be relocatable. Benefits:

  • Avoids image bloat from statically linking every (transitively) referenced library into every single executable.
  • Automatically picks up new library versions — no recompilation needed when a shared library is updated.

Lazy Linkage

The mechanism: an indirection table holds a small stub for each not-yet-resolved routine. On the first call, the stub loads a routine ID and jumps into linker/loader code, which resolves the real address and patches the indirection table. On every subsequent call, the (now-patched) table jumps straight to the resolved, dynamically-mapped code — paying the resolution cost exactly once.

This "resolve once, then jump directly forever after" pattern is precisely the mechanism behind the PLT/GOT (Procedure Linkage Table / Global Offset Table) in real ELF binaries on Linux, if you want the modern-day name for it.

☕ Aside: Starting Java Applications

The JVM defines a simple, portable instruction set (bytecode). By default the JVM interprets bytecode directly — but a JIT (just-in-time) compiler monitors execution and compiles "hot" (frequently executed) methods down into native machine code specific to the host machine, for a big speed boost on the code that matters most. This is a nice real-world callback to the "ISA vs. implementation" theme from §2.1 — bytecode is itself a kind of ISA, just one implemented in software (interpretation) as often as hardware.

Self-TestWhat two concrete problems does dynamic linking solve compared to static linking?

(1) It avoids image bloat — with static linking, every executable that uses a library carries a full copy of it; with dynamic linking, one shared copy serves every process. (2) It automatically picks up new library versions — since linking happens at call-time rather than build-time, an updated shared library benefits every program that uses it without anyone needing to recompile.
§2.19 – 2.20 Fallacies, Pitfalls & Concluding Remarks

Fallacies, Pitfalls & Wrap-up

The textbook closes every chapter this way on purpose — these are the misconceptions and bugs that experienced engineers still fall for, distilled into an exam-ready list.

Fallacy: "A more powerful instruction means higher performance"

The intuition is that fewer, more powerful instructions should mean less total work. But:

  • Complex instructions are hard to implement efficiently in hardware.
  • Supporting them can slow down the clock for every instruction, including simple ones that didn't need the extra complexity — because the whole chip shares one clock speed.
  • Modern compilers are excellent at generating fast code from simple instructions — hand-written assembly for "performance" rarely beats a good compiler's output today, and more lines of code (including hand-tuned asm) means more bugs and less productivity.

Fallacy: "Backward compatibility means the instruction set never changes"

In reality, ISAs almost always only ever add instructions over time (removing one would break old binaries) — this is called instruction set accretion. It's exactly why the x86 instruction set has ballooned over 40+ years: MMX, SSE, AVX, and more, all layered on top of the original design, never removed.

Pitfall: Sequential words are not at sequential addresses

The textbook explicitly calls this out as an official "pitfall" — a direct callback to the byte-addressing trap from §2.3. Increment word pointers by 4, not 1!

Pitfall: Keeping a pointer to an automatic variable after the procedure returns

E.g., passing the address of a local (stack) variable back to the caller via an out-parameter. The moment the procedure returns and its stack frame is popped, that pointer becomes invalid — the memory it points to can be silently overwritten by the very next function call. This is the root cause behind classic C compiler warnings like "returning address of local variable."

⚠️ Exam Trap

Both pitfalls above are extremely popular as short "spot the bug" exam questions — you'll often be shown a snippet of C or MIPS and asked to identify which of these two classic mistakes it contains.

Concluding Remarks: The Four Design Principles

Every "why does MIPS do it this way" question in this chapter ultimately traces back to one of these four:

1. Simplicity favors regularity

The fixed 3-operand shape, uniform instruction formats.

2. Smaller is faster

32 registers, not millions — small structures are fast structures.

3. Make the common case fast

Immediate operands avoid a load for common small constants.

4. Good design demands good compromises

Multiple instruction formats, beq/bne-only branches, ll/sc pairs.

Layers of Software / Hardware

Compiler → Assembler → Hardware — each layer builds an abstraction the layer above can rely on, exactly mirroring the translation pipeline from §2.12.

MIPS in Context

MIPS is typical of RISC ISAs generally (Reduced Instruction Set Computer) — simple, regular, fixed-length instructions, load/store-only memory access. This stands in contrast to x86, a CISC (Complex Instruction Set Computer) design with variable-length instructions and memory-operand arithmetic — the polar opposite of nearly every regularity choice we've studied this chapter.
