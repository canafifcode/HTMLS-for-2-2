The Single-Cycle CPU at a Glance

Condensed from Part 1, slides 2–22

One instruction, one clock cycle, one trip through the whole machine.

Our processor implements a deliberately small MIPS subset — small enough to build, rich enough to show every important idea:

  • Memory reference: lw, sw
  • Arithmetic/logical (R-type): add, sub, and, or, slt
  • Control transfer: beq (Part 2's pipeline drops j to keep the datapath clean)

Every instruction, regardless of type, follows the same skeleton: the PC addresses instruction memory and fetches an instruction; register numbers from the instruction fields read the register file; the ALU computes an arithmetic result, a memory address, or a comparison; loads and stores touch data memory; and finally the PC becomes either the branch target or PC + 4.

FIG 0.1 — The complete single-cycle datapath. Multiplexers stand wherever two different sources compete for one destination; you can never simply join wires together.

The elements, in one breath

Combinational elements (ALU, adders, multiplexers, the sign-extender) compute outputs purely from present inputs. State elements (the PC, the register file, the memories) store information and update only on the clock edge — and only when their write-control input says so. Data therefore flows state → combinational logic → state within each cycle, and the longest combinational delay between two state elements sets the clock period. Tattoo that sentence somewhere; it is the entire reason Part 2 exists.

Keep This

The instruction formats matter constantly in Part 2. All MIPS instructions are 32 bits: R-format op rs rt rd shamt funct (6-5-5-5-5-6), I-format op rs rt imm16, and the destination register is rd for R-type but rt for loads — a mux (RegDst) chooses between them. That little asymmetry will come back to haunt us in the pipeline.

EXAMWhich control signals are "don't care" (X) for sw, and why is marking them X (not 0) legitimate?▼

RegDst and MemtoReg are X for sw (and for beq). A store never writes the register file, so it does not matter which register number the RegDst mux selects or which value the MemtoReg mux presents — RegWrite = 0 guarantees nothing is committed. Marking them X lets the logic minimizer produce simpler control equations. The trap: MemWrite, RegWrite are never X — an accidental 1 there would corrupt state.

Recap · 3 of 3

Why Single-Cycle Falls Short

Part 1, slide 33 — the bridge into Part 2

The clock must be slow enough for the slowest instruction — and that punishes everyone.

In a single-cycle design, every instruction takes exactly one cycle, so the period must cover the critical path — the longest journey any instruction makes. That instruction is lw:

Instruction memory → Register file → ALU → Data memory → Register file

A beq finishes far earlier, but it still waits out the full period. Varying the period per instruction is not feasible in synchronous design, and it violates the great design principle from Chapter 1: make the common case fast. The fix is not to make instructions faster — it is to stop letting the hardware sit idle. That fix is pipelining, and it is the entire subject of Part 2.

Classic Exam Trap

"Pipelining reduces the execution time of each instruction." False. Each instruction takes the same time (or slightly longer, because of register overhead). Pipelining increases throughput — instructions completed per second — not per-instruction latency. Expect a true/false or MCQ on exactly this distinction.

§4.5 · Slide 2

The Laundry Analogy

Part 2, slide 2

Pipelining is not doing one thing faster. It is doing many things at once, each in a different stage of completion.

Four housemates each have laundry to do: wash (30 min), dry (30 min), fold (30 min), and put away (30 min). Done sequentially, each person's laundry takes 2 hours and four loads take 8 hours. But the washer is idle while the dryer runs. So: as soon as load 1 moves to the dryer, load 2 enters the washer. Every 30 minutes a new load starts, and all four finish in 3.5 hours.

Notice three things, because each becomes a theorem about processors:

  • Each individual load still takes 2 hours. Latency is unchanged; only throughput improved.
  • The speedup comes from overlap — four resources working simultaneously on four different loads.
  • The stage rate is set by the slowest stage. If drying took 45 minutes, loads could only start every 45 minutes, and washers would idle again.
Brainstorm

What is the laundry equivalent of a "hazard"? Suppose load 2 cannot be washed until load 1's clothes are folded, because they share a garment bag. Load 2 must wait — the washer bubbles along empty. Keep this picture; it is exactly a data hazard, and the empty washer slot is exactly a bubble.

The Five Stages of the MIPS Pipeline

Part 2, slides 3–4

MIPS execution divides into five stages, one step per stage, one stage per clock cycle:

StageNameWhat happensHardware used
IFInstruction FetchRead instruction at PC; compute PC+4Instruction memory, PC adder
IDInstruction DecodeDecode fields; read rs and rt from register file; sign-extend immRegister file (read ports), sign-extender
EXExecuteALU operation, or address calculation, or compare for branchALU, branch adder
MEMMemory Accesslw reads / sw writes data memory; others pass throughData memory
WBWrite BackWrite result into the register fileRegister file (write port)

The single-cycle datapath already has this left-to-right structure; pipelining simply draws vertical lines through it and lets a different instruction occupy each region every cycle:

FIG 1.1 — The datapath partitioned into its five stages. In a pipelined machine, five different instructions live in these five regions simultaneously.
Edge Cases & Fine Print

Not every instruction uses every stage — sw never writes back, beq uses neither MEM nor WB usefully, R-types skip MEM. They still pass through all five stages, doing nothing in the unused ones. This uniformity is what keeps the pipeline simple: one instruction enters and one leaves every cycle, no scheduling required. The "wasted" pass-through cycles are the price of regularity.

EXAMWhy does ID read two registers even for lw, which only needs one (the base register rs)?▼

Because at the moment ID happens, the machine reads both rs and rt speculatively — decoding which are actually needed would take extra logic and time, and reading an unneeded register is harmless. For lw the rt read is simply ignored; for sw the rt read supplies the data to store. Reading both unconditionally keeps the ID stage fast and uniform.

The speedup law

If all stages were perfectly balanced:

Time between instructionspipelined = Time between instructionsnonpipelined / Number of stages

Here that ideal would give 800/5 = 160 ps. Because we are unbalanced, we get 200 ps — imbalance always costs speedup. And crucially, the gain is throughput; the latency of each instruction does not decrease (in fact one lw now occupies 5 × 200 = 1000 ps of pipeline, more than its 800 ps single-cycle time).

Worked Example — slide 8, fully expanded

Three instructions. Pipelined: first finishes at 5×200 = 1000 ps, then one per 200 ps → T = 1400 ps. Non-pipelined: 3 × 800 = 2400 ps. Speedup = 2400/1400 ≈ 1.71. Far below 4× — with so few instructions, the fill time of the pipeline dominates.

Now add 1,000,000 instructions.
Tpipelined = 1,000,000 × 200 + 1400 = 200,001,400 ps
Tnonpipelined = 1,000,000 × 800 + 2400 = 800,002,400 ps
Speedup = 800,002,400 / 200,001,400 ≈ 4.0 = the clock-period ratio 800/200.

Moral: as instruction count → ∞, speedup → Tc,single / Tc,pipe, not the number of stages. The number of stages is only the ideal ceiling when stages are balanced.

Exam Traps (three of them)

1. Using 160 ps (=800/5) as the pipelined period. Wrong: the period is the max stage delay, 200 ps.
2. Forgetting fill time: the first instruction still needs 5 cycles before the "one per cycle" rhythm starts. For N instructions: cycles = N + (stages − 1).
3. Claiming pipelining shortens instruction latency. It doesn't; it can even lengthen it (register overhead, unbalanced stages).

EXAMA 5-stage pipeline has stage delays 150, 200, 180, 220, 100 ps, and pipeline registers add 20 ps each. Find the clock period, the latency of one instruction, and the ideal speedup vs. single-cycle.▼

Period = max(stage) + overhead = 220 + 20 = 240 ps. Latency = 5 × 240 = 1200 ps (every stage stretches to the period). Single-cycle period = sum = 150+200+180+220+100 = 850 ps. Speedup for large N = 850/240 ≈ 3.54 — less than 5 because of imbalance and register overhead. This two-penalty structure (imbalance + overhead) is the standard exam variation.

§4.5 · Slide 9

MIPS Was Born to Be Pipelined

Part 2, slide 9

The ISA decisions of Chapter 2 were not aesthetic choices — they were pipeline engineering, done years in advance.

  • All instructions are 32 bits. Fetch is trivially one cycle: read one word, done. Contrast x86, whose instructions run 1 to 17 bytes — you cannot even know where the next instruction starts until you have partially decoded this one.
  • Few, regular formats. rs and rt sit in the same bit positions in every format, so the register file can be read in parallel with figuring out what the opcode even is. Decode and register-read share one stage.
  • Load/store architecture. Memory operands only appear in lw/sw, whose address is always base + offset. So the address is computed in stage 3 (EX) and memory touched in stage 4 (MEM) — a clean fit. An ISA allowing add r1, (r2) would need address-calc and memory and arithmetic in one instruction: the stages stop lining up.
  • Aligned memory operands. A word never straddles two memory words, so every access completes in exactly one MEM cycle — no instruction ever needs two.
EXAMGive two concrete reasons variable-length instructions (like x86's 1–17 bytes) complicate pipelining.▼

(1) Fetch alignment: the next PC depends on this instruction's length, so IF can't compute PC+len until partial decode — fetch and decode become entangled instead of independent stages. (2) Field extraction: register specifiers sit at varying offsets, so the register file cannot be read speculatively in parallel with decode. (Modern x86 chips solve this by translating to fixed-length micro-ops internally — effectively building a MIPS-like machine behind a translator.)

§4.5 · Slide 11

Structural Hazards

Part 2, slide 11

Suppose we had one unified memory. In cycle 4 of our three-lw example, instruction 1 is in MEM reading data while instruction 4 wants IF — both need the memory in the same cycle. One of them must wait: the fetch stalls, and a bubble (a do-nothing slot) ripples down the pipeline.

MIPS's solution is blunt and effective: separate instruction and data memories (in real silicon, separate L1 instruction and data caches). Likewise the register file is engineered so ID (two reads) and WB (one write) can coexist in one cycle — more on that clever timing in Part III.

Edge Case

Could a structural hazard exist on the ALU? In our 5-stage MIPS: no — each stage has its own adder (PC+4 adder in IF, branch adder + main ALU in EX), precisely so no two stages compete. That's a design choice, not luck: the textbook pipeline eliminates structural hazards by construction, by duplicating hardware. Machines with (say) one multiplier shared by several stages genuinely stall on structural hazards.

EXAMWith a single unified memory, how many stalls does a lw itself force onto the pipeline behind it?▼

One bubble per memory-stage conflict: when the lw occupies MEM (its cycle 4), the instruction trying to fetch that same cycle must wait one cycle. So each load or store introduces one stall cycle for the instruction three behind it. With loads/stores being ~30% of instructions, that alone would add ~0.3 to CPI — which is why nobody builds unified-memory pipelines.

★ = value actually computed here (end of CC3). ✎ = value written to register file here (CC5). The sub needs $s0 at the start of its EX (CC4) — one full cycle before the register file gets it, and its ID read in CC3 was two cycles too early.

The rescue: forwarding (bypassing)

Ask the slide's own question: when is the value actually ready? For an R-type, at the end of EX — it exists in the datapath (about to be latched into a pipeline register), it just hasn't reached the register file. So don't wait for the register file. Run a wire from where the value is to where it is needed: from the ALU's output straight back to the ALU's input for the next instruction.

add computes $s0 at end of CC3; sub needs it at start of its EX in CC4. End of CC3 = start of CC4. The timing works with zero stalls — provided we add the extra connections (muxes at the ALU inputs) and the logic to control them. That hardware is Part III's whole story.

The Golden Rule of Forwarding

Forwarding works whenever the value is produced in an earlier-or-equal cycle than it is consumed. You can send data forward in time, never backward. Every forwarding question on every exam reduces to comparing two clock-cycle numbers: ready-at vs needed-at.

Exam Trap

"Forwarding eliminates all data-hazard stalls." False — the load-use case always costs one bubble even with full forwarding. Conversely, "a load followed by a dependent instruction always stalls" is also too strong: if one unrelated instruction sits between them, the gap absorbs the delay and no stall occurs. Count the cycles, always.

EXAMlw $t0, 0($a0); add $t1, $t0, $t0 — how many stalls with full forwarding? What if an unrelated ori is inserted between them?▼

Back-to-back: 1 stall (load-use). With one independent instruction between: the add's EX naturally lands one cycle later, exactly when MEM/WB forwarding can serve it — 0 stalls. This is precisely why compilers reorder code (next section).

§4.5 · Slides 22–24

Code Scheduling: The Compiler Joins the Fight

Part 2, slides 22–24

The hardware stalls when it must — but the compiler can often rearrange instructions so it never has to. The slides' example: compile A = B + E; C = B + F;

« stall »lw  $t4, 8($t0)  ← hoisted

Both stalls were load-use hazards: lw $t2→add $t3, and lw $t4→add $t5. Hoisting the third load into the first gap fixes both at once: it separates $t2 from its user, and it moves $t4's load three instructions ahead of $t4's user. Two stalls saved, 13 → 11 cycles.

Edge Cases the Compiler Must Respect

Reordering is only legal if it preserves meaning: the hoisted lw must not (a) overwrite a register still needed ($t4 is fresh — fine), (b) move across a store to the same address (memory aliasing! lw 8($t0) vs sw 12($t0) — different offsets from the same base, provably distinct, so legal), or (c) cross a branch. Exam questions love to offer an "optimization" that silently violates one of these.

EXAMIn the scheduled version, verify with cycle numbers that no load-use stall remains.▼

Number the scheduled instructions 1–7, issue one per cycle. lw $t2 (instr 2) has MEM in CC5; add $t3 (instr 4) has EX in CC6 — MEM→EX forward, legal. lw $t4 (instr 3) MEM in CC6; add $t5 (instr 6) EX in CC8 — two cycles of slack, no forwarding even needed from MEM (register file suffices by CC8's read... in fact MEM/WB forwarding or the write-then-read register trick covers it). 7 instructions + 4 fill = 11 cycles, matching the slide.

§4.5 · Slides 25–27

Control Hazards

Part 2, slides 25–27

Every cycle the pipeline must fetch something — but a branch doesn't tell you what until it resolves.

By the time beq $1, $2, 40 has merely reached ID, the machine should already be fetching the next instruction. Fetch what — the fall-through or the target? In the plain datapath, the comparison happens in EX (ALU subtract, test Zero) and the PC is updated from the branch logic even later; meanwhile wrong-path instructions may have marched in behind and must be squashed into bubbles if the branch is taken.

Cure #1: resolve the branch earlier

Slide 27's "improved" design adds hardware to do everything in ID: an extra register-equality comparator (XOR-and-NOR the two register values — cheaper and faster than the full ALU), plus a dedicated target adder. Now only the single instruction fetched during the branch's ID is in doubt. Cost of a taken branch: one bubble — the slide's timing shows the next correct fetch beginning 400 ps (two cycles) after the branch's fetch instead of the usual 200 ps.

Edge Case: what moving the branch to ID costs elsewhere

Resolving in ID means the comparator needs its operands in ID — one stage earlier than the ALU would. If those operands come from an instruction just ahead, forwarding into ID may be impossible in time, creating extra stalls (e.g., a load immediately followed by a dependent branch needs two stalls). Early resolution trades a smaller branch penalty for occasionally harder data hazards. §4.5 · Slides 28–30

Branch Prediction

Part 2, slides 28–30

For longer pipelines (or branches resolved later), stalling on every branch is unacceptable. So: guess, keep fetching at full speed, and pay only when wrong.

Predict not taken — MIPS's simple default

Always fetch the fall-through instruction. If the branch is not taken (prediction correct): zero penalty, the pipeline never missed a beat. If taken (prediction incorrect): squash the wrong-path instruction(s) already fetched — turn them into bubbles — and fetch the target. With ID-stage resolution the misprediction penalty is that same single bubble.

Static vs. dynamic prediction

SchemeRuleRationale
StaticBackward branches: predict taken. Forward branches: predict not taken.Backward branches close loops, and loops iterate many times (taken far more often than not); forward branches guard if-statements, often skipped.
DynamicHardware records each branch's recent history and predicts the trend continues.Real branches are creatures of habit; typical accuracy >90%. On a miss: stall/flush, re-fetch, and update the history.
EXAMA loop branch is taken 9 times then falls through (10 executions). How many mispredictions under (a) predict-not-taken, (b) static backward-taken, (c) a 1-bit dynamic predictor initialized "not taken"?▼

(a) Every taken execution mispredicts: 9. (b) Backward ⇒ predicted taken every time: wrong only on the final fall-through: 1. (c) 1-bit: first execution mispredicts (predicted NT, was T), flips to T; correct for executions 2–9; final execution mispredicts (predicted T, was NT): 2. Bonus insight: on the loop's next full run, the 1-bit predictor mispredicts twice again (it was left saying NT) — the classic argument for 2-bit counters.

§4.5 · Slide 31

Delayed Branch: The MIPS Solution

Part 2, slide 31

If one instruction after the branch will be fetched no matter what — make that official.

MIPS defines the instruction slot immediately after a branch as the branch delay slot: it is always executed, taken or not. The hardware never wastes the slot; instead, the assembler/compiler fills it with something useful — typically an instruction from before the branch that the branch doesn't depend on. The one-cycle delay is thereby hidden by rearrangement, and the "penalty" becomes zero when the slot is filled usefully.

# before scheduling            # after scheduling (delay slot filled)
add  $s1, $s2, $s3             beq  $s0, $zero, target
beq  $s0, $zero, target        add  $s1, $s2, $s3   # delay slot: always runs
(delay slot: nop)              ...
Exam Traps

1. The delay-slot instruction executes even when the branch is taken. Tracing code and skipping it is the #1 error.
2. The instruction moved into the slot must be independent of the branch decision (can't move the compare itself!) and safe to execute on both paths.
3. Why is this a "solution to the control hazard"? Because with ID-stage resolution there is exactly one uncertain slot — and the ISA legalizes it. Deeper pipelines with multi-cycle branch latency made delay slots obsolete (you'd need several), which is why modern ISAs dropped them: an ISA feature that froze one microarchitecture's timing into the architecture forever.

The Big Picture — §4.5 in Four Lines

Part 2, slide 32
  • Pipelining improves performance by increasing instruction throughput — many instructions in flight, each with unchanged latency.
  • It is subject to structural, data, and control hazards.
  • ISA design (fixed length, regular formats, load/store, alignment) determines how painful pipelining is to implement.
  • The cures — duplication, forwarding, stalling, scheduling, early resolution, prediction, delay slots — each attack one hazard.

§4.6 · Slide 33

The MIPS Pipelined Datapath

Part 2, slide 33

Almost everything flows left-to-right. The two wires that flow right-to-left are exactly the two hazards.

FIG 2.1 — The stage-partitioned datapath with its two right-to-left flows called out: the branch target returning to the PC (control hazard) and the write-back value returning to the register file (data hazard).

Study the direction of every wire in Fig 2.1. Left-to-right flows are harmless: they hand a value from an older stage to a younger one within the same instruction. The two right-to-left flows are different — they carry information from a later stage of one instruction back to an earlier stage where a different, younger instruction now lives:

  • MEM→IF: the branch decision updating the PC — the control-hazard source. Whatever was fetched in the meantime may be wrong.
  • WB→ID: the write-back into the register file — the data-hazard source. Whoever read that register in the meantime got a stale value.
Professor's Compass

This is the single most orienting slide of the deck. Whenever you're lost later — in forwarding conditions, in hazard detection — come back to this picture and ask: which right-to-left wire is misbehaving? Everything in §4.7 is machinery to manage exactly these two arrows.

§4.6 · Slide 34

Pipeline Registers

Part 2, slide 34

Five instructions share one datapath. What keeps them from trampling each other? Four walls.

Between every pair of stages sits a wide clocked register — IF/ID, ID/EX, EX/MEM, MEM/WB — named for the stages it separates. On every clock edge, each register captures everything its left-hand stage produced, and holds it steady for the right-hand stage all next cycle. An instruction's entire state — operand values, immediate, computed results, register numbers, control bits — must ride these registers forward; anything not latched is lost, overwritten by the instruction one step behind.

The table above is the data-only baseline your exam most likely asks for; state your assumptions when answering.

EXAMWhy does IF/ID carry PC+4 along? IF is over — who still needs it?▼

The branch target is computed as (PC+4) + (offset << 2) — in the EX stage, two cycles after fetch. By then the architectural PC has moved on (it points at younger instructions), so the branch must use its own private, latched copy of PC+4, carried through IF/ID and ID/EX. General principle: an instruction may only use values that traveled with it; the live datapath belongs to someone else now.

Exam Trap

"Why is there no WB/IF register after the fifth stage?" Because WB's result lands in the register file, which is itself the state element beginning the next instruction's journey. The register file and PC are architectural state; pipeline registers are invisible microarchitectural plumbing. Confusing the two costs marks on definition questions.

§4.6 · Slides 35, 46–49

Two Ways to Draw a Pipeline

Part 2, slides 35, 46–49

The deck uses two complementary diagram styles; exams use both, so be fluent in both:

  • Multi-clock-cycle diagram — time flows rightward, one row per instruction (all the stage-grids in this guide). Best for counting cycles, spotting hazards, and showing overlap. It abstracts away what each stage does.
  • Single-clock-cycle diagram — a snapshot of the whole datapath during one cycle, with each stage's active hardware highlighted and up to five different instructions annotated across the five stages. Best for asking "which wires and units does instruction X use right now?"

A perfect exam-style prompt: "Draw the single-cycle diagram for clock cycle 4 of: lw, sub, add, or, slt." Answer: lw is in MEM, sub in EX, add in ID, or in IF — slt hasn't entered yet. You'd shade data memory (lw), the ALU (sub), the register file read ports (add), and instruction memory + PC adder (or), simultaneously.

Reading Trick

To convert between the two: fix a vertical line (one clock cycle) in the multi-cycle grid — the set of stage-cells it crosses is the single-cycle snapshot. One diagram is the other, sliced.

§4.6 · Slides 41–43

A Store, Stage by Stage

Part 2, slides 41–43

Store's first two stages are identical to load's (this uniformity is the pipeline's friend). The differences begin at EX:

EXSame address calculation — but now the rt register's value (read data 2) matters: it rides along into EX/MEM as the data to be stored.

Edge Case Worth Noticing

Read-data-2 must be latched through two pipeline registers (ID/EX, then EX/MEM) before MEM uses it — the value is read in cycle 2 and consumed in cycle 4. If the designer "saved space" by not carrying it through EX/MEM, the store would write whatever the following instruction's rt value happened to be. Every field in Fig 2.2's width table earns its bits this way.

§4.6 · Slides 44–45

The Destination-Register Bug — and Its Fix

Part 2, slides 44–45

The deck's most beautiful moment: the "finished" datapath contains a real bug, and you should be able to both spot it and repair it.

The bug

In WB, load writes its result to… which register? The naïve datapath wires the write-register number straight from the IF/ID register's instruction field. But WB happens in cycle 5 — by then IF/ID holds the instruction fetched three cycles later. The load would write its data into some unrelated instruction's register field. Wrong register number.

The fix

The destination register number must travel with the instruction, like everything else: latch it into ID/EX, pass it to EX/MEM, then MEM/WB, and only at WB feed it back to the register file's Write-register port — arriving in the same cycle as the data it belongs with.

FIG 2.3 — The corrected datapath: the destination register number (maroon) rides the pipeline registers alongside the data, reuniting with it at the Write-register port in WB. This adds 5 bits to ID/EX, EX/MEM, and MEM/WB.
Why Exams Adore This Bug

It tests the deepest pipeline invariant in one stroke: any value an instruction needs later must be carried forward in its own pipeline registers — never read "live" from an earlier stage. Variants to expect: "the design reads ALUSrc's immediate from IF/ID during EX — what goes wrong?" Same disease, same cure. Also expect the arithmetic follow-up: the fix widens ID/EX, EX/MEM, MEM/WB by 5 bits each (the write-register number), so the earlier width answers become 64 / 133 / 102 / 69.

EXAMWith the buggy datapath, exactly which instruction's rt/rd field would a lw's write-back use? Trace it.▼

lw is in WB during cycle 5. IF/ID is written at the end of every cycle by whatever was just fetched; during cycle 5 it holds the instruction fetched in cycle 4 — the one three after the lw (lw fetched in cycle 1, so the cycle-4 fetch is instruction #4). The lw's data would be written to instruction #4's destination field. If #4 were, say, beq, the "destination" bits are actually part of an immediate — garbage squared.

§4.7 · Slides 53–56

The Canonical Hazard Sequence

Part 2, slides 53–56

One producer, four consumers. This five-instruction sequence is the fruit fly of pipeline genetics — every case lives in it.

sub  $2, $1, $3    # $2 produced here (writes RF in CC5; $1=30, $3=50 → $2 = −20)
and  $12, $2, $5   # reads $2 in ID at CC3  — hazard!
or   $13, $6, $2   # reads $2 in ID at CC4  — hazard!
add  $14, $2, $2   # reads $2 in ID at CC5  — saved by register-file timing
sw   $15, 100($2)  # reads $2 in ID at CC6  — no hazard at all

Assume $2 held 10 before the sub, which computes −20. Without any countermeasures, who reads what?

InstructionReads $2 in (ID)Value seen (no forwarding)Verdict
andCC310 (stale)WRONG — needs help
orCC410 (stale)WRONG — needs help

So the raw hazard window is the two instructions immediately following a producer. The third is rescued by a timing trick, and the fourth is naturally safe. Forwarding exists to fix exactly those first two rows.

§4.7 · Slides 55–56

The Register-File Timing Trick

Part 2, slides 55–56 (the boxed note)

Why is the third instruction safe? Because the register file leads a double life inside a single cycle.

The slides state it precisely: a read of a register during a clock cycle returns the value written at the end of the first half of that cycle, when such a write occurs. In other words, the register file writes in the first half-cycle and reads in the second half-cycle. When sub's WB and add's ID share CC5, the write lands first and the read then picks up the fresh −20. This is sometimes called internal forwarding within the register file — drawn in diagrams as the register block shaded half-dark, half-light.

Why This Matters Beyond Trivia

It shortens the hazard window from three instructions to two — which is why the forwarding unit only ever needs to look at EX/MEM and MEM/WB (two pipeline registers back), never further. Every condition in the next section silently relies on this half-cycle convention. If an exam variant says "the register file reads before it writes," the window becomes three and you'd need a third forwarding path — know how the answer changes.

EXAMWith write-first-half/read-second-half register timing, is a hazard-detection comparison against the WB-stage instruction's destination ever needed?▼

No — for ID-stage reads, any instruction currently in WB completes its write in the first half-cycle, and the ID read in the second half sees it. That's why MIPS forwarding conditions stop at MEM/WB and never mention a "WB/beyond" register. (But note: the value sitting in MEM/WB is compared — that instruction is in WB this cycle serving the EX stage's needs via ForwardA/B = 01, a different consumer than the ID read.)

§4.7 · Slides 57–59

Detecting the Need to Forward

Part 2, slides 57–59

Hardware can't see "dependencies" — it can only compare 5-bit register numbers riding in pipeline registers. So we make it do exactly that.

First, plumbing: the register numbers themselves must travel with each instruction (just like the destination number in §2.6). Notation: ID/EX.RegisterRs means "the rs field of the instruction currently sitting in the ID/EX register" — i.e., the instruction now in its EX stage. The ALU's operands in EX are named by ID/EX.RegisterRs and ID/EX.RegisterRt.

A data hazard exists when the instruction in EX wants a register that an older instruction (now in MEM or WB) is about to write:

CaseConditionForward from
1aEX/MEM.RegisterRd = ID/EX.RegisterRsEX/MEM pipeline register (ALU result, 1 instr. ahead)
1bEX/MEM.RegisterRd = ID/EX.RegisterRtEX/MEM pipeline register
2aMEM/WB.RegisterRd = ID/EX.RegisterRsMEM/WB pipeline register (result, 2 instr. ahead)
2bMEM/WB.RegisterRd = ID/EX.RegisterRtMEM/WB pipeline register

Two guard clauses (slide 59) — where marks are won and lost

  • Only if the older instruction actually writes a register: require EX/MEM.RegWrite (resp. MEM/WB.RegWrite) asserted. Otherwise a sw or beq whose bit-pattern happens to match would trigger phantom forwarding.
  • Only if the destination isn't $zero: require RegisterRd ≠ 0. $0 is architecturally always 0; an instruction "writing" $0 discards its result, but its stale value sits in the pipeline register and would be forwarded as if it were the constant zero's new value. A sneaky, classic bug.
EXAMConstruct a two-instruction sequence where omitting the $zero guard produces a wrong result.▼

add $0, $5, $6 (result discarded — say $5+$6 = 99) followed by and $8, $0, $7. Without the guard: EX/MEM.RegisterRd = 0 = ID/EX.RegisterRs, RegWrite is even asserted for the add, so 99 gets forwarded as "$0" and the and computes 99 & $7. Correct behavior: $0 is always 0, so the and must produce 0. The guard RegisterRd ≠ 0 restores truth. (Yes, MIPS assemblers really emit writes to $0 — it's the idiomatic nop's cousin.)

Notational Edge Case

"RegisterRd" in these conditions means the destination register number carried in that pipeline register — which is rd for an R-type but rt for a load (the RegDst mux chose it back in EX). The name is historical shorthand; don't let the letter "d" convince you loads aren't covered. Loads absolutely trigger the MEM-hazard forward (that's the lw→use-after-a-gap case working correctly).

EXAMFor: sub $2,$1,$3 ; or $13,$6,$2 (one unrelated instruction between them is NOT present — or is the 2nd instruction after sub). Which condition fires and what are ForwardA/ForwardB during or's EX?▼

When or is in EX, sub is two ahead… careful: if or directly follows sub's follower (i.e., sub, and, or), then during or's EX, sub sits in MEM/WB. MEM/WB.RegisterRd=2 = ID/EX.RegisterRt (or's second source $2). So ForwardB = 01; ForwardA = 00 ($6 has no hazard). If instead or immediately followed sub, sub would be in EX/MEM: ForwardB = 10. The rhythm to internalize: distance 1 → 10 (EX/MEM); distance 2 → 01 (MEM/WB); distance ≥3 → 00.

§4.7 · Slides 64–66

The Double Data Hazard

Part 2, slides 64–66

When both conditions fire at once, only one answer is right: the most recent one.

add $1, $1, $2    # $1: 10 → 40   (with $2=30)
add $1, $1, $3    # $1: 40 → 60   (with $3=20)
add $1, $1, $4    # $1: 60 → 64   (with $4=4)   — expected!

During the third add's EX, both older adds want to forward $1: instruction 1 from MEM/WB (value 40) and instruction 2 from EX/MEM (value 60). Both raw conditions are true. If the MEM hazard wins, the ALU receives the stale 40 and computes 44 — the slide stamps it WRONG!!! The programmer's contract says the third add reads the most recent write: 60, giving 64.

The fix (slide 66): give the EX hazard priority

Revise the MEM-hazard condition so it yields whenever the EX hazard also matches — add a "not (EX hazard)" clause:

if (MEM/WB.RegWrite and (MEM/WB.RegisterRd ≠ 0)
    and not (EX/MEM.RegWrite and (EX/MEM.RegisterRd ≠ 0)
             and (EX/MEM.RegisterRd = ID/EX.RegisterRs))
    and (MEM/WB.RegisterRd = ID/EX.RegisterRs))  →  ForwardA = 01

(and symmetrically for Rt / ForwardB). Now EX/MEM — the younger, more recent result — always outranks MEM/WB. Note the elegance: the priority is encoded purely in the MEM condition; the EX condition never needed to know.

Exam Trap

Notice the not-clause repeats the full EX-hazard test including RegWrite and the $zero guard — not merely the register-number equality. Why? If the in-between instruction matches on number but doesn't actually write (RegWrite=0, e.g., a beq with matching bits), it must NOT suppress the legitimate MEM/WB forward. Abbreviating the clause to just the equality is the standard way students lose 3 marks on this question.

EXAMTrace the three adds cycle-by-cycle (values of $1 seen at each ALU) with correct priority forwarding. $1=10, $2=30, $3=20, $4=4 initially.▼

Add₁ EX in CC3: reads clean $1=10, computes 40. Add₂ EX in CC4: ForwardA=10 (add₁ in EX/MEM), gets 40, computes 60. Add₃ EX in CC5: both hazards match; priority picks EX/MEM (add₂'s 60), ForwardA=10, computes 64. Register file timeline for $1: 10 through CC4, 10/40 at CC5 (WB of add₁), 40/60 at CC6, 60/64 at CC7 — exactly the slide's table.

§4.7 · Slides 67–68

The Assembled Datapath — and a Free Lunch

Part 2, slides 67–68

Slide 67's full "Datapath with Forwarding" adds one more plumbing detail worth naming: the rs/rt/rd fields flow from IF/ID into the ID/EX register (labelled IF/ID.RegisterRs etc. on entry), so the forwarding unit in EX always has the current EX-instruction's operand numbers to compare against EX/MEM.RegisterRd and MEM/WB.RegisterRd. Control (WB/M/EX groups from §2.7) rides above; register numbers ride below; data rides in the middle. Three lanes, one instruction per stage.

Slide 68's aside: lw → sw (memory-to-memory copy)

lw  $2, 20($1)     # data ready: end of MEM (CC4)
sw  $2, 15($3)     # data needed: in MEM (CC5) — as the store data!

Ask the slide's two questions. When is lw's data ready? End of its MEM, CC4 (then sitting in MEM/WB during CC5). When does sw need $2? Not in EX (there it only computes the address from $3) — it needs the store data in its MEM stage, CC5. Ready end-of-4, needed in 5: forwardable, zero stalls — with a forwarding path from MEM/WB to the data-memory write port. A load followed immediately by a dependent store costs nothing. (Contrast next section, where the consumer needs the value in EX.)

The Deep Pattern

Forwarding legality never depends on instruction types — only on the cycle a value is produced vs. the cycle and place it is consumed. lw→ALU-use: too early, stall. lw→sw's data: just in time, forward. Learn to draw the two timelines and the answer computes itself.

§4.7 · Slides 69–71

Load-Use Hazard Detection

Part 2, slides 69–71

Forwarding's one unfixable case needs its own detector — and it must fire a stage earlier than the forwarding unit.

lw  $2, 20($1)
and $4, $2, $5     # needs $2 in EX — one cycle too soon
or  $8, $2, $6
add $9, $4, $2
slt $1, $6, $7

The and cannot be saved by wires (§1.8), so the pipeline must stall it for one cycle. Crucially, the check happens while the using instruction is still in ID — before it commits to EX — because once it's in EX it's too late to hold it back. The detector therefore compares the ID-stage instruction (in IF/ID) against the EX-stage instruction (in ID/EX):

The Condition (slide 71) — verbatim exam material
Load-use hazard when:
  ID/EX.MemRead and
    ((ID/EX.RegisterRt = IF/ID.RegisterRs) or
     (ID/EX.RegisterRt = IF/ID.RegisterRt))

If detected: stall and insert a bubble.

Decode each piece: ID/EX.MemRead asserted ⇔ the instruction now in EX is a load (only lw reads memory). A load's destination is its rt field — hence comparing ID/EX.RegisterRt against both source registers of the instruction in ID.

Edge Cases Worth Arguing About

(1) Why RegisterRt and not RegisterRd? Because in the EX stage the RegDst mux may not have committed yet in this formulation — and for a load, rt is the destination. MemRead=1 guarantees we're looking at a load, so rt is exactly right.
(2) Strictly, this condition slightly over-stalls: if the ID instruction is (say) sw whose rt is only needed at MEM, or doesn't truly use one of the matching registers, a stall fires anyway. The textbook accepts the rare unnecessary bubble to keep the detector simple — a correctness-vs-simplicity trade worth mentioning for bonus marks.
(3) The $zero guard is absent here; a load with destination $0 (pointless but legal) would trigger a phantom stall against an instruction reading $0. Harmless to correctness (only performance), which is why the slides omit it.

§4.7 · Slides 72–76

How to Stall: Anatomy of a Bubble

Part 2, slides 72–76

Detecting the hazard was the easy half. Now: how does hardware physically make an instruction wait?

Three simultaneous actions, all triggered by the detection unit (slides 73–74):

  • Zero the controls: force the control fields entering ID/EX to 0. The instruction slot moving into EX becomes a nop — EX, MEM, WB all do nothing (RegWrite=0, MemWrite=0: it can't touch state). This is the bubble.
  • Freeze IF/ID: don't let it update — the using instruction (the and) stays put and is decoded again next cycle.
  • Freeze the PC: don't let it update — the following instruction (the or) is fetched again next cycle.

This is why §2.7 noted the PC and IF/ID "write every cycle, unconditionally — until Part III": they now gain write-enable inputs, driven by the hazard detection unit.

Exam Traps

1. The bubble is created by zeroing controls, not by inserting an actual nop instruction opcode — the datapath values in ID/EX are garbage-but-harmless because no write-enable survives.
2. All three actions (zero ID/EX controls, freeze IF/ID, freeze PC) are needed. Forget the PC freeze and the or is skipped forever; forget the IF/ID freeze and the and is lost; forget the control-zeroing and the and executes twice — with stale data the first time.
3. After the stall, the and still needs forwarding (MEM/WB → ALU). Stall and forward are partners, not alternatives. "1-cycle stall allows MEM to read data for lw; can subsequently forward" — slide 74, verbatim.

EXAMIn slide 73's snapshot the detection cycle shows: ID/EX.MemRead asserted, ID/EX.rt = IF/ID.rs = $2. Identify which instruction is where, and state the three control actions taken this cycle.▼

Next cycle the lw is in MEM fetching the data; the cycle after, forwarding completes the rescue.

§4.7 · Reference

Every forwarding and stalling question in existence reduces to two timestamps: when a value is produced, and when it is needed. Learn these two tables and the rest is arithmetic.

The two arrows mark the exam gold. sw's rt is needed a stage later than everyone else's operands — it's the most patient consumer in the ISA. And an ID-resolved branch needs its operands a stage earlier than anyone — the most impatient consumer. (bne is identical to beq in every timing respect; it just inverts the Zero test.)

Read the sw Rows Twice

Same producer (lw), same consumer instruction (sw) — opposite verdicts, purely because sw $2,0($3) (dependency on rt, the data) and sw $4,0($2) (dependency on rs, the base) consume $2 at different stages. An exam question that swaps which operand of the store depends on the load is testing whether you know Table 2, not just Table 1.

The Compressed Version to Carry Into the Exam

Producers: R-type delivers at end-of-EX; lw delivers at end-of-MEM; sw/branches deliver nothing.
Consumers: everything is needed at start-of-EX, except sw's store data (MEM, later — forgiving) and ID-resolved branch operands (ID, earlier — demanding).
Method: write the two timestamps, compare. Ready ≤ needed → forward, count 0. Ready > needed → stall until it isn't, count the bubbles.

EXAMlw $5, 0($9); bne $5, $zero, L — on the improved (ID-resolution) datapath, how many stalls? What single change (compiler-side, not hardware-side) removes them?▼

lw→ID-resolved-branch is the worst pairing in Table 3: ready end-of-MEM (CCn+1), needed start-of-ID (CCn) — that's needed before the producer even reaches EX. 2 stalls are required no matter how forwarding is arranged, because ID happens before MEM produces anything to forward. The compiler-side fix (echoing §1.9's code-scheduling idea): insert an independent instruction between the lw and the bne. With one instruction between them, the bne's ID moves out from under the lw's EX/MEM window enough that a MEM/WB→ID forward (if the hardware provides one) or the natural register-file timing can supply $5 in time — the stall count drops with distance, exactly like every other hazard in Table 3.

The Trap List — Ten Ways to Lose Marks

Collected from every section above
  1. Claiming pipelining reduces instruction latency (it raises throughput).
  2. Computing the pipelined period as total/stages instead of max(stage).
  3. Forgetting the +4 fill cycles when counting total cycles.
  4. Believing forwarding removes all stalls (load-use survives).
  5. Stalling a load-use pair that has an instruction between it (it doesn't stall).
  6. Skipping the delay-slot instruction when tracing a taken branch.
  7. Dropping the RegWrite / $zero guards from forwarding conditions.
  8. Writing the double-hazard fix with only the register-equality inside the not-clause.
  9. Comparing ID/EX.RegisterRd (instead of Rt) in the load-use detector.
  10. Reading any needed value "live" from an earlier stage instead of carrying it in pipeline registers (the §2.6 bug, in all its disguises).

Answer Notes

1. max=240, +10 overhead = 250. 2. Only the adjacent add stalls once; the or sits at distance 2, served by MEM/WB forwarding. 3. Both frozen — that's what "repeat ID / repeat IF" means. 4. add is 3 after sub: $2 was written to the register file in the first half of the very cycle add reads it — no forwarding needed, 00/00. The bait answers assume the hazard window is longer than it is. 5. WB signals ride until MEM/WB, the last register before they act.
