Lecture 2 · Orientation

Structural Design Patterns

Welcome back. In Lecture 1 we asked "how do we create objects well?" — that gave us the Creational family. Today we ask a different question: once objects exist, how do we assemble them into larger structures without the design collapsing under its own weight?

👨‍🏫 Professor's framing

Your slides give the one-line definition, and it is worth memorising verbatim: Structural patterns explain how to assemble objects and classes into larger structures, while keeping this structure flexible and efficient.

Notice the two promises hidden in that sentence — flexible (easy to extend/recombine) and efficient (no combinatorial blow-up). Every pattern today is a different answer to "how do I get both at once?"

Where we are in the course

Done

Creational

Singleton, Factory, Abstract Factory, Builder — who makes the object.

You are here

Structural

Decorator, Composite, Adapter, Bridge — how objects compose.

Later

Behavioral

Strategy, Observer, State… — how objects talk & decide.

The one idea that unifies all four

If you remember nothing else, remember this: favour object composition over class inheritance. Every pattern today replaces a rigid inheritance tree with objects that hold references to (and delegate to) other objects.

Pattern 1 · Wrapping

Decorator ☕

The Starbuzz Coffee saga. A beverage plus any combination of condiments — steamed milk, soy, mocha, whip — and the bill has to be right every time. This is the pattern that teaches you to stop subclassing and start wrapping.

Act 1 — The naïve tree explodes

Starbuzz sells beverages. Then they add condiments: Steamed milkSoyMochaWhip. A customer may take some, all, or none. First instinct: make a subclass for every combination.

Act 2 — Booleans in the superclass (a tempting trap)

Second instinct from the slides: push boolean flags hasMilk, hasSoy, hasMocha, hasWhip up into Beverage, and let the superclass cost() add condiment prices.

The Boolean design — looks clever, ages badlypublic abstract class Beverage {
    boolean milk, soy, mocha, whip;         // condiment flags

    public double cost() {                    // superclass does the maths
        double c = 0;
        if (milk)  c += 0.10;
        if (soy)   c += 0.15;
        if (mocha) c += 0.20;
        if (whip)  c += 0.10;
        return c;                             // subclass adds base drink cost on top
    }
}
⚠ Why the Boolean design is a design smell (straight from the slide)

1️⃣ New condiments break the superclass. Adding "caramel" means editing Beverage — violates Open/Closed.

2️⃣ Inappropriate inheritance. An iced tea still inherits hasWhip/hasMocha even though those make no sense for it. (BAD)

3️⃣ No multiplicity. A boolean can't express double mocha. You'd need counters, and now the superclass is a mess.

👨‍🏫 Connect it to SOLID (they love this in vivas)

The Boolean trap is a textbook Open/Closed Principle violation — you must modify existing code to extend behaviour. Decorator's whole selling point is: extend by adding new classes, touch nothing old.

Act 3 — "Let's do it like decoration"

The insight: start with a beverage and wrap it with condiments. For a Dark Roast with double Mocha and Whip, we build an onion — each layer is an object that wraps the one inside and adds its own cost.

The design (UML)

★ Exam gold — the "double inheritance/composition" line

A decorator has the same supertype as the object it decorates (inheritance — for type compatibility) and holds a reference to it (composition — for behaviour). Examiners want both halves. "Decorator subclasses the component only to match its type, not to inherit its behaviour." Write that sentence and you bank the marks.

The code

Component + Decorator (the two abstract classes)public abstract class Beverage {
    String description = "Unknown Beverage";
    public String getDescription() { return description; }
    public abstract double cost();            // concrete drinks must define
}

// Decorator shares the supertype so it "is a" Beverage…
public abstract class CondimentDecorator extends Beverage {
    Beverage beverage;                            // …and "has a" Beverage (the wrapped one)
    public abstract String getDescription();     // force re-describe
}
Concrete component + concrete decoratorpublic class DarkRoast extends Beverage {
    public DarkRoast() { description = "Dark Roast Coffee"; }
    public double cost() { return 2.99; }
}

public class Mocha extends CondimentDecorator {
    public Mocha(Beverage beverage) { this.beverage = beverage; }

    public String getDescription() {
        return beverage.getDescription() + ", Mocha";   // delegate + append
    }
    public double cost() {
        return 0.20 + beverage.cost();               // add own price, then recurse inward
    }
}
Test drive — the "onion" is built at run-timeBeverage b = new DarkRoast();       // $2.99
b = new Mocha(b);                 // wrap: +0.20
b = new Mocha(b);                 // wrap again (double mocha!): +0.20
b = new Whip(b);                  // wrap: +0.10

System.out.println(b.getDescription() + " $" + b.cost());
// → Dark Roast Coffee, Mocha, Mocha, Whip $3.49

Definition & consequences

📖 GoF / Head First definition

The Decorator pattern attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality. (Your slide's phrasing: "…by placing these objects inside special wrapper objects that contain the behaviours.")

Wins

Add/stack responsibilities at run-time · honours Open/Closed · supports multiplicity (double mocha) · avoids class explosion.

Costs

Many small classes · lots of wrapping code · hard to debug deeply nested wrappers · code that checks the concrete type breaks (it only sees the outermost wrapper).

⚠ Edge cases the exam pokes at

Type-checking pitfall: if (bev instanceof DarkRoast) fails after wrapping — the object is now a Whip. Decorator changes the skin, not the type you can detect.

Order matters for behaviour, not for cost: Whip(Mocha(x)) vs Mocha(Whip(x)) give the same price but a different description string — useful when wrappers transform I/O (e.g., Encrypt(Compress(stream)) ≠ Compress(Encrypt(stream))).

Real-world sighting: java.io — new BufferedReader(new InputStreamReader(System.in)) is Decorator in the JDK. Great "name a real example" answer.

Checkpoint · Decorator
A student wraps a drink as new Whip(new Mocha(new DarkRoast())) and then writes if (drink instanceof DarkRoast) applyLoyaltyDiscount();. What happens?
Correct: the discount never fires. Once wrapped, the outermost object is a Whip. Decorator deliberately hides the concrete component behind uniform supertype calls — so any logic that depends on detecting the concrete type is a classic Decorator anti-pattern. Program to the Beverage interface instead.
Pattern 2 · Trees

Composite 🌳

The Pancake House merges with the Diner, and now the menu is a menu-of-menus: breakfast items, a dessert sub-menu inside the lunch menu, and so on. You want to print the whole thing — or just desserts — with the same code. That's Composite.

The problem — "something tree-like"

From the slides, the requirements are:

  • Tree-structured menus with support for sub-menus and items.
  • Traversal should be flexible — iterate over one sub-menu (e.g. desserts) or the entire hierarchy.

The pain without Composite: the client must constantly ask "is this a single MenuItem or a whole Menu?" and branch — if (x is Menu) loopThroughChildren(); else printItem();. That conditional metastasises everywhere.

💭 Brainstorm — where have you already used this?

File systems (a folder contains files and folders), the HTML DOM (a <div> contains text nodes and more elements), org charts, GUI containers holding widgets and sub-panels. Any time "a whole" and "a part" should respond to the same commands, Composite is lurking.

Nodes and leaves

The design (UML)

The code

The uniform component — leaves & composites share itpublic abstract class MenuComponent {
    // Default: not supported. Leaves override the "part" ops,
    // composites override the "child-management" ops.
    public void add(MenuComponent c)    { throw new UnsupportedOperationException(); }
    public void remove(MenuComponent c) { throw new UnsupportedOperationException(); }
    public MenuComponent getChild(int i) { throw new UnsupportedOperationException(); }
    public void print() { throw new UnsupportedOperationException(); }
}
Leaf vs Compositepublic class MenuItem extends MenuComponent {
    String name; double price;
    public MenuItem(String n, double p){ name=n; price=p; }
    public void print() { System.out.println("  " + name + "  $" + price); }
}

public class Menu extends MenuComponent {
    List<MenuComponent> children = new ArrayList<>();   // ◆ holds the same type
    String name;
    public Menu(String n){ name=n; }
    public void add(MenuComponent c){ children.add(c); }
    public void print() {
        System.out.println("== " + name + " ==");
        for (MenuComponent c : children) c.print();       // recurse — leaf or menu, same call
    }
}
Client treats a whole tree exactly like one itemMenu all = new Menu("ALL MENUS");
Menu dessert = new Menu("DESSERTS");
dessert.add(new MenuItem("Cheesecake", 3.99));
all.add(new MenuItem("Pancakes", 2.99));
all.add(dessert);          // a Menu inside a Menu — no special case

all.print();               // prints the entire hierarchy…
dessert.print();           // …or just one sub-menu. Same method.
★ Exam gold — the "uniformity vs safety" trade-off

Putting add()/remove() in the abstract component is transparency (client treats all nodes identically) but sacrifices type-safety (you can call add() on a leaf → runtime exception). The alternative — put child-ops only on Menu — is safe but not transparent (client must know the type). GoF favours transparency. Name this trade-off and you look like you actually read the book.

📖 Definition

Composite lets you compose objects into tree structures and then work with these structures as if they were individual objects. The keyword the grader hunts for is "tree" plus "treat individual objects and compositions uniformly."

⚠ Edge cases

Leaf calling composite ops: calling add() on a MenuItem throws — by design. Some implementations return a no-op or an empty list instead; know which your course expects.

Cycles & parent pointers: a naïve tree assumes no cycles. If children need to reach parents (for "remove me"), you add a parent pointer — but then you must guard against a node being added to two parents.

Composite ≠ Decorator even though both hold a same-type reference: Decorator holds exactly one wrapped object to add behaviour; Composite holds a list of children to build a tree. (More on this in Compare & Confuse.)

Checkpoint · Composite
Why does Menu.print() not need to know whether each child is a MenuItem or another Menu?
Correct — it's pure polymorphism. The client calls print() on the abstract type. A leaf prints itself; a composite prints its header then loops and calls print() on each child (which may recurse). No type-checking, no branching — that uniform treatment is the pattern.
Pattern 3 · Translation

Adapter 🦆

Your code speaks "Duck". A vendor ships you a "Turkey". Both are birds, both fly — but the method names don't line up and you can't touch the vendor's code. An Adapter is the travel-plug of software: it makes an incompatible thing fit a socket it was never built for.

Adapters in real life → in OO

The slide opens with the physical analogy: a European plug won't fit a US socket, so you slot in an adapter. It doesn't change the plug or the wall — it sits between them and translates. In OO, the "shapes" are interfaces.

The problem — Duck vs Turkey

Existing code uses the Duck interface. A vendor gives you Turkey. They're close but incompatible:

Duck (what the client expects)

interface Duck {
  void quack();
  void fly();   // long flights
}

Turkey (the vendor's "adaptee")

interface Turkey {
  void gobble();  // not "quack"
  void fly();     // only short hops
}

The question from the slide: "Current code uses the Duck interface — how do we incorporate Turkey?" We can't rename the vendor's methods, and we don't want to rewrite the client. So we insert a translator.

The solution — a TurkeyAdapter that "is a" Duck

The adapter — translation happens herepublic class TurkeyAdapter implements Duck {   // IS-A Duck (the target)
    Turkey turkey;                                // HAS-A Turkey (the adaptee)
    public TurkeyAdapter(Turkey t) { this.turkey = t; }

    public void quack() { turkey.gobble(); }         // map quack → gobble

    public void fly() {
        for (int i = 0; i < 5; i++) turkey.fly();  // 5 short hops ≈ 1 duck flight
    }
}
Test drive — "getting a Turkey using existing Duck code"Turkey turkey = new WildTurkey();
Duck  adapted = new TurkeyAdapter(turkey);

testDuck(adapted);   // client method that only knows how to test a Duck — works!

Two flavours: Object Adapter vs Class Adapter

Object Adapter

Composition

Adapter implements the target interface and wraps (holds) the adaptee. Delegates each call.

  • ✅ Works in any OO language
  • ✅ Can adapt an adaptee and all its subclasses
  • ✅ Loose coupling
Class Adapter

Multiple inheritance

Adapter inherits from both Target and Adaptee at once — no wrapping object.

  • ⚠ Needs multiple inheritance → C++ only, not Java
  • ✅ Can override adaptee behaviour
  • ❌ Binds to one concrete adaptee class
⚠ The diamond problem connection (they WILL ask)

Why is the Class Adapter "C++ only"? Because it needs a class to inherit from two classes, and Java forbids multiple class inheritance to dodge the diamond problem (ambiguous inherited members). Java allows multiple interface inheritance, which is why we implement Duck (interface) but compose the Turkey. This ties straight back to your Lecture-1 diamond discussion.

📖 Definition

Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces. Grader's keyword: "convert an existing interface" — Adapter changes nothing about behaviour, only the shape of the interface.

★ Exam gold — Adapter vs Decorator vs Facade

All three "wrap." Distinguish by intent: Adapter changes the interface (same behaviour, new shape). Decorator keeps the interface, adds behaviour. Facade simplifies a whole subsystem behind one new interface. If the question says "incompatible," "legacy," "vendor," or "third-party" → almost always Adapter.

Checkpoint · Adapter
You're integrating a legacy OldPrinter (method printDocument()) into new code that expects Printer.print(). You can't modify OldPrinter, and you're in Java. Which is correct?
Object Adapter is right. In Java you can't multiply-inherit two classes, so the class-adapter route is out. Object adapter (implement the target interface, compose the adaptee, delegate) is the idiomatic Java choice. It's not Decorator — you're converting an interface, not adding behaviour to the same interface.
Pattern 4 · Decoupling

Bridge 🔵🟥

Two shapes, two colours, and suddenly four classes: RedCircle, BlueCircle, RedSquare, BlueSquare. Add green and a triangle and you're drowning. Bridge is the pattern that says: when a thing varies along two independent axes, give each axis its own hierarchy and connect them with a reference.

The problem — Colored Shapes multiply

Straight from the slides:

  • You have two shapes: Circle and Square.
  • You want colours: Red and Blue.
  • You create four combinations: BlueCircle, RedSquare…
  • New colour (green) or shape (triangle)? The hierarchy grows exponentially.
  • Why? Because things extend in two independent dimensions.

From inheritance to composition

The fix from the slides: two independent dimensions — form and colour. Move from inheritance to composition. A Shape delegates colour-related work to a Color object it holds.

📖 The GoF vocabulary (memorise these two words)

GoF names the two hierarchies Abstraction and Implementation:

  • Abstraction — the high-level control layer (also called the interface). It does no real work itself; it delegates.
  • Implementation — the layer that does the actual work (also called the platform). Interchangeable.

The slide's real example: Abstraction = the GUI (regular customer view, admin view); Implementation = the OS APIs for Linux / Windows / macOS. One GUI, swappable platform underneath — the same appearance runs on any OS.

The design (UML) & code

Implementation hierarchy (the "platform")public interface Color { String applyColor(); }
public class Red  implements Color { public String applyColor(){ return "red"; } }
public class Blue implements Color { public String applyColor(){ return "blue"; } }
Abstraction hierarchy holds the bridgepublic abstract class Shape {
    protected Color color;                 // ◆ the bridge — a reference, not inheritance
    public Shape(Color color){ this.color = color; }
    public abstract String draw();
}
public class Circle extends Shape {
    public Circle(Color c){ super(c); }
    public String draw(){ return "Circle in " + color.applyColor(); }  // delegate!
}
Mix & match at run-time — no combinatorial classesShape a = new Circle(new Red());    // "Circle in red"
Shape b = new Square(new Blue());   // "Square in blue"
// Add Green → 1 new class. Add Triangle → 1 new class. Never N×M.
📖 Definition

Bridge lets you split a large class or a set of closely related classes into two separate hierarchies — abstraction and implementation — which can be developed independently of each other.

⚠ Edge cases & the #1 confusion

Bridge vs Strategy look identical in code (both hold an interface and delegate). Difference is intent & scale: Strategy swaps one algorithm; Bridge decouples a whole abstraction hierarchy from a whole implementation hierarchy. Bridge is "structural & big-picture"; Strategy is "behavioural & one-method."

Bridge is designed up-front; Adapter is usually retro-fitted onto existing incompatible code. If the question emphasises "planned so the two axes evolve independently" → Bridge. If it emphasises "make this existing/legacy thing fit" → Adapter.

Abstraction does no real work — if your "abstraction" starts implementing the actual logic instead of delegating, you've lost the pattern.

★ Exam trigger phrases → Bridge

"two independent dimensions", "grows exponentially / N×M classes", "abstraction and implementation should vary independently", "same GUI across different OS/platforms", "form and colour". See any of these → write Bridge.

Checkpoint · Bridge
A messaging app must support {SMS, Email, Push} × {Urgent, Normal, Low-priority} formatting, and management expects to keep adding both channels and priority styles. Best structural choice?
Bridge. Two independent axes that both keep growing is the textbook trigger. Nine classes today becomes 4×4=16 tomorrow — exponential. Bridge keeps it additive: a new channel is +1 class, a new priority style is +1 class. Decorator is for stacking optional add-ons on one axis, not decoupling two axes.

Compare & Confuse ⚖️

Three of today's four patterns share nearly identical UML — an object holding a reference to a related object. The exam separates the "A" students by intent. Here's your disambiguation cheat-sheet.

The four classic mix-ups

Decorator vs Composite

Same supertype-reference shape. But Decorator wraps exactly one child to add behaviour; Composite holds a list of children to form a tree. "One-to-add" vs "many-to-nest."

Adapter vs Decorator

Both wrap. Adapter changes the interface (behaviour unchanged); Decorator keeps the interface (behaviour enhanced). "Translate" vs "augment."

Bridge vs Adapter

Bridge is designed up-front to let two axes evolve; Adapter is retro-fitted to reconcile things that already exist and clash. "Plan" vs "patch."

Bridge vs Strategy

Identical code, different scope. Strategy swaps one algorithm (behavioural); Bridge decouples whole abstraction & implementation hierarchies (structural). "One method" vs "two towers."

💭 A 10-second decision tree for the exam

1. Are two things with clashing interfaces already built? → Adapter.
2. Is it a part-whole tree? → Composite.
3. Am I stacking optional features on one thing? → Decorator.
4. Are there two independent dimensions exploding into N×M? → Bridge.

👨‍🏫 Professor's meta-tip

When a scenario question gives no pattern name, underline the verbs and pain-points: "incompatible/legacy" (Adapter), "tree/submenu" (Composite), "optional/stack/at runtime" (Decorator), "two axes/exponential/platform" (Bridge). The graders write these scenarios around those trigger words — train your eye to spot them.

Scenario drill — name the pattern (no names given)

These mimic the "identify from context" style. Decide before you reveal.

Drill 1
A photo-editing library must apply optional filters — blur, sepia, sharpen — in any combination and any order, decided while the user clicks. Adding a "vignette" filter later must not touch existing filter code.
Decorator. Optional, stackable, any-order, chosen at runtime, extensible without editing old code — every signal points to wrapping. Each filter wraps the image and adds its effect.
Drill 2
A drawing app renders shapes to multiple rendering backends (OpenGL, DirectX, SVG). The team wants to add new shapes and new backends independently without a class for every shape-backend pair.
Bridge. Two independent axes (shape × backend), "vary independently," avoiding N×M — this is the platform/OS story from the slides in disguise. Shapes = abstraction, renderers = implementation.
Drill 3
Your app expects a PaymentProcessor.pay(amount) interface. A newly-acquired company's billing SDK only exposes chargeCustomer(cents, currency). You cannot alter the SDK.
Adapter. "Cannot alter", "newly-acquired/third-party SDK", "interface doesn't line up" — reconcile incompatible interfaces without changing either side. The adapter maps pay(amount) → chargeCustomer(...).
Drill 4
A project-management tool models tasks and task-groups. A group contains tasks or other groups, and "mark complete" / "estimate hours" must work the same whether called on a single task or a whole group.
Composite. Part-whole tree, groups-within-groups, uniform operations on leaf and node — the menu example wearing a project-management costume.
Drill 5 · the tricky one
Two patterns produce almost the same UML: an object holding a reference to another object of a related type, delegating work to it. Which pair is this, and what tells them apart?
Bridge & Strategy. Their code is nearly identical, so intent decides: Strategy is behavioural and swaps a single algorithm; Bridge is structural and decouples an abstraction hierarchy from an implementation hierarchy. This exact "same shape, different intent" trap is a favourite discriminator question.
