Change how the code is built, not what it does.

Refactoring restructures a system so its external behavior stays identical while its internal structure gets better. Think of tidying a workshop: the same jobs get done, but now you can find the tools.

The two meanings (Fowler)

Refactoring (noun): a change to the internal structure of software that makes it easier to understand and cheaper to modify, without changing its observable behavior.

Refactoring (verb): restructuring software by applying a series of refactorings, again without changing observable behavior.

Notice the word "series". A refactoring is a small, named step. A big rewrite is not a refactoring.

Edge cases: is it refactoring?
  • Renaming a confusing variable: yes.
  • Fixing a bug: no, behavior changes (a bug fix is a behavior change on purpose).
  • Adding a feature: no. Fowler's advice is to wear "two hats" and never wear both at once.
  • Rewriting a module from scratch: no. It isn't a series of small, behavior-preserving steps.
  • Timing changes: "observable behavior" means what callers and requirements can see. Speed differences are normally tolerated, hard real-time code excepted.
Brainstorm: you shortened a method, then a test fails. Was it a refactoring?

No. By definition a refactoring preserves behavior, so a failing test means you changed behavior. Either you introduced a bug, or the test was coupled to internals it shouldn't know about. Check which, but in the first case undo and retry with a smaller step.

Refactoring is dangerous... and useful

It can introduce bugs, and a manager sees "cleaning code" as time not spent on features. The answer is to make refactoring systematic, incremental, and safe.

How to make it safe

  • Use named refactoring patterns. Fowler names refactorings like the Gang of Four named design patterns, so each one has known steps and pitfalls.
  • Test constantly. Write tests first (agile style), refactor in a tiny step, run the tests. A failure points at the step you just took.

Why refactor

  • Design decays as changes pile up. Refactoring pushes back.
  • Easier to understand: better structure, less duplication.
  • Finds bugs: you must understand the code deeply to restructure it.
  • Faster programming later, because a good design enables progress.

When to refactor

  • Rule of Three: the first time you do something, just do it. The second time you wince and duplicate. The third time, refactor.
  • When adding functionality: before (to make the new function easy to add) or after (to clean up).
  • When fixing a bug and when doing a code review.

Problems with refactoring

Databases

Business apps are tightly coupled to their schema. Code is easy to change, databases are not (data migration, other systems reading the tables).

Changing interfaces

If you own every caller, change freely. If the interface is published to code you can't edit, you can't just change it.

Edge case: what to do with a published interface

Keep the old method as a thin delegate to the new one and mark it deprecated. That is the same idea as the "optional delegation" in Move Method later on.

The cookbook

Martin Fowler's book Refactoring: Improving the Design of Existing Code is a catalog of refactoring patterns. Online: refactoring.com/catalog and sourcemaking.com/refactoring.

Brainstorm: how would you persuade a manager whose schedule is slipping?

Frame it as reducing the cost of the next change. Refactor right before adding a feature (so the feature is faster), do it in small tested steps (so risk is low), and use the Rule of Three so you only pay when duplication has proven itself.

Where do I start? Follow the smell.

A "bad smell" is a symptom in code that suggests a refactoring is due. It isn't a bug; the code runs. It is a hint that the design will hurt later. Tools such as Codegrip, Checkstyle, PMD, FindBugs, and SonarQube detect many smells automatically.

Exam prep

One-page cheat sheet

Mix-ups that cost marks

  • Divergent Change vs Shotgun Surgery: one class many reasons, versus one reason many classes.
  • Data Class vs Lazy Class: a Data Class has fields plus getters and setters but its logic lives elsewhere. A Lazy Class doesn't do enough to justify existing. Not every Data Class is bad; it is a problem when it should have behavior but doesn't, or when the behavior is scattered.
  • Feature Envy vs Data Class: they often come as a pair. The envious method sits in class A and wants data from class B, and B is the data class. Move Method fixes both.
  • Extract Variable vs Replace Temp with Query: a variable names a value inside one method. A query method makes that value reusable across methods.
  • Refactoring vs optimization: both preserve behavior, but refactoring aims at clarity, optimization at speed.
  • Comments: only comments that cover for bad code are the smell. Comments that explain why are fine.
