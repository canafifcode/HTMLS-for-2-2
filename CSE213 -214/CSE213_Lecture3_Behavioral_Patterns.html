Welcome back to class

Behavioral Design Patterns

Creational patterns answered "how are objects born?" — behavioral patterns answer "how do objects talk, delegate, and share responsibility?"

Behavioral patterns deal with how objects behave and interact — defining communication, responsibility flow, and how tasks are carried out between objects. They are concerned with algorithms and the assignment of responsibilities between objects. — Lecture 3, slides 2–3

The mental model

Think of a software system as an office. Creational patterns are the HR department — they decide how employees (objects) are hired. Behavioral patterns are the org chart and the meeting culture — who reports to whom, who notifies whom, who is allowed to talk to whom, and who can be swapped out of a role without disrupting the team.

Pattern 1 of 6 · Object behavioral

Strategy

"Define a family of algorithms, encapsulate each one, and make them interchangeable."

The SimUDuck disaster (slides 4–18)

We have a duck simulator. All ducks swim() and quack() the same way but display() differently — so classic inheritance: a Duck superclass, subclasses override display. Then a new requirement lands: ducks must fly. The "obvious" fix is adding fly() to the superclass. And at the project demo… the rubber duck starts flying.

Brainstorm — why did that happen? Inheritance pushed behavior down to every subclass whether it made sense or not. A local change to the superclass caused a non-local, unintended side effect. This is the classic danger of code reuse via inheritance.

Attempt #1 — override the ones that don't fly?

RubberDuck overrides fly() to do nothing. Then someone adds a wooden DecoyDuck which neither flies nor quacks — now we override two methods with empty bodies. Every new "exception duck" means more dead overrides. The slides call it plainly: bad design. And features change every six months.

Attempt #2 — interfaces (Flyable, Quackable)?

Pull fly() and quack() out into interfaces; only the ducks that fly implement Flyable. This fixes the rubber-duck bug but creates a worse one: interfaces carry no implementation. If 48 duck species implement Flyable and we need to tweak wingbeat rate, we change all 48 implementations. Zero code reuse.

Professor's Note — the principle behind the pattern The slide titled "Another Principle" is pointing at two of the most examinable design principles:
1. Encapsulate what varies — take the parts that change (fly/quack behavior) and separate them from what stays the same.
2. Favor composition over inheritance — a Duck HAS-A FlyBehavior instead of IS-A flyer.
A third one rides along: program to an interface, not an implementation.

The Strategy solution (slides 20–41)

Create two interfaces — FlyBehavior and QuackBehavior — each with a family of concrete implementations. The Duck holds references to behavior objects and delegates to them. Because the reference is a field, we can even swap behavior at runtime with a setter — the slides call this making behavior "DYNAMIC" (a model rocket-powered duck mid-simulation!).

Strategy: the Context (Duck) composes a behavior interface; concrete strategies are interchangeable.

Java implementation

// The strategy interfaces — the "family of algorithms"
public interface FlyBehavior { void fly(); }
public interface QuackBehavior { void quack(); }

public class FlyWithWings implements FlyBehavior {
    public void fly() { System.out.println("I'm flying!!"); }
}
public class FlyNoWay implements FlyBehavior {
    public void fly() { System.out.println("I can't fly"); }
}

// The Context
public abstract class Duck {
    protected FlyBehavior flyBehavior;      // composition!
    protected QuackBehavior quackBehavior;

    public void performFly()   { flyBehavior.fly(); }     // delegate
    public void performQuack() { quackBehavior.quack(); }

    // runtime swap — the "DYNAMIC" slide
    public void setFlyBehavior(FlyBehavior fb) { this.flyBehavior = fb; }
    public abstract void display();
}

// Client code
Duck model = new ModelDuck();          // starts with FlyNoWay
model.performFly();                       // "I can't fly"
model.setFlyBehavior(new FlyRocketPowered());
model.performFly();                       // rocket-powered, at runtime!

Second slide example: the map app

Your deck's "yet another example": a navigation app computing a route between two points. Driving, walking, cycling, public transport are each a RouteStrategy; tapping a mode swaps the strategy object in real time. The Navigator class never changes when a new mode (say, scooter routing) is added — that's the Open/Closed Principle in action.

Edge Cases & Gotchas • Null strategy: if the context's behavior field is never set, delegation throws NullPointerException. Fix: set a sensible default in the constructor, or use a Null-Object strategy (FlyNoWay is effectively one!).
• Client must know the strategies: whoever calls setFlyBehavior() must be aware of concrete strategy classes — that awareness has to live somewhere.
• Class explosion: two independent behavior axes handled with inheritance alone would need m × n subclasses; Strategy needs only m + n strategy classes. Great quantitative point for a "justify your design" question.
• Overkill alarm: if an algorithm never varies, Strategy adds indirection for nothing. Patterns are cures, not vitamins.
Exam Tips • Memorize the definition verbatim — it's on slide 45 and it's short: "Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from the clients that use it."
• Trigger phrases in scenario questions: "different ways of doing the same task", "switch algorithm at runtime", "payment methods / sorting methods / routing modes", "avoid conditionals selecting behavior".
• Be ready to draw the SimUDuck UML from memory and to narrate the two failed attempts first — the marks are in the design justification, exactly like your FoodFlow assignment.
Pattern 2 of 6 · Class behavioral

Template Method

"Same skeleton, different flesh." The only pattern today built on inheritance rather than composition — remember that, it's an exam favorite.

The Coffee & Tea shop (slides 50–71)

Look at the two recipes side by side:

CoffeeTeaVerdict
Boil waterBoil waterExactly same
Brew coffee grindsSteep tea bagVaries (both are "brewing")
Pour into cupPour into cupExactly same
Add sugar & milkAdd lemonVaries (both are "condiments")

A naive abstraction keeps only the literally-identical methods (boilWater, pourInCup) in the superclass and lets each subclass write its own prepareRecipe(). But wait — the slides ask: "Don't they have the same skeleton?" Both recipes are really: boil → brew → pour → addCondiments. The algorithm's structure is the invariant; only two steps differ.

Template Method defines the skeleton of an algorithm in the superclass but lets subclasses override specific steps of the algorithm without changing its structure. — Slide 73

Java implementation — with the two exam-critical keywords

public abstract class CaffeineBeverage {

    // THE template method — declared final so no subclass can
    // rearrange the algorithm's skeleton (slide 74: "It is final method")
    public final void prepareRecipe() {
        boilWater();
        brew();                       // abstract — subclass must supply
        pourInCup();
        if (customerWantsCondiments()) // hook controls a step
            addCondiments();          // abstract — subclass must supply
    }

    abstract void brew();
    abstract void addCondiments();

    void boilWater()  { System.out.println("Boiling water"); }
    void pourInCup()  { System.out.println("Pouring into cup"); }

    // HOOK: default implementation, subclasses MAY override
    boolean customerWantsCondiments() { return true; }
}

public class Tea extends CaffeineBeverage {
    void brew()          { System.out.println("Steeping the tea"); }
    void addCondiments() { System.out.println("Adding lemon"); }
}
Professor's Note — anatomy of the superclass Four kinds of methods can live in a template class:
1. The template method itself — final, calls the steps in fixed order.
2. Concrete steps — identical for everyone (boilWater).
3. Abstract steps — subclasses must implement (brew).
4. Hooks — have a default body, subclasses may override to plug into or steer the algorithm (the if-else conditional-execution slide, #72). "Must vs may" is exactly the abstract-vs-hook distinction — a classic short question.

Second slide example: Data Mining (slides 75–77)

An app mines corporate documents in three formats — DOC, CSV, PDF. Opening, extracting-raw-data and closing differ per format, but analyzing and reporting are identical. The slides note "only these vary": the template method mine(path) fixes the pipeline openFile → extractData → parseData → analyzeData → sendReport → closeFile, and format subclasses override only the file-specific steps. Duplicate analysis code across three classes collapses into the base class.

Brainstorm — the Hollywood Principle Template Method embodies "Don't call us, we'll call you." The high-level superclass calls down into subclass steps; subclasses never call the algorithm upward. Where else have you seen frameworks calling your code? JUnit's setUp()/tearDown(), Android's onCreate(), servlet doGet() — all Template Method hooks in the wild. Dropping one such real-world sighting into an exam answer signals depth.
Edge Cases & Gotchas • Forgetting final lets a subclass override the template and destroy the skeleton — the whole point evaporates.
• LSP tension: a subclass could implement a step in a way that violates what the skeleton assumes (your Square/Rectangle radar should tingle here).
• Too many abstract steps = every subclass becomes tedious to write; keep the mandatory set minimal, prefer hooks.
• It's static: behavior is fixed at compile time by which subclass you instantiated. You cannot switch from Tea to Coffee mid-object — that's Strategy's superpower, not this one's.
Exam Tips Trigger phrases: "steps of a process", "same procedure with some steps differing", "skeleton", "override specific steps", "invariant order". If a scenario reads like a fixed pipeline or recipe with pluggable stages → Template Method. If the whole algorithm is swappable as a unit → Strategy.
Pattern 3 of 6 · Object behavioral

Observer

Publishers + Subscribers = the newspaper of object-oriented design.

Weather-o-Rama (slides 82–94)

Contract: a physical weather station acquires temperature/humidity/pressure; a WeatherData object receives it and must update three displays — current conditions, statistics, forecast. Crucially: change triggers it (new measurements arrive → displays refresh) and displays must be addable/removable later (expandability!).

The misguided implementation

public void measurementsChanged() {
    float temp = getTemperature();
    float humidity = getHumidity();
    float pressure = getPressure();
    // hard-coded, concrete display calls:
    currentDisplay.update(temp, humidity, pressure);
    statisticsDisplay.update(temp, humidity, pressure);
    forecastDisplay.update(temp, humidity, pressure);   // add a 4th? EDIT THIS CODE.
}

Diagnosis, in principle-speak: we're coding to concrete implementations, the area that varies (the display list) is not encapsulated, and every new display forces modification of tested code (violating OCP).

The magazine-subscription analogy (slides 95–107)

A publisher prints magazines; you subscribe and issues arrive automatically; you unsubscribe and they stop; the publisher keeps publishing for everyone else. Swap names: Publisher = Subject, Subscriber = Observer (slide 123 states this equivalence explicitly — quote it in exams).

Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically. — Slide 121
Subject knows observers only through the Observer interface — loose coupling.

Java implementation (mirrors slides 112–120)

public class WeatherData implements Subject {
    private List<Observer> observers = new ArrayList<>();  // list of observers
    private float temperature, humidity, pressure;

    public void registerObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o)   { observers.remove(o); }
    public void notifyObservers() {
        for (Observer o : observers) o.update(temperature, humidity, pressure);
    }
    public void measurementsChanged() { notifyObservers(); }
}

public class CurrentConditionsDisplay implements Observer, DisplayElement {
    private Subject weatherData;

    // Subject passed in constructor (slide 118) …
    public CurrentConditionsDisplay(Subject weatherData) {
        this.weatherData = weatherData;
        weatherData.registerObserver(this);   // … how it registers ITSELF (slide 119)
    }
    public void update(float t, float h, float p) {
        this.temperature = t; this.humidity = h;
        display();                             // display() called (slide 120)
    }
}
Edge Cases & Gotchas • Push vs pull: here the Subject pushes all data into update(t,h,p). If observers need different subsets, pass the Subject reference instead and let observers pull via getters — more flexible, more calls.
• Notification order is not guaranteed — never write observers that depend on being told first.
• Lapsed-listener leak: observers that never unregister keep being referenced by the subject → memory leak. The remove path matters!
• A slow or throwing observer inside the notify loop stalls or breaks notification for the rest.
• Cascading updates (observer changes subject → re-notify) can cause infinite loops.
Exam Tips Trigger phrases: "notify automatically", "subscribers", "when X changes, Y and Z should refresh", "event listener", "news feed / stock ticker / weather displays". If the deck's expandability line appears — "displays can be added/removed" — it's screaming Observer + OCP. Also remember: the connection is one-way (subject → observers) and dynamic (subscribe/unsubscribe at runtime); those two adjectives come straight from your Mediator-vs-Observer slide.
Pattern 4 of 6 · Object behavioral

Mediator

Air traffic control for your objects: nobody talks to anybody — everybody talks to the tower.

The control tower (slides 129–130)

During landing, aircraft pilots never talk to each other directly — all communication goes through the control tower. Without it, every pilot would need to be aware of every other aircraft, and "airplane crash statistics would probably skyrocket." With n planes, direct communication means up to n(n−1)/2 channels; the tower reduces it to n. That formula is worth writing in an exam.

The customer-profile dialog (slides 131–150)

A dialog for creating/editing customer profiles has text fields, checkboxes, buttons. They interact: selecting "Business" enables the company-name field; "Apply" validates everything. The naive approach puts interaction logic inside the elements themselves — the checkbox class contains Logic-1 for the button and Logic-2 for the text field.

Brainstorm — why is that fatal? Ask the slides' question: can we reuse the checkbox class in another form? NO — it's hard-wired to 1 button, 1 textfield, 1 dialog. That is coupling. A generic widget class has become a single-use widget.

Solution: ① cease all direct communication between components; ② they collaborate only through a mediator that redirects calls to appropriate components. Here, the Dialog class is the mediator. The Dialog already knows its sub-elements (no new dependency!). Previously the Apply button had to know every element; now Apply merely notifies the mediator, which runs the validation across elements it owns. The button keeps a reference to its mediator so it knows whom it is notifying.

Components depend on one mediator instead of being coupled to dozens of colleagues (slide 144, verbatim idea).

Java sketch

public interface Mediator { void notify(Component sender, String event); }

public abstract class Component {
    protected Mediator mediator;                // the ONLY dependency
    public Component(Mediator m) { this.mediator = m; }
}

public class Checkbox extends Component {
    public void check() { mediator.notify(this, "check"); }  // no widget-to-widget calls
}

public class ProfileDialog implements Mediator {
    private Checkbox businessType; private TextField companyName; private Button apply;

    public void notify(Component sender, String event) {
        if (sender == businessType && event.equals("check"))
            companyName.setEnabled(businessType.isChecked());   // "Business" enables field
        else if (sender == apply && event.equals("click"))
            validateAll();                                      // Apply validates everything
    }
}
Edge Cases & Gotchas • The God-Object trap: as interactions grow, all the logic accumulates in the mediator; it can bloat into an unmaintainable monolith. This is the canonical drawback — always mention it.
• The mediator knowing its components is fine (a dialog already owns its widgets — "no new dependency"), but components must know only the mediator interface, else you've re-coupled.
• Testing wins: each widget can now be unit-tested with a mock mediator.
Exam Tips Trigger phrases: "objects communicate through a central hub", "reduce chaotic dependencies", "many-to-many interactions", "chat room", "air traffic control", "form elements affecting each other". Definition (slide 157): restricts direct communications between objects and forces them to collaborate only via a mediator, reducing chaotic dependencies. Pair it with the n(n−1)/2 → n coupling argument for full marks.
Pattern 5 of 6 · Object behavioral

Command

Turn a verb into a noun: the request itself becomes an object you can pass, queue, log — and undo.

The text editor (slides 168–178)

We're building an editor with a toolbar of buttons. They all look the same → one neat Button class. But they do different things → subclass Button for every operation? Two disasters follow:

① Enormous subclass count — CopyButton, PasteButton, SaveButton… and modifying the base Button class now risks breaking dozens of subclasses.
② The "ugliest part" — Save is reachable from the toolbar button, from Ctrl+S, and from File → Save. Either you duplicate the save code three times, or the menu and shortcut call the button's click handler — making business features depend on a GUI widget. The slides' verdict: "too ugly."

Separation of concerns (slides 179–188)

Split into a GUI layer (renders pictures, captures input) and a business-logic layer (calculation, data loading). The GUI delegates work down. But GUI objects shouldn't fire raw requests directly either — each operation lives in its own Command class implementing one common interface with a single execute() method. Parameters? Pre-configured inside the command — the command already knows what to do and to whom.

Command turns a request into a stand-alone object that contains all information about the request. This lets you parameterize methods with different requests, delay or queue a request's execution, and support undoable operations. — Slide 192 (note the margin gloss: "passing a request as an argument")
Invoker → Command → Receiver. "Commands know editor" (slide 190): each concrete command carries its receiver reference.

Java implementation with UNDO (slide 191's stack)

public interface Command { void execute(); }

public class SaveCommand implements Command {
    private Editor editor;                          // pre-configured receiver
    public SaveCommand(Editor e){ editor = e; }
    public void execute() { editor.saveToDisk(); }
}

// One command object — three invokers. Zero duplication.
Command save = new SaveCommand(editor);
toolbarSaveButton.setCommand(save);
shortcutMap.put("Ctrl+S", save);
fileMenu.item("Save").setCommand(save);

// UNDO — commands that change editor state push a backup on a stack;
// undo pops the state and restores it (slide 191)
public class CutCommand implements Command {
    public void execute() {
        history.push(editor.backup());     // snapshot BEFORE mutating
        editor.cutSelection();
    }
}
public void undo() { editor.restore(history.pop()); }
Professor's Note — the four consequences to recite From the definition, four exam-ready superpowers: (1) decouple invoker from receiver; (2) pass requests as method arguments ("parameterize"); (3) delay/queue execution — slide 201 shows queuing, and the deck's "operating system?" aside points at task schedulers and job queues executing commands later, even on another thread; (4) undo/redo via a history stack. Composite bonus: macro commands = a list of commands executed in sequence.
Edge Cases & Gotchas • Snapshot-based undo (as in the slides) can eat huge memory for large documents — the alternative is storing inverse operations, which the Memento pattern refines later.
• Undo of irreversible effects (sent email, printed page) is impossible — decide which commands are undoable.
• One class per operation → many tiny classes; in modern Java, lambdas can stand in for simple commands (Runnable ≈ Command with run() as execute()).
• Queued commands may execute after the world changed — validate inside execute(), not just at creation.
Exam Tips Trigger phrases: "undo/redo", "queue or schedule requests", "same operation from button, menu, and shortcut", "log operations", "remote control", "transactional requests". Multiple entry points to one operation is the deck's signature clue — spot it and name Command immediately.
Pattern 6 of 6 · Object behavioral

State

The Gumball Machine: when your object seems to "change its class" every time a quarter drops.

The machine (slides 203–216)

A gumball machine has four states — No Quarter → Has Quarter → Gumball Sold → Out of Gumballs — and four actions: insertQuarter(), ejectQuarter(), turnCrank(), dispense(). The first implementation stores the current state as an int constant and every action method is a wall of conditionals:

public void insertQuarter() {
    if (state == HAS_QUARTER)        System.out.println("You can't insert another");
    else if (state == NO_QUARTER)  { state = HAS_QUARTER; System.out.println("Quarter inserted"); }
    else if (state == SOLD_OUT)      System.out.println("Machine is sold out");
    else if (state == SOLD)          System.out.println("Please wait...");
}   // …and the SAME conditional ladder in ejectQuarter, turnCrank, dispense

Then marketing strikes: "10% of the time the customer wins a free gumball — buy one, get one!" That's a brand-new Winner state — and the deck calls what happens next "the nightmare of change": you must reopen and rewrite all four action functions, re-testing every branch. The state diagram gets a new node; the code gets surgery everywhere.

The new design (slides 217–240)

Invert the structure. Instead of actions containing state-conditionals, make each state a class that implements every action for itself:

Context delegates every action to its current state object; states themselves trigger transitions.
public class NoQuarterState implements State {
    private GumballMachine machine;                       // machine ref passed in
    public NoQuarterState(GumballMachine m){ machine = m; }

    public void insertQuarter() {
        System.out.println("You inserted a quarter");
        machine.setState(machine.getHasQuarterState());   // knows who's next
    }
    public void ejectQuarter() { System.out.println("You haven't inserted one"); } // invalid op
    public void turnCrank()    { System.out.println("You turned, but no quarter"); }
    public void dispense()     { System.out.println("You need to pay first"); }
}

// Context: conditionals GONE — pure delegation
public class GumballMachine {
    State noQuarterState, hasQuarterState, soldState, soldOutState, winnerState;
    State state = noQuarterState;                        // start at NoQuarter (slide 210)

    public void insertQuarter() { state.insertQuarter(); }
    public void turnCrank()     { state.turnCrank(); state.dispense(); }
    void setState(State s)      { this.state = s; }
}

Adding WinnerState now (slides 236–240): write one new class (dispenses two gumballs), give the machine a reference to it, and have HasQuarterState.turnCrank() roll the 10% dice to choose Winner vs Sold. Slide 229's payoff line: "No change when new state is added" to the machine's action functions — Open/Closed Principle, delivered.

Allow an object to alter its behavior when its internal state changes. The object will appear to change its class. — Slide 241

The deck's second example (slide 252): a Document whose publish() "works a little bit differently in each state" — Draft → moderation, Moderation → published only if the caller is an admin, Published → does nothing. Same method, state-dependent behavior: textbook State.

Edge Cases & Gotchas • Who owns transitions? Here states set the next state themselves — flexible, but scatters the transition table across classes. The alternative (context decides) centralizes it but bloats the context. Know both trade-offs.
• States here are long-lived fields on the machine (fine — they're stateless behavior objects). If states carried per-transaction data, you'd instantiate them fresh.
• Only two or three states with trivial logic? The pattern is overkill — a plain enum + switch is honest engineering.
• Invalid operations must still be handled in every state (slide 224's "Invalid Ops."), even if the handling is just a polite message — that completeness is where beginners lose marks.
Exam Tips Trigger phrases: "behaves differently depending on its mode/status", "finite state machine", "vending machine / order lifecycle / media player / document workflow", "massive switch on a status field". If the scenario gives you a state diagram or a status enum with sprawling conditionals — it's State. Justify with: eliminates conditional ladders, new states without touching existing code (OCP), each state's logic cohesive in one class (SRP).
