State & Statechart Diagrams

Good morning. Today we cross from the structural world of class diagrams and the interaction world of sequence diagrams into the world of behavior over time — how a single object's life unfolds as events strike it. By the end of this session you should be able to read any statechart cold, build one from a scenario, and defend every arrow you draw in a viva. Let's begin.

01What Is "State"?

Every object you have ever modelled — a Campaign, a StaffMember, a phone line — is quietly changing shape as the program runs, even though its identity never changes. That changing shape is what we call state.

"A state is a condition during the life of an object, or an interaction during which it satisfies some condition, performs some action, or waits for some event."

Formally: the current state of an object is determined by the current value of its attributes and the links it holds with other objects. Nothing more, nothing less. If you can point to the attribute(s) whose value flips a decision, you have found a state boundary.

Canonical example — StaffMember.startDate

A StaffMember object doesn't have an explicit "isProbationary" flag. Instead, the attribute startDate — compared against today's date — determines whether the object is currently in the Probationary state. This is the core insight of the whole topic: states are usually derived from attribute values and links, not stored as a separate field.

🎓 Professor's Note
Notice the parallel with sequence diagrams: there, we cared about messages between objects. Here, we zoom into one object and ask "as messages/events arrive over its lifetime, what shape does it take?" State diagrams are the natural complement — sequence/collaboration diagrams show one scenario across many objects; statecharts show all scenarios for one object.
💡 Brainstorm
Think of your own Campaign object from the ERD lecture. Without looking ahead, jot down: what states might it pass through from creation to archival? What attribute or event would trigger each transition? We'll compare your answer against the slide's actual model in Section 08.

02State Diagram vs. Statechart Diagram

These two names refer to the same UML diagram type — "Statechart diagram" is simply the more formal/complete name (from Harel statecharts, which UML adopted). Key facts to lock in:

  • State diagrams capture the behavior of a software system — how it responds to stimuli over time.
  • They can model the behavior of a class, a subsystem, a package, or an entire system — not just single objects.
  • They are used to model event-based systems: a state of an object is controlled by an event.
  • Statechart diagrams describe the various states an entity can be in within the application system.
📝 Exam Tip
A common short-answer question: "Is a State diagram the same as a Statechart diagram?" Answer: Yes — "Statechart" is the UML-standard, fuller name; "State diagram" is the everyday shorthand. Don't lose marks treating them as different diagram types.

03Anatomy of a Statechart — the GradeRate Example

Let's dissect the slide's simplest complete example: the lifecycle of a GradeRate object.

Pending → Active → Lapsed → (final), each transition guarded by a date condition
SymbolMeaning
● (filled circle)Initial state (pseudostate) — where the object's life begins, e.g. on construction via GradeRate()
Rounded rectangleState — a named condition the object is "in" for some duration
ArrowTransition — instantaneous movement from one state to another, usually labelled with the triggering event/condition
◉ (circle in circle)Final state — the object's life (or this part of its life) ends here
⚠ Edge Case
Notice all three transitions in GradeRate are not triggered by a method call — they're triggered by time/condition checks (when [...] and after [...]). Students often assume every transition needs an explicit event name; many are pure guard conditions on the passage of time. We formalize this as the elapsed-time event and change event next.

04Types of Events

An event is what makes a transition fire. UML recognizes exactly four kinds — memorize all four verbatim, this is a favourite short-answer question.

1. Change Event

Occurs when a condition becomes true. Written as when [condition]. E.g. when [rateStartDate <= currentDate].

2. Call Event

Occurs when an object receives a call to one of its operations, from another object or from itself. E.g. authorized(authorizationCode).

3. Signal Event

Occurs when an object receives a signal — an asynchronous communication (fire-and-forget, unlike a call which usually implies synchronous invocation).

4. Elapsed-Time Event

Caused by the passage of a designated period of time after a specified event — frequently, the entry into the current state. Written as after [duration]. E.g. after [1 year].

The Campaign Event Rule

event(params) [guard condition] / action-expression

Read this transition label as: "When the authorized(authorizationCode) call-event arrives, and the guard [contract Signed] is true, fire the transition and execute the action setCampaignActive()."

📝 Exam Tip
The general transition label syntax is event-signature [guard-condition] / action-expression. All three parts are optional independently — you can have a transition with only a guard (change event, e.g. [rateStartDate <= currentDate]), only an action, or all three together. Examiners test whether you can correctly split a compound label into its three clauses.
⚠ Edge Case
A call event named on a transition must correspond to an actual operation in that class's class diagram. If your statechart shows authorized(authorizationCode) triggering a transition on Campaign, then Campaign (or a class it delegates to) must declare that operation — statechart and class diagram must stay consistent with each other (more on this in Section 12).

05Actions & Activities Inside a State

A state box isn't always just a name — it can carry an internal transition compartment listing what happens on entry, on exit, while inside, or as a call-triggered internal reaction.

Generic anatomy: name compartment on top, internal transitions below
KeywordFires when…Runs once or continuously?
entry /the state is entered, regardless of which transition led hereOnce, instantaneously
exit /the state is left, regardless of which transition leavesOnce, instantaneously
do /the object remains in the stateContinuously / for a duration — can be interrupted by an outgoing transition
include /—References a nested sub-statechart (submachine) by name

Concrete example — DropDownMenu.MenuVisible

Opening the menu displays it (entry), a sound loops while open (do), selecting an item highlights it in place (internal call event — no state change), closing hides it (exit)
⚠ Edge Case
itemSelected() / highlightItem() here is an internal transition — it reacts to an event without leaving the state (no arrow to another box). Contrast this with a normal transition, which always exits and (re-)enters a state, re-triggering exit/entry actions. If a question asks "does highlighting an item re-display the menu?" — the answer is no, because entry only fires when the state is freshly entered, and an internal transition never exits.

08Worked Example — Campaign Statechart (Evolving Through Revisions)

This is the flagship example of the lecture, and the slides deliberately show it evolving across four revisions. Walking through why each revision happened is exactly the kind of "requirements changed, update the model" reasoning examiners love to test.

Revision 1 — the flat lifecycle

v1: Commissioned → Active → Completed → Paid, with a recursive self-loop on Completed for partial payments

The recursive (self) transition on Completed — paymentReceived(payment) [paymentDue - payment > 0] — models any payment that does not fully clear the balance: the object leaves and immediately re-enters the same state, which correctly re-runs entry/exit if any were defined.

Revision 2 — requirement change: automatic refunds

When the client asked for overpayments to auto-generate a refund, a single new transition was added — no existing state or transition was removed:

🎓 Professor's Note
paymentReceived(payment) [paymentDue - payment < 0] / generateRefund() — same event, different guard, going straight to Paid. Compare the three guards side by side: > 0 (still owing, stay in Completed), = 0 (exact payment, go to Paid), < 0 (overpaid, refund and go to Paid). Together these three guards must be mutually exclusive and collectively exhaustive — a golden rule for any set of guarded transitions leaving one state on the same event.

Revision 3 — nested substates for Active

Active itself is not atomic — it decomposes into Advert Preparation → Scheduling → Running Adverts, looping back to Advert Preparation on extendCampaign(). We formalize this pattern in Section 09.

Revision 4 — concurrency + cancellation

The final version adds a second, independent, concurrently-running region inside Active called Monitoring (Survey ⇄ Evaluation), and a campaignCancelled() event reachable from almost anywhere. We cover concurrency in Section 10 and cancellation as an edge case in Section 13.

📝 Exam Tip
Class Test 2-style questions often give you Revision 1 and ask you to draw Revision 2 (or vice versa) given a one-line requirement change ("what if overpayment should auto-refund?"). Practice the skill of adding exactly one new guarded transition without disturbing the rest of the diagram — resist the urge to redraw everything.

09Nested (Composite) Substates

A state can itself contain a complete statechart — this is a composite state (also "superstate"). The inner diagram is called a substate machine.

The Active state of Campaign, showing nested substates and its own initial pseudostate
  • The initial pseudostate arrow inside the composite should not be labelled with an event — but may be labelled with an action (not required here).
  • A state's decomposition can be hidden to reduce clutter, shown instead as include / SubmachineName plus a small decomposition indicator icon in the corner of the box (two small linked rectangles) — this is exactly what the Active state's collapsed view does when referencing the Running submachine.
  • An exit transition drawn from the outer boundary of the composite state (like campaignCompleted() leaving straight to the final state) applies no matter which inner substate the object is currently in.
💡 Brainstorm
If campaignCancelled() can fire while the campaign is in any inner substate of Active (Advert Preparation, Scheduling, or Running Adverts) and always leads to Completed, would you draw three separate arrows — one from each inner state — or one arrow from the composite state's boundary? (Answer: one arrow from the boundary — that's precisely why composite states exist, to avoid duplicating the same transition on every substate.)

10Concurrent (Orthogonal) Substates

Sometimes a composite state genuinely has two or more independent threads of behavior happening at once. UML shows this by splitting the composite state box into regions with a dashed line.

Active split by a dashed line into two orthogonal regions: Running (top) and Monitoring (bottom), each with its own initial state
One transition in, two states entered. A single transition into the composite Active state is equivalent to a simultaneous transition into the initial state of each concurrent region — the Campaign object enters Advert Preparation and Survey at once.
Every region needs its own initial state. This is mandatory — without it, there's ambiguity about which substate to enter first in that region.
Regions evolve independently. Once inside the composite state, a transition firing in one region (say, Running advancing from Advert Preparation to Scheduling) has zero effect on the other region's current substate (Monitoring stays wherever it was).
Leaving the composite exits everything. A transition out of Active applies to all its substates, no matter how deeply nested each region currently is.

Synchronization bars

Fork bar splits one transition into both regions; join bar waits for both regions to finish before continuing

The thick vertical/horizontal bar is a synchronization bar. Splitting (fork) explicitly shows an event triggering entry into specific concurrent substates at once; merging (join) shows that the composite state is not exited until both concurrent regions have reached their own final states.

📝 Exam Tip
"Concurrent" here means logically independent, not necessarily executing on separate CPU threads — the exam wants you to explain why a designer chose concurrent regions (e.g. advert scheduling and audience monitoring genuinely don't depend on each other's progress) rather than just define the notation.

11Worked Example — Garage Door Controller (Practice Scenario)

This is the slide's hardest scenario — a great self-test before the quiz. Read the requirements, then study how they map onto two concurrent regions.

💡 Scenario
  • The operator sets the garage control mode: off, auto, closed, or open — at any time.
  • entrygate / exitgate events signal cars entering/leaving.
  • The garage tracks count (cars currently inside) against max (capacity).
  • Entry gates: locked in closed mode, unlocked in open mode, no particular state in off mode, and in auto mode should lock automatically once full.
Top region (Gate Control): NoCentralControl ⇄ CentrallyControlled{Manual, Automatic}. Bottom region (Sign): NotFull ⇄ Full — independent of gate mode
⚠ Edge Case — why is Sign a separate concurrent region?
NotFull/Full (the capacity sign) changes purely based on count vs max, regardless of what mode the operator has set. It doesn't fit inside Manual or Automatic, and it isn't affected by mode-off/mode-auto transitions either. That is exactly the signal to model it as an independent concurrent region rather than trying to cram it into the gate-control hierarchy — a great pattern-recognition cue for exam scenario questions: "does this piece of behavior change independently of everything else? If yes, it's probably its own orthogonal region."

12Preparing Statecharts — Two Approaches

The slides define two systematic ways to derive a statechart rather than guess one from scratch: the Behavioural approach (bottom-up, from interaction diagrams) and the Life cycle approach (top-down, from the object's conceptual life stages).

Behavioural Approach — 8 Steps

Examine all interaction diagrams (sequence/collaboration) that involve each class with heavy messaging.
Identify the incoming messages on each interaction diagram that may correspond to events. Also identify the possible resulting states.
Document these events and states on a statechart.
Elaborate the statechart as necessary to cater for additional interactions as these become evident, and add any exceptions.
Develop any nested statecharts (unless already done in an earlier step).
Review the statechart to ensure consistency with use cases — in particular, check that any constraints implied by the statechart are appropriate.
Iterate steps 4, 5, and 6 until the statechart captures the necessary level of detail.
Check the consistency of the statechart with the class diagram, with interaction diagrams, and with any other statecharts and models.
This is exactly how the Behavioural approach found the campaignCompleted() event: it's the incoming message to :Campaign in the sequence diagram for "Set Campaign Completed"
🎓 Professor's Note
This is the payoff of having studied sequence diagrams first: every call arrow landing on an object's lifeline in a sequence diagram is a candidate event on that object's statechart. The Behavioural approach formalizes exactly this cross-diagram reasoning — it's the strongest argument for why UML diagrams must stay mutually consistent (Section 13).

Life Cycle Approach

The alternative: reason top-down about the natural, conceptual life stages of the object first (e.g. "a Campaign is commissioned, then runs, then completes, then gets paid, then archived") and only afterward attach concrete events/guards/actions to each transition, cross-checking against interaction diagrams as they become available. In practice, real projects blend both approaches — life-cycle thinking gives you the skeleton fast, interaction diagrams supply the exact triggering event names and action calls.

13Exam Pitfalls & Consistency Rules

❌ Pitfall: unlabelled initial transition

Labelling the arrow out of the initial pseudostate with an event is wrong — it may carry an action (/assignManager()) but never an event, since the pseudostate itself has no "state" for an event to interrupt.

❌ Pitfall: call event with no matching operation

Every call-event name on a transition must exist as an operation on that class (or a class it delegates to) in the class diagram. Mismatches are a classic consistency-check exam question.

❌ Pitfall: overlapping guards

Two transitions leaving the same state on the same event must have mutually exclusive guard conditions (e.g. >0, =0, <0) — overlapping guards make the statechart non-deterministic and ambiguous.

❌ Pitfall: forgetting per-region initial states

In a concurrent (orthogonal) composite state, each region needs its own initial pseudostate. Omitting one in any region is an incomplete-model error.

❌ Pitfall: internal transition drawn as an arrow

An internal transition (e.g. itemSelected() / highlightItem()) stays inside the state's compartment — drawing it as an arrow looping back to the same box incorrectly implies exit/entry re-fire.

❌ Pitfall: confusing "do" with "entry"/"exit"

entry/exit run once, instantaneously, on boundary crossing. do runs for the duration the object remains in the state and can be pre-empted by an outgoing transition mid-activity.

Cross-Model Consistency Checklist

Statechart elementMust be consistent with…
Call event nameAn operation declared on that class in the class diagram
Action expressions (/action())Operations that the class (or a collaborator) actually implements
States entered/exitedAttribute values and links described in the class diagram's attributes, and referenced in interaction diagrams
Sequence of events across a use caseThe corresponding use case description and its sequence/collaboration diagram
📝 Exam Tip
A guaranteed viva-style question: "How would you verify this statechart is consistent with the rest of your design?" Give the checklist above as your answer structure — examiners reward naming which other diagram each element must match, not a vague "make sure everything lines up."
