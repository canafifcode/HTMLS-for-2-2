Sequence & Collaboration Diagrams

A sequence diagram is a single scenario, frozen in time and stretched out on paper. It answers one question precisely: who talks to whom, in what order, and what do they say? A collaboration diagram tells the exact same story from a different angle — structure first, numbers instead of a timeline. Where a class diagram shows the skeleton of a system, these two show it breathing.

01

What is a Sequence Diagram, and why do we need it?

One of UML's "interaction diagrams" — it doesn't describe structure, it describes behavior over time.

A sequence diagram models a single scenario executing in a system — typically one path through a use case. It shows exactly which messages get sent, by whom, to whom, and in what order.

  • It visualizes the execution sequence of a use case — not the whole system, just one story unfolding.
  • It complements the class diagram: the class diagram is the cast list and their relationships; the sequence diagram is one scene of the play, with actual dialogue.
  • It's read like a script top to bottom — the vertical axis is time.
👨‍🏫 Professor's Note
Think of it as a subway map through time: each vertical line is a station (an object), and every train that leaves a station toward another is a message. Nothing about the diagram tells you the station's internal structure — that's the class diagram's job. The sequence diagram only cares about the trips.
💭 Brainstorm
Before scrolling further: if you had to draw "a student submitting an assignment on a portal" as a comic strip with time flowing downward, who are your 3–4 "characters" (objects), and what's the very first message? Hold that scenario in your head — we'll reuse this instinct across every section below.
02

Key Parts of a Sequence Diagram

Three building blocks — participant, message, and the two axes — before any notation details.

  • Participant — an object or entity; the "actor" of the diagram. Drawn as a labelled box at the top.
  • Message — communication between objects, drawn as a horizontal arrow.
  • Axes —
    • Horizontal: which participant is acting (position = identity)
    • Vertical: time, flowing downward ↓

Every sequence diagram begins with an unattached "found message" — an arrow that starts from nowhere (a filled dot or just off-diagram) and hits the first participant. This represents the trigger that kicks off the scenario — usually a user action or an external event.

Fig 2.1 — Email client checking for mail (found message → checkEmail)
📝 Exam Tip
If a question says "draw the sequence diagram for this use case," always start with a found message (the dot-and-arrow) even if the trigger isn't explicitly named — examiners dock marks for lifelines that start "mid-air" with no found message.
03

Syntax: Representing Objects

The box-and-lifeline notation, and the three legal ways to label a participant.

An object is drawn as a box with an underlined label — underlining is what marks it as an instance, not a class. The general format is:

// general label syntax Objectname:Classname

Below the box hangs the object's lifeline: a dashed vertical line representing how long that object exists within the scenario being modeled.

Fig 3.1 — The three ways to label a participant
  • Named object (Smith:Patient) — use when the diagram has multiple objects of the same class and you must tell them apart (e.g. two :Distributors).
  • Anonymous object (:Patient) — the common case. When there's only one instance in play, naming it just adds clutter.
  • Object of unknown class (Smith) — rare; used when you know an object exists but its class isn't determined/relevant yet.
⚠️ Edge Case
Don't confuse "no name" with "no colon." :Patient (colon, no name) is a perfectly normal anonymous object — it is not the same notation as "object of unknown class," which drops the colon entirely (Smith, no class after it). Examiners sometimes test whether you can read this distinction off a diagram.
👨‍🏫 Professor's Note
Rule of thumb: write the object's name only if it clarifies the diagram — i.e., only when you need to disambiguate. Don't name every object out of habit; a sequence diagram cluttered with unnecessary names is harder to read, not easier.
04

Representing Messages Between Objects

A message is a method call — the arrow's head style and line style together tell you what kind.

A message is drawn as a horizontal arrow pointing to the receiving object, with the message name and arguments written above the arrow — e.g. admit(patientID, roomType).

Fig 4.1 — The three arrow types, side by side
  • Synchronous message — solid line, solid (filled) arrowhead. The caller blocks and waits for this call to finish. Most method calls in Java are this.
  • Asynchronous message — solid line, stick (open, unfilled) arrowhead. The caller fires it off and continues immediately — no waiting.
  • Return message — dashed line, stick arrowhead. Shows a value/control coming back from a completed call. Often optional to draw if it's obvious, but required whenever the return value matters to the story.
solid + solid head = synchronous solid + open head = asynchronous dashed + open head = return
📝 Exam Tip
A classic trap: examiners draw a dashed arrow going forward (in the same direction as the call) and ask what's wrong. Dashed lines are only valid for return messages, which always point backward, toward the caller. A forward-pointing dashed arrow is invalid notation — call it out if you see it.
⚠️ Edge Case
Asynchronous vs. synchronous is easy to mix up under time pressure because both use a solid line. Zoom in on the arrowhead only — solid filled triangle = sync, open "stick"/V-shape = async. Don't rely on line style alone.
05

Indicating Method Execution: Activation Bars

The thick box on a lifeline — showing when an object's method is actually "live" on the call stack.

An activation is a thick, narrow box drawn over an object's lifeline, active exactly while that object's method is on the call stack — either it's actively running code, or it's paused, waiting on another object's method to return.

Fig 5.1 — A plain activation, and a nested self-call activation
👨‍🏫 Professor's Note
Activation bars answer "who's currently doing work?" at a glance. When you see a stack of nested boxes on the same lifeline (one narrow box on top of a wider one), read it as "this object called one of its own methods" — the outer box is the original call still waiting, the inner box is the fresh call sitting on top of it.
⚠️ Edge Case
An activation bar doesn't necessarily mean the CPU is executing that object's code right this instant — it might be idle, blocked, waiting for a synchronous call it made to someone else to return. The box represents stack presence, not CPU activity. This distinction trips people up when reasoning about concurrency-adjacent questions.
06

Lifetime of Objects: Creation & Deletion

Two special notations for when an object is born mid-scenario, or explicitly dies.

  • Creation — an arrow labelled new, pointing at the top of a fresh object box. Because it's created after the scenario started, that box is drawn lower than objects present from the beginning.
  • Deletion — a large X at the bottom of the lifeline, marking where the object stops existing.
Fig 6.1 — Handler creates a Query object, uses it, then it's destroyed
⚠️ Edge Case
Java doesn't have explicit object destruction — objects simply fall out of scope and get garbage-collected. So drawing an X in a Java-based sequence diagram is a modeling choice to show "this object is logically done being used here," not a literal call to a destructor. Don't write delete() as if it were a real Java method — that's a C++ habit, and examiners will flag it.
📝 Exam Tip
"20-minute" style questions on this exact topic tend to ask you to identify the bug in a given diagram — a classic one is an object receiving a message after its X mark, i.e. after it was already deleted. Scan lifelines top-to-bottom for any arrow that touches a lifeline below its X — that's an invalid diagram.
07

Alternatives, Options & Loops (Frames)

A frame is a labelled box drawn around part of the diagram to express control flow — conditionals and repetition.

FrameKeywordMeaning
opt[condition]Optional block — runs only if the condition holds. No "else."
alt[condition] / [else]If/else — two (or more) regions separated by a horizontal dashed line, exactly one region executes.
loop[condition or items]Repetition — e.g. [for each line item], runs the enclosed messages repeatedly.
Fig 7.1 — loop wrapping an alt: dispatch differently based on order value
👨‍🏫 Professor's Note
Read frames like nested brackets in code: loop { alt { ... } else { ... } }. The frame's label tab (top-left corner flag) tells you which construct it is; the bracketed text next to it is the guard condition, exactly like an if statement's condition in Java.
📝 Exam Tip
The 30-minute "Builder"-adjacent long questions sometimes ask you to translate a frame-heavy sequence diagram into pseudocode or Java. Map directly: opt → if, alt → if/else, loop → for/while. Practice this both directions — diagram → code, and code → diagram.
⚠️ Edge Case
Don't nest frames sloppily — an alt region living partially outside its enclosing loop box is a common hand-drawing mistake in timed exams. Every nested frame's rectangle must sit fully inside its parent's rectangle.

09

Actors, Branching & Object States

Lecture 8 pushes sequence diagrams closer to real systems: humans as participants, mid-activation branching, and objects that can be "busy."

So far every participant has been an object box. But the very first message in a scenario almost always comes from a human actor — drawn with the standard UML stick-figure, exactly like on a use-case diagram, but here it also gets its own lifeline running down the page like any other participant.

Fig 9.1 — CustomerP / PrinterP: actor lifeline, branching, and active/inactive states
  • Actor as participant — a person can own a lifeline exactly like an object does. Its activation bar tracks "the customer is engaged in this scenario," not code execution.
  • Branching — one activation can send different messages down different guarded paths, exactly like alt, but drawn informally as forking lines from the same point rather than inside a boxed frame. You'll see both notations across different textbooks — recognize them as equivalent.
  • Active vs. Inactive lifeline — a plain dashed line with no activation box is inactive (the object exists but is doing nothing right now); the moment a message hits it and a box appears, it becomes active.
👨‍🏫 Professor's Note
The Printer example is doing three jobs at once worth separating in your head: it shows an object querying state before acting (GetStatus() before Print()), it shows guard-based branching without a formal alt box, and it shows an asynchronous callback (Ready(file)) arriving whenever the printer finishes — the customer doesn't sit there blocked waiting.
⚠️ Edge Case
Some textbooks draw the asynchronous arrowhead as a small filled or open triangle rather than the "stick"/V shape we used earlier — both mean the same thing (non-blocking call). BUET's slides use this triangle style in the printer example. Don't panic if a past paper's arrowheads look slightly different from your lecture slides; the rule to apply is always "solid line = call, dashed = return; open/unfilled head = async, filled head = sync."

11

Collaboration Diagrams

Same information as a sequence diagram — structured completely differently, with no time axis at all.

  • Holds the same information as a sequence diagram — same objects, same messages, same guards.
  • Shows the links (structural connections) between objects that participate in the collaboration — closer in spirit to an object diagram than to a timeline.
  • Has no time dimension. Instead, order is captured entirely with sequence numbers written next to each message.
  • Numbers use a nested style — e.g. 3, then 3.1, then 3.1.1 — to show which messages are nested inside which, mirroring how deep a call sits within another call.
👨‍🏫 Professor's Note
If a sequence diagram is a subway map through time, a collaboration diagram is the subway's actual track network — objects sit wherever makes structural sense (often radiating out from a controller), and you follow the numbered labels, not vertical position, to reconstruct "what happened when."
Sequence DiagramCollaboration Diagram
Order shown by vertical position (time flows down)Order shown by sequence numbers on each message (1, 2, 3.1, 3.2…)
Emphasizes the timing of an interactionEmphasizes the structure / links between objects
Great for spotting concurrency, async gaps, long waitsGreat for spotting which objects are structurally coupled to which
Layout is mostly fixed (lifelines side by side)Layout is free — often drawn radially around a central object
Fig 11.1 — Register: Collaboration Diagram (same scenario as Fig 10.1–10.2, restructured)
📝 Exam Tip
A guaranteed exam skill: given one diagram type, redraw the same scenario as the other. The safest method — list every message from the sequence diagram top-to-bottom, number them 1, 2, 3… (going one level deeper, e.g. 3.1, for anything nested inside another call), then place that number next to a link on the collaboration diagram. You are not inventing new messages, only re-expressing the same ones.

12

Model Consistency

Two rules that keep your sequence/collaboration diagrams honest against the rest of your UML model.

  • Operation allocation must match the class diagram. If a message verifyLogin(id, pw) appears on a sequence diagram pointed at :Register, then the Register class on your class diagram must actually declare a verifyLogin(id, pw) operation — same name, same parameter list. A message with no matching operation is a modeling bug, not just a drawing slip.
  • Every sending object needs an object reference to its target. An object can't send a message to something it has no way of reaching. This reference has to come from somewhere:
    • an association already exists between the two classes on the class diagram, or
    • some other object passes the reference to the sender first (e.g. as a parameter, or a return value).
👨‍🏫 Professor's Note
This is why we say sequence/collaboration diagrams and class diagrams are two views of one model, not two separate documents. Every arrow you draw on a sequence diagram is a promise your class diagram has to keep — an operation that exists, reachable through a real reference. Message pathways should always be traced back and sanity-checked this way.
📝 Exam Tip
A frequent "find the design flaw" question gives you a sequence diagram and a class diagram side by side and asks you to spot an inconsistency — e.g. a message calling a method the class diagram doesn't declare, or a sender with no association path to reach its target. Always cross-check both directions: message → operation exists? sender → has a reference path?
13

Exam Pitfalls & Commonly Confused Ideas

Where marks are lost — mixing up notation, or mixing up two diagram types entirely.

ConfusionHow to tell them apart
Sequence vs. Collaboration diagram Sequence = order shown by vertical position on a timeline. Collaboration = order shown by nested sequence numbers (1, 2, 3.1…) on structural links. Same underlying information, different layout logic.
Sync vs. Async message Both use a solid line. Look only at the arrowhead: filled triangle = sync (blocking); open/stick (or open triangle, in some textbooks) = async (fire-and-forget).
Async vs. Return message Both use an open arrowhead. Look at the line style: solid = async call (forward); dashed = return (always backward, to the original caller).
Activation vs. Lifeline Lifeline (thin dashed line) exists for the object's entire presence. Activation (thick box) exists only while a method is on the stack.
opt vs. alt opt has no "else." alt always pairs with a divided region, whether drawn as a boxed frame or as informal branching lines with guard labels.
📝 Exam Tip
Trigger-word recognition still applies here: "for all" / "for each" → loop (or the * shorthand); "link between objects, no timing shown" → collaboration diagram; "nested numbering like 3.1.1" → collaboration diagram; "draw the timeline of..." → sequence diagram.
⚠️ Edge Case
A message arrow pointing to an object's own lifeline that doesn't create a nested activation box (i.e., just touches the same activation) is sometimes drawn informally to mean "internal processing note" rather than a real method call — be ready to distinguish a formally nested self-call from this looser notation if a past paper uses it.
14

Practice Quiz

Instant feedback — click an option to see if you're right, and why.

Q1. An arrow with an open/stick arrowhead and a dashed line represents:
✅ Correct answer: A return message. Dashed line + stick head = return, and it always points back toward the original caller.
Q2. You need to model "for every item in the cart, reserve it in inventory." Which frame do you use?
✅ Correct answer: loop. "For every item" is the trigger phrase for repetition — never manually duplicate lifelines to represent a loop.
Q3. In Smith:Patient, what does the underline signify?
✅ Correct answer: This is an object instance, not a class. Underlining is the universal UML convention for instances (also used for objects in class-diagram-adjacent contexts).
Q4. On a lifeline, you see an X placed above a message arrow that still touches that lifeline further down. What's wrong?
✅ Correct answer: invalid diagram. Once an object's lifeline ends at X, nothing may interact with it further down. This is a favorite "spot the bug" exam question.
Q5. What's the key difference between an opt frame and an alt frame?
✅ Correct answer: alt has a paired else-region. opt is a plain "if, no else" — if the guard fails, the enclosed messages simply don't happen.
Q6. In a collaboration diagram, how is the order of messages shown, since there's no time axis?
✅ Correct answer: nested sequence numbers. Since layout is free-form, numbers (with dotted nesting to show call depth) are the only thing encoding order.
Q7. A sequence diagram shows :Register sending calculateGPA() to :Student, but the class diagram's Student class has no such operation and no association to Register. What principle is violated?
✅ Correct answer: model consistency. Every message needs a matching class-diagram operation, and every sender needs a reachable reference (association or a passed-in reference) to its target.
Q8. What does a leading * before a message name, like *getCourseList(), typically shorthand for?
✅ Correct answer: sent repeatedly. It's a compact substitute for wrapping a single message in a full loop frame — same meaning, less drawing.
