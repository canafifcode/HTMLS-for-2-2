Additional Collaboration Diagrams

Five fully worked collaboration diagrams from a marketing Campaign Management case study — a new domain on purpose, so you're forced to prove you understand the pattern behind these diagrams, not just one memorized scenario. We'll also formalize two things Lec 7–8 only touched lightly: the boundary / control / entity icon vocabulary, and the exact rules for nested decimal numbering.

01

Setting the Scene

A quick orientation before the diagrams start — who's in this world, and why the domain changed.

Lecture 10 stays inside Chapter 9 (Bennett) — still collaboration diagrams — but swaps out the Course Registration case study from Lec 7–8 for a marketing agency's Campaign Management system. The cast of domain objects:

  • Campaign Manager — the human actor who runs the show.
  • Client — a company the agency runs campaigns for.
  • Campaign — a marketing campaign belonging to a client, with a budget.
  • Advert — an individual advert that's part of a campaign, and has a cost.
  • StaffMember — an agency employee who can be assigned as a client's point of contact.

Five use cases get the full worked-diagram treatment: add a campaign, assign a staff contact, check a campaign's budget, record a campaign's completion, and add an advert to a campaign. The last one comes with both a collaboration diagram and its equivalent sequence diagram, side by side — that pairing is the single most exam-relevant page in this lecture.

🎓 Professor's Note

Notice the domain swap is deliberate pedagogy, not laziness. If you can only reproduce the Course Registration diagrams from memory but freeze when handed Campaign/Client/Advert, you've memorized a picture, not learned a technique. The exam will hand you an unfamiliar domain. Your job in this lecture is to internalize the shape: actor → boundary → controller → (query loop, then act on entities) — a shape that's identical across all five examples here, just wearing different class names.

💡 Brainstorm

Before you scroll further: given only the use-case name "Check campaign budget," sketch for yourself which entity classes you'd expect to be involved, and guess which one actually does the arithmetic (adds up advert costs). Compare your guess against Example 3 below — there's a real design principle hiding in the answer.

02

Boundary / Control / Entity — the Three Icons

Every non-actor object in every diagram this lecture is one of exactly three analysis-class stereotypes. Learn the icons cold — you'll be reading them nonstop.

These come from Jacobson's robustness analysis convention (the same idea behind ICONIX-style analysis), and every collaboration diagram in this lecture uses all three:

«boundary»A screen, form, or external interface (printer, gateway). One boundary object per UI screen the user touches. Circle with a small perpendicular bar — think "plug into the outside world."
«control»Coordinates one use case's logic. Exactly one control object per use case realization; it lives only for that interaction. Circle with a curved arrow on top.
«entity»A persistent, business/domain object — Client, Campaign, Advert, StaffMember. These map almost directly onto your class diagram. Plain circle.

The rule of thumb for identifying them

  • One boundary object per screen or external interface the interaction touches — including non-UI interfaces like a printer (you'll see :CompleteCampaignPI — a "printer interface" boundary — in Example 4).
  • Exactly one control object per use case. If you see two "curved-arrow" circles doing the coordinating in one diagram, something's wrong — split the use case, or you've mis-tagged an entity as a controller.
  • One entity object per persistent domain noun that the use case reads or writes: Client, Campaign, Advert, StaffMember here.
⚠️ Edge Case

The curved arrow sitting on top of the control icon is part of the class symbol itself — it is fixed decoration on every instance of a control class, drawn identically whether or not that object ever sends itself a message. Don't confuse it with an actual self-message loop-back arrow (which would be a separate numbered arrow drawn from an object back to itself, representing a real message in the interaction). One is iconography; the other is a message.

📌 Exam Tip

A very common CSE213 question format: "Given this use case description, list the candidate boundary, control, and entity classes." Walk the description sentence by sentence — every screen/form/report → boundary; the use case itself → one control class named after the use case (e.g. AddNewCampaign); every business noun the actor or system needs to remember → entity. If a "thing" doesn't outlive the use case and doesn't touch the outside world, it's probably not a class at all — just a local variable or parameter.

03

The Numbering Scheme

Collaboration diagrams have no time axis — the numbers on the arrows are the only thing telling you what happens when. Get this rule wrong and every diagram you draw is illegible.

  1. Top-level messages — the ones sent directly as part of the root interaction — are numbered 1, 2, 3, 4 … in the order they occur.
  2. If handling message N causes its receiver to send further messages, those nested messages are numbered N.1, N.2, N.3 …
  3. If one of those (say N.2) itself triggers more messages, they get N.2.1, N.2.2 … — and so on, arbitrarily deep.
  4. The number of dots = stack depth. A message numbered 4.1.1.1 is happening four call-frames deep inside the handling of top-level message 4. Read it exactly like a nested outline or a recursive call stack.
  5. An asterisk * immediately before a message name means it's sent repeatedly — a loop. You'll often see an explicit guard alongside it, e.g. 1 *[For all clients]: getClient. This is the collaboration-diagram equivalent of a sequence diagram's loop combined fragment (Section 09 makes the translation explicit).
  6. Numbering restarts fresh for every separate collaboration diagram — each one models a single, self-contained use case (or use-case fragment), not a running total across the lecture.
1. control → EntityA : doSomething()
1.1 EntityA → EntityB : helperCall()
1.1.1 EntityB → EntityC : *fetchDetail()  // iterated — one call per item
2. control → boundary : refreshView()
2.1 boundary → control : ???  ← what comes next?
💡 Brainstorm

In the outline above, if boundary → control triggers one more message back down into an entity, what number does that message get? (Answer: 2.1.1 — one level deeper than its parent 2.1, regardless of what numbers were used earlier in the diagram.) This "reset per branch, nest per depth" logic is exactly what trips people up on exams when a diagram has two or three sibling top-level messages each with their own nested sub-trees, as you'll see starting with Example 3.

📌 Exam Tip

If you're asked to draw a collaboration diagram from a sequence diagram (or vice versa), number every message on the sequence diagram in the order its activation bar starts, top to bottom, then translate directly using the nesting rule above — a nested activation bar becomes a nested decimal number one level deeper than the activation bar that spawned it.

04

Worked Example 1 — Add a New Campaign

The baseline shape. Every later example is a variation on this skeleton, so study it slowly.

sd Add a new campaign — collaboration diagram

Reading it step by step

  1. 1 *getClient — before the user sees anything, the control object asks every Client entity for its data (the * means "loop over all of them") so the UI can populate a client-picker list.
  2. 2 startInterface — control tells the boundary to actually display itself now that it has data ready.
  3. 3 selectClient — the Campaign Manager picks a client on screen.
  4. 4 showClientCampaigns — the boundary forwards that selection into the control object.
  5. 5 getClientCampaigns — control asks the chosen :Client for its existing campaigns, to display them.
  6. 6 createNewCampaign — the actor clicks "new campaign" on the UI.
  7. 7 createNewCampaign — boundary forwards that click to control.
  8. 8 createCampaign — control asks the Campaign class to manufacture a brand-new Campaign instance.
  9. 9 addNewCampaign — the new :Campaign registers itself with :Client — the domain objects link to each other directly, without going back through control.
🎓 Professor's Note

Steps 1–2 happen before the actor does anything — that's the setup phase every one of these diagrams has: prime the boundary with data, then let the human act. And step 9 is the opposite pattern: once control has assembled the pieces, it lets two entities talk to each other directly rather than routing every last domino through itself. Control coordinates; it doesn't micromanage.

⚠️ Edge Case

Why is 8 createCampaign drawn as control → :Campaign when no Campaign object exists yet to receive it? In UML this models a message to the class (a "class-scope"/static-style creation operation) rather than to a specific instance — you're allowed to draw a link to an anonymous or not-yet-existing object when the message's job is to create it. Some textbooks draw a dashed "create" arrow instead; Bennett's notation here just numbers it like any other message.

Worked Example 3 — Check Campaign Budget

First diagram with real nested numbering — up to four dots deep. This is the one to slow down for.

sd Check campaign budget — collaboration diagram

The same interaction, written as a nested call outline

1 control → :Client  *getClient()
2 control → boundary : startInterface()
3 actor → boundary : selectClient()
3.1 boundary → control : showClientCampaigns()
3.1.1 control → :Client : getClientCampaigns()
3.1.2 control → :Campaign  *getCampaignDetails()
4 actor → boundary : checkCampaignBudget()
4.1 boundary → control : checkCampaignBudget()
4.1.1 control → :Campaign : checkCampaignBudget()
4.1.1.1 :Campaign → :Advert  *getCost()
4.1.1.2 :Campaign → :Advert : getOverheads()
🎓 Professor's Note

Look at who actually adds up the budget: :Campaign, not the control object. Control receives checkCampaignBudget() at depth 3, forwards it one level deeper to the Campaign entity, and Campaign is the one that loops over its adverts (*getCost) and sums them. This is the Information Expert principle you saw in the SOLID/GRASP material: the object holding the data (Campaign owns its list of Adverts) is the one that should compute over it — not the controller. That's the answer to the Section 01 brainstorm.

📌 Exam Tip

Notice 4.1.1 reuses the exact same message name checkCampaignBudget as its parent 4.1 and grandparent 4. That's normal and common — the same conceptual operation gets forwarded down the call chain, object to object, each hop getting a deeper number. Don't assume a repeated message name means a mistake; check the numbering, not just the name, to know which hop you're looking at.

07

Worked Example 4 — Record Completion of a Campaign

Same core skeleton, plus a twist: control talks to two different boundary objects in one interaction — one for input, one for output.

sd Record completion of a campaign — collaboration diagram

Steps 1 through 3.1.2 are identical in shape to Example 3 (populate the client list, let the manager pick a client, show that client's campaigns). The new material starts at step 4:

  1. 4 → 4.1 → 4.1.1 completeCampaign — the manager's "mark complete" click cascades from actor → boundary → control → the :Campaign entity, exactly like the budget check cascaded in Example 3.
  2. 4.1.2 printCompletionForm — after the entity update, control sends one more message — but this time not down into an entity, out to a second boundary object, :CompleteCampaignPI ("PI" = printer interface). Note the number: it's a sibling of 4.1.1, not nested inside it — both are direct children of 4.1, happening one after the other as part of handling the same top-level click.
⚠️ Edge Case

Boundary objects are not only input forms. Anything that talks to the world outside the software — a printer, an email gateway, a payment terminal, another system's API — is modeled as a boundary object too. A single use case can perfectly legally involve two, three, or more boundary objects: one per distinct outside-world touchpoint, input and output alike.

📌 Exam Tip

If an exam scenario says something like "…and the system prints a receipt," that sentence alone is enough to justify a second boundary class in your candidate-class list — don't fold printing into the control object just because it feels like "system logic." Printing touches the outside world, so it's boundary work.

Worked Example 5 — Add a New Advert

The keystone example: the same use case, drawn twice — once as a collaboration diagram, once as a sequence diagram — so you can see the translation happen in front of you.

This use case has a three-step drill-down: pick a client, pick one of their campaigns, then create a new advert inside it. Each drill-down step re-populates a list, and re-populating a list means iterating — which is exactly the mechanic this example exists to teach.

sd Add a new advert to a campaign — collaboration diagram
⚠️ Edge Case

Two naming quirks worth flagging: the new instance is called newAd:Advert instead of just :Advert — use the instanceName:ClassName form whenever you need to refer back to a specific object later in the diagram; plain :ClassName stays anonymous. And this particular slide labels the actor :CampaignManager with a leading colon, even though it's an actor, not an object instance — a labeling inconsistency you'll sometimes meet in real slide decks; don't let it confuse you about what's an actor versus an entity.

sd Add a new advert to a campaign — equivalent sequence diagram

The vocabulary this diagram introduces

TermWhat it is in the diagram above
LifelineThe dashed vertical line under each object's header box — its personal timeline, running top to bottom.
Activation / ExecutionThe thin filled rectangle on a lifeline while that object is actively doing work (e.g. :Client's bar while it handles getName/listCampaigns).
Combined FragmentThe bordered box wrapping one or more messages — here, both loop boxes.
Interaction OperatorThe keyword in the small tab at the frame's top-left corner — loop, in both cases here (others you'll meet: alt, opt, par).
Interaction ConstraintThe bracketed guard condition next to the operator — [For all client's campaigns] and [For all campaign's adverts]. It's the sequence-diagram cousin of collaboration diagram's *[…] notation.
Object CreationA dashed arrow (open arrowhead) pointing at a box that appears partway down the page — newAd:Advert, which didn't exist before the addNewAdvert call.
🎓 Professor's Note

Line the two diagrams up side by side and match them piece by piece: every *[condition]: message on the collaboration diagram is one loop [condition] combined fragment on the sequence diagram, wrapped around exactly the one message it iterates. And 5.1.1.1 Advert creating newAd:Advert on the collaboration side is the same event as the dashed creation arrow spawning newAd:Advert on the sequence side — same moment, same actor, two notations. This equivalence is Section 09's whole topic, formalized as a translation table.

09

Translation Guide — Collaboration ⇄ Sequence

They model the exact same interaction. Here's the dictionary between the two notations, extended from Lec 7–8 with this lecture's iteration mechanics.

Collaboration diagramSequence diagram
Objects free-floating, connected by association linksObjects laid out left-to-right as headers, each with a vertical lifeline
Explicit numbered order on every arrow (1, 2, 3.1…)Implicit order = top-to-bottom position; no numbers needed
Nested calls shown by a deeper decimal number (3.1.1)Nested calls shown by a nested activation bar, drawn further right / lower on the same lifeline
*message — asterisk before the nameloop combined fragment wrapped around the message
*[condition]: message — bracketed guard after the asteriskloop [condition] — the same condition, written as the fragment's interaction constraint
Object creation shown as a normal numbered message to the classObject creation shown as a dashed arrow (often «create»-labeled) to a box appearing partway down the page
No explicit return arrows — assumed implicitDashed return arrows optional, drawn back along the same path
Great for showing structure — which objects talk to whichGreat for showing timing — exact order, concurrency, nesting depth at a glance

A mechanical translation algorithm

  1. List every message on the sequence diagram in top-to-bottom order.
  2. For each message, count how many activation bars deep it is — that's its nesting depth.
  3. Assign decimal numbers by depth: depth 1 → next top-level integer; depth 2 → parent number + .1, .2… in order among siblings; deeper levels keep appending.
  4. Any message inside a loop fragment gets a leading *; carry the fragment's bracketed condition along as the guard.
  5. Redraw the objects as free nodes and connect them with links carrying their numbered messages — multiple messages can share one link if they connect the same pair of objects.
💡 Brainstorm

Try the algorithm in reverse on Example 3's checkCampaignBudget collaboration diagram: redraw it as a sequence diagram from scratch, using the numbering to decide where each activation bar nests. If you get four levels of nested activation bars by the time you reach 4.1.1.1, you've done it correctly.

Exam Pitfalls

Where marks get lost on this material, specifically.

PitfallWhy it costs marksFix
Drawing two "controller" objects for one use caseBreaks the one-control-per-use-case rule; usually means an entity got mistaggedIf a class needs its own coordinating logic across multiple use cases, it's probably an entity with a method — not a second controller
Forgetting the leading * when a message is clearly a loop (e.g. "for each advert…")Without it, the diagram claims the message fires exactly onceAny phrase like "for all," "for each," "every" in the use case text ⇒ asterisk the corresponding message
Restarting message numbering mid-diagram, or reusing a numberMakes the diagram ambiguous / unreadable — the numbers are the only ordering signalNumber strictly in the order messages are sent; nested messages always get a longer decimal than their parent, never a fresh top-level integer
Putting business logic (e.g. summing costs) directly in the control objectViolates Information Expert — control should coordinate, not compute over data it doesn't ownDelegate the computation to the entity that owns the data (Example 3: :Campaign sums its own adverts' costs)
Treating the control icon's curved arrow as a self-messageConfuses class iconography with an actual message in the interactionThe curved arrow is fixed to every control-stereotype object; a self-message would instead be a separate numbered arrow looping from an object back to itself
Missing a second boundary object for output (printing, email, etc.)Undercounts candidate classes on an "identify boundary/control/entity classes" questionAny distinct touchpoint with the outside world — input or output — gets its own boundary object
