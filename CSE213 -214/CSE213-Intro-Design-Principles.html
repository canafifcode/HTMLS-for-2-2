Sheet 00 · Orientation

Welcome to Software Design Principles

Scale: Conceptual
Rev: SOLID-1
Source: Dive Into Design Patterns, Ch.3

Good morning, everyone. Before we touch a single design pattern this semester, we need to talk about the principles that make patterns necessary in the first place. Think of today as learning to read blueprints before we start building houses — patterns are the pre-fabricated house designs, but principles are the physics that decide whether any house stands up.

Why this lecture matters

Every "clean code" habit you'll ever adopt — small classes, meaningful interfaces, avoiding god-objects — traces back to a small set of ideas: encapsulation, coupling/cohesion, and the five SOLID principles. We'll walk through the exact examples from your textbook slides (the tax-calculating Order class, the Cat/Food hierarchy, the shipping-cost example, the cloud-provider interfaces, and the light-switch DIP example), and I'll annotate each one with the traps students fall into during exams and interviews.

🎓 Professor's Note

None of these principles are laws of physics — they're heuristics. The slide deck itself says applying SOLID can make a program's architecture more complicated than it needs to be. The exam-worthy skill isn't reciting the rules; it's judging when a principle earns its complexity and when it doesn't.

Roadmap for today

  • Encapsulation — hiding what varies, at the method and class level
  • Interface vs. Implementation — programming to a contract, not a concrete type
  • The Diamond Problem — why multiple inheritance is dangerous
  • Coupling — the disease that principles are trying to cure
  • SOLID — Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion

Sheet 01 · Foundations

Encapsulation

Scale: Method → Class
Rev: ENC-1
Ref: Slides 2–5

Encapsulation is usually taught as "hiding data with private fields and getters/setters." That's true but shallow. The deeper definition your textbook uses: identify the parts of your program that vary and separate them from the parts that stay the same. Encapsulation is drawing a wall around volatility.

Encapsulation at the method level

Here's the classic example: a method that computes an order's total, including tax.

getOrderTotal() — beforetangled
method getOrderTotal(order) is
  total = 0
  foreach item in order.lineItems
    total += item.price * item.quantity

  if (order.country == "US")
    total += total * 0.07 // US sales tax
  else if (order.country == "EU"):
    total += total * 0.20 // European VAT

  return total
getOrderTotal() — afterencapsulated
method getOrderTotal(order) is
  total = 0
  foreach item in order.lineItems
    total += item.price * item.quantity
  total += total * getTaxRate(order.country)
  return total

method getTaxRate(country) is
  if (country == "US"): return 0.07
  else if (country == "EU"): return 0.20
  else: return 0

Nothing about the behavior changed — same inputs, same outputs. What changed is that "how tax is calculated" (the part that varies as new countries are added) is now walled off inside getTaxRate, behind a stable interface: a country in, a rate out.

Encapsulation at the class level

Zoom out one level. The Order class in the slides has 20+ fields (lineItems, country, state, city, ...) and grew a second responsibility: computing tax rates for the US, EU, and China.

Order
- lineItems
- country / state / city
- …20+ fields
+ getOrderTotal()
◇──▶has-a
TaxCalculator
…
+ getTaxRate(country, state, product)
- getUSTax(state)
- getEUTax(country)
- getChineseTax(product)
AFTER: tax logic is pulled into its own class — Order only asks a question, it doesn't know the answer's logic.
⚠ Edge case students miss

Encapsulation is not the same as "make every field private." A class with 40 private fields, all exposed through public getters/setters, is still poorly encapsulated if client code has to read three fields and combine them itself to get useful information — that's "feature envy," and it means the behavior lives in the wrong place.

📝 Likely exam question

"Given a class with a bloated method mixing multiple responsibilities, refactor it using method-level encapsulation." — Expect to be given something like getOrderTotal() and asked to extract the varying part into a helper method. Practice spotting which branch of logic will grow over time (that's always the part to extract).

💡 Brainstorm

What would happen to the TaxCalculator design if a new requirement appeared: "tax rate also depends on the product category (digital goods vs. physical goods) inside the same country"? Where would you add that logic without touching Order at all?

Program to an Interface, Not an Implementation

Scale: Class Contract
Rev: IFC-1
Ref: Slide 6

The slide uses a wonderfully weird example: a Cat that eats Sausage. Let's see why that's fragile.

Cat
- energy
+ eat(Sausage s)
▽depends on
Sausage
…
+ getNutrition()
+ getColor()
+ getExpiration()
BEFORE: Cat is welded to the concrete Sausage class.

The instant your cat needs to eat Fish too, you either duplicate eat() or start littering it with instanceof checks. The fix: introduce a Food interface exposing only what Cat actually needs (getNutrition()), and have every edible thing implement it.

Cat
- energy
+ eat(Food s)
▽depends on
«interface» Food
 
+ getNutrition()
△implements
Sausage
…
+ getNutrition()
+ getColor()
+ getExpiration()
AFTER: Cat only knows about the Food contract — any future food type just implements it.
🎓 Professor's Note — read this twice

Your slide is refreshingly honest here: "After making this change, you won't probably feel any immediate benefit. On the contrary, the code has become more complicated than it was before." This is the single most important sentence in the whole deck for exam essay-questions: abstraction has an up-front cost, and it only pays off if extension actually happens. Don't introduce an interface "just in case" for a class you're certain will never have a second implementation — that's speculative generality, a well-known anti-pattern.

📝 Likely exam question

"When is introducing an interface premature?" — Correct answer references YAGNI (You Aren't Gonna Need It): only extract an interface when you have concrete evidence of a second implementation, a plugin point, or a testing need (mock objects).

Sheet 03 · Foundations

The Diamond Problem

Scale: Inheritance Graph
Rev: DIA-1
Ref: Slide 7

Why doesn't Java, C#, or most modern OOP languages allow multiple class inheritance? This diagram is the reason.

Both ClassA and ClassB implement doSomething(). Which one does ClassC inherit?
Illegal multiple inheritance (pseudocode)won't compile
// this is just an assumption to explain the diamond problem
// this code won't compile
public class ClassC extends ClassA, ClassB{

    public void test(){
        // calling super class method — but which super?
        doSomething();
    }
}

If ClassA.doSomething() and ClassB.doSomething() have different implementations, the compiler has no principled way to decide which one ClassC inherits. That ambiguity is the "diamond."

⚠ Edge case

Languages don't all solve this the same way. Java and C# forbid multiple class inheritance entirely but allow implementing multiple interfaces (which — pre-default-methods — had no bodies, so no ambiguity). C++ allows multiple inheritance but requires explicit disambiguation (ClassA::doSomething()) or virtual inheritance to collapse a shared base. Java 8+ default methods reopened a mini version of this problem for interfaces, resolved by requiring the implementing class to override the conflicting method explicitly.

📝 Likely exam question

"Why does Java disallow multiple inheritance of classes but allow multiple interface implementation?" Be ready to explain the diamond problem in your own words and name at least one language's resolution strategy.

💡 Brainstorm

Composition ("has-a") is often suggested as the cure for diamond-shaped hierarchies — instead of inheriting behavior from two parents, a class holds two collaborator objects and delegates to them. Try mentally redesigning ClassC using composition instead of inheritance. What do you gain? What do you lose (hint: think about polymorphism)?

Sheet 04 · Foundations

Coupling: The Disease Principles Cure

Scale: System
Rev: CPL-1
Ref: Slides 8–9

If encapsulation is a wall, coupling is a measure of how many doors you cut into it. Tight coupling means a class knows too much about the concrete details of other classes; loose coupling means it only knows about abstractions.

Company
…
+ createSoftware()
──▶
Designer
…
+ designArchitecture()
Programmer
…
+ writeCode()
Tester
…
+ testSoftware()
BEFORE: Company directly instantiates new Designer(), new Programmer(), new Tester() — tight coupling.

Every time you add a new kind of employee (an Artist? a DevOps engineer?), you must open up Company and edit its internals. That violates the Open/Closed Principle we'll meet shortly — and it's a maintenance nightmare in any real codebase.

Company
…
+ getEmployees()
+ createSoftware()
△extends
GameDevCompany
…
+ getEmployees()
OutsourcingCompany
…
+ getEmployees()
──▶returns
«interface» Employee
 
+ doWork()
AFTER: Company only knows the Employee interface. Subclasses decide which concrete employees to create.

Now Company.createSoftware() just loops: foreach (Employee e in getEmployees()) e.doWork(). It never needs to change again, no matter how many new employee or company types are invented — new subclasses extend the system instead of modifying it.

⚠ Edge case: coupling vs. cohesion aren't opposites, but they trade off

Zero coupling is not the goal — a system where no class talks to any other class does nothing. The real target is high cohesion within a class, loose coupling between classes. A class should have a tightly focused job internally, but expose only a thin, stable surface to the outside world.

📝 Likely exam question

Given a UML diagram with concrete-to-concrete dependency arrows, identify the tight coupling and redraw it using an interface/abstraction layer, exactly like the Company → Employee refactor. This pattern (concrete dependency ⟶ interface dependency) reappears in every SOLID principle below, so master it now.

Sheet 05 · SOLID

SOLID: The Big Picture

Scale: Program Architecture
Rev: SOLID-0
Ref: Slide 10

SOLID is a mnemonic — five principles, one letter each — meant to make object-oriented designs more understandable, flexible, and maintainable. You now already understand the seed idea behind all five: encapsulate what varies, and depend on abstractions instead of concretions. SOLID just gives that idea five specific faces.

S — Single Responsibility
A class should have one reason to change.
O — Open/Closed
Open for extension, closed for modification.
L — Liskov Substitution
Subclasses must be safely substitutable for their base class.
I — Interface Segregation
Don't force clients to depend on methods they don't use.
D — Dependency Inversion
Depend on abstractions, not concrete implementations.
🎓 Professor's Note

Straight from your slide, in bold for a reason: "The cost of applying these principles into a program's architecture might be making it more complicated than it should be." This will show up as a discussion or short-answer question. SOLID is a tool for managing change in a codebase that will be maintained for years by a team — it is overkill for a one-off script or a throwaway prototype.

💡 Brainstorm

Notice that S and O are about a single class, L is about the relationship between a class and its subclass, and I and D are about the relationship between a class and other classes it depends on. Try grouping the five letters this way in your notes — it's a much easier way to memorize them than alphabetical order.

Sheet 06 · SOLID · S

Single Responsibility Principle

Rule: One reason to change
Rev: SRP-1
Ref: Slide 11

"A class should have just one reason to change." Every class should have a single responsibility, entirely encapsulated by that class.

Employee
- name
+ getName()
+ printTimeSheetReport()
BEFORE: Employee mixes "being an employee" with "formatting reports" — two different reasons to change.
TimeSheetReport
…
+ print(employee)
──▶
Employee
- name
+ getName()
AFTER: printing logic moves to its own class, free to grow (PDF export, CSV export…) without touching Employee.

Why it matters

  • Less fragile code — a bug fix in reporting can't accidentally break employee logic.
  • Low coupling, high cohesion — direct payoff of what we discussed in Sheet 04.
  • Changeability & maintainability — one team can own Employee, another can own reporting.
  • Testability — you can unit-test report formatting without constructing a full employee record, and vice versa.
⚠ Edge case: "responsibility" is not "method"

SRP does not mean "one method per class." A class can have many methods as long as they all serve one cohesive purpose and change for the same reason. The test isn't a method count — it's: "if I list every reason this class might need to change, is it always because of the same stakeholder / same concern?" If Employee changes both when HR policy changes and when the report's PDF layout changes, that's two reasons — two responsibilities.

📝 Likely exam question

"Identify the SRP violation in this class diagram and refactor it." Look for a class name that doesn't describe one coherent noun (e.g., UserAndEmailSender), or a class whose methods naturally split into two unrelated groups.

💡 Brainstorm

Revisit your phone-app example from the intro. Was the "bad update" possibly a case where one class or module took on a second responsibility it shouldn't have (e.g., a messaging feature also started handling payments)?

Sheet 07 · SOLID · O

Open/Closed Principle

Rule: Open to extend, closed to modify
Rev: OCP-1
Ref: Slides 12–17

Classes should be open for extension but closed for modification. Once a class is finished and tested, you should be able to add new behavior without editing its existing source code — only by adding new code (usually a new subclass).

The shipping-cost trap

Order.getShippingCost() — beforemust edit for every new method
if (shipping == "ground") {
  // Free ground delivery on big orders.
  if (getTotal() > 100) { return 0 }
  // $1.5 per kilogram, but $10 minimum.
  return max(10, getTotalWeight() * 1.5)
}
if (shipping == "air") {
  // $3 per kilogram, but $20 minimum.
  return max(20, getTotalWeight() * 3)
}

Adding "Drone delivery" means opening Order and adding another if. Every edit risks breaking the branches that already work and were already tested.

Order
- lineItems
- shipping: Shipping
+ getShippingCost()
◇──▶
«interface» Shipping
 
+ getCost(order)
+ getDate(order)
△
Ground
…
+ getCost(order)
+ getDate(order)
Air
…
+ getCost(order)
+ getDate(order)
AFTER (Strategy pattern): Order.getShippingCost() simply calls shipping.getCost(this). Adding "Drone" = adding a new class, zero edits to Order.

The shape-area classic (C#)

This progression from your slides is one of the cleanest OCP demonstrations in the whole textbook. Toggle between the three stages:

Stage 1 — only rectangles exist, seems fine
public class Rectangle
{
    public double Width { get; set; }
    public double Height { get; set; }
}

public class AreaCalculator
{
    public double Area(Rectangle[] shapes)
    {
        double area = 0;
        foreach (var shape in shapes)
            area += shape.Width * shape.Height;
        return area;
    }
}
Stage 2 — Circle added the tempting wayviolates OCP
public double Area(object[] shapes)
{
    double area = 0;
    foreach (var shape in shapes)
    {
        if (shape is Rectangle)
        {
            Rectangle rectangle = (Rectangle) shape;
            area += rectangle.Width * rectangle.Height;
        }
        else
        {
            Circle circle = (Circle)shape;
            area += circle.Radius * circle.Radius * Math.PI;
        }
    }
    return area;
}

To support Circle, we had to modify the already-working Area() method and give up compile-time type safety by casting from object. Adding Ellipse or Triangle means editing this method again — and again.

Stage 3 — Shape abstraction, OCP restoredextend without modifying
public abstract class Shape
{
    public abstract double Area();
}

public class Rectangle : Shape
{
    public double Width { get; set; }
    public double Height { get; set; }
    public override double Area() { return Width * Height; }
}

public class Circle : Shape
{
    public double Radius { get; set; }
    public override double Area() { return Radius * Radius * Math.PI; }
}

public class AreaCalculator
{
    public double Area(Shape[] shapes)
    {
        double area = 0;
        foreach (Shape shape in shapes)
            area += shape.Area();
        return area;
    }
}

// Adding Ellipse needs zero edits above:
public class Ellipse : Shape
{
    public double majorRadius { get; set; }
    public double minorRadius { get; set; }
    public override double Area() { return majorRadius * minorRadius * Math.PI; }
}

AreaCalculator.Area() is now closed — you will never edit it again — while the Shape hierarchy is open — you can add Ellipse, Triangle, Hexagon forever, each as a brand-new file.

⚠ Edge case

OCP is famously the hardest SOLID principle to apply perfectly in advance, because it requires predicting which axis of variation will need extension. Over-applying it (making everything abstract "just in case") causes needless indirection. The rule of thumb: apply OCP to the parts of the system that have already changed more than once, not to speculative future ones.

📝 Likely exam question

You'll almost certainly be given the "Rectangle + is/cast" code and asked either to (a) point out which SOLID principle it violates and why, or (b) rewrite it using an abstract base class or interface. Practice writing the Shape/Area() refactor from memory.

Sheet 08 · SOLID · L

Liskov Substitution Principle

Rule: Subtypes must honor the contract
Rev: LSP-1
Ref: Slides 18–20

When extending a class, you must be able to pass an object of the subclass anywhere the parent class was expected — without breaking the client code. A subclass should extend the base behavior, never quietly replace or weaken it.

Document
- data
- filename
+ open()
+ save()
△
ReadOnlyDocument
 
+ save() ⇒ throws Exception
BEFORE: ReadOnlyDocument "implements" save() by throwing — this breaks any Project.saveAll() loop that assumes every Document can be saved.
Client code that now crashesviolates LSP
foreach (doc in documents) {
  if (!doc instanceof ReadOnlyDocument)
    doc.save()   // client must know about the subtype — a code smell
}

Notice the client had to add an instanceof check to defend itself. That's the tell-tale sign of an LSP violation: if calling code needs to check the concrete type before calling a method the base class promised, the substitution has already failed.

Document
- data
- filename
+ open()
△
WritableDocument
 
+ save()
AFTER: save() is moved down into WritableDocument. Project keeps two lists — allDocs (opened) and writableDocs (saved) — so no document is ever asked to do something it can't.

The classic four checks (design-by-contract view)

  • Preconditions cannot be strengthened in the subclass (don't demand more than the base method did).
  • Postconditions cannot be weakened (don't promise less than the base method did).
  • Invariants of the base class must be preserved.
  • No new exceptions that the client wasn't already prepared to catch (like ReadOnlyDocument.save() above).
⚠ Edge case: the famous Square/Rectangle problem

This isn't in your slides but is the single most-quoted LSP example in the industry and very likely to appear as a bonus question: if Square extends Rectangle, and Rectangle has independent setWidth()/setHeight(), then a Square must keep both sides equal — meaning setWidth() silently also changes the height. Any client that does setWidth(5); setHeight(10); assert area == 50 will fail for a Square but pass for a Rectangle. Mathematically a square is a rectangle, but behaviorally, forcing that inheritance breaks LSP.

📝 Likely exam question

"Explain why this subclass violates LSP" — usually shown as an overridden method that throws an unexpected exception, returns null where the base guaranteed a value, or narrows an accepted parameter type. State the fix: pull the incompatible behavior into a sibling subclass or restructure the hierarchy, exactly as the Document/WritableDocument example does.

Sheet 09 · SOLID · I

Interface Segregation Principle

Rule: No fat interfaces
Rev: ISP-1
Ref: Slides 21–22

Clients shouldn't be forced to depend on methods they do not use. Keep interfaces narrow enough that implementers never have to write "not implemented" stubs.

«interface» CloudProvider
 
+ storeFile(name)
+ getFile(name)
+ createServer(region)
+ listServers(region)
+ getCDNAddress()
△
Amazon
+ storeFile(name)
+ getFile(name)
+ createServer(region)
+ listServers(region)
+ getCDNAddress()
Dropbox
+ storeFile(name)
+ getFile(name)
+ createServer() — n/a
+ listServers() — n/a
+ getCDNAddress() — n/a
BEFORE: Dropbox only stores files — it has no servers or CDN — yet must "implement" three methods it cannot honor.
«interface» CloudHostingProvider
+ createServer(region)
+ listServers(region)
«interface» CDNProvider
+ getCDNAddress()
«interface» CloudStorageProvider
+ storeFile(name)
+ getFile(name)
AFTER: one bloated interface split into three focused ones. Amazon implements all three; Dropbox implements only CloudStorageProvider — honestly.
⚠ Edge case: ISP and SRP look similar but aren't the same

SRP is about a class having one reason to change. ISP is about an interface (contract) not forcing unrelated capabilities onto every implementer. You can violate ISP even in a language with no interfaces at all, if you use an abstract base class with unrelated abstract methods that not every subclass can meaningfully implement.

📝 Likely exam question

Given an interface where an implementing class throws NotImplementedException or returns a dummy value for one or more methods, that's the signature of an ISP violation. You'll be asked to split the interface by cohesive capability, exactly like CloudProvider → three role interfaces above.

Sheet 10 · SOLID · D

Dependency Inversion Principle

Rule: Depend on abstractions
Rev: DIP-1
Ref: Slides 23–31

Two clauses, and both matter: (1) High-level classes shouldn't depend on low-level classes — both should depend on abstractions. (2) Abstractions shouldn't depend on details — details should depend on abstractions. Memorize the closing line from the slide: "Depend upon Abstractions. Do not depend upon concretions."

BudgetReport (high level)
- database
+ open(date)
+ save()
──▶
MySQLDatabase (low level)
+ insert()
+ update()
+ delete()
BEFORE: the high-level report logic is bolted directly to a specific database engine.
BudgetReport
- database
+ open(date)
+ save()
──▶
«interface» Database
+ insert()
+ update()
+ delete()
△
MySQL
+ insert()/update()/delete()
MongoDB
+ insert()/update()/delete()
AFTER: BudgetReport depends on a Database abstraction. MySQL and MongoDB depend on the same abstraction — the dependency arrow now points "up" toward the interface from both sides.

This is why it's called inversion: naively, you'd expect the low-level detail (database engine) to define the contract and the high-level policy to adapt to it. DIP flips that — the high-level module defines what it needs, as an interface, and low-level modules must conform to it.

Worked example: the light switch (Java)

This is the most detailed worked example in your slide deck, so let's trace it fully.

Without DIPswitch → bulb, hard-wired
public class LightBulb {
  public void turnOn() { …"Bulb turned on"… }
  public void turnOff() { …"Bulb turned off"… }
}

public class ElectricPowerSwitch {
  public LightBulb lightBulb;
  public boolean on;

  public ElectricPowerSwitch(LightBulb lightBulb){
    this.lightBulb = lightBulb;
  }
  public void press(){
    if (isOn()) { lightBulb.turnOff(); on=false; }
    else       { lightBulb.turnOn();  on=true;  }
  }
}
With DIPswitch → any Switchable
public interface Switchable {
  void turnOn();
  void turnOff();
}
public interface Switch {
  boolean isOn();
  void press();
}

public class ElectricPowerSwitch implements Switch {
  public Switchable client;
  public boolean on;
  public ElectricPowerSwitch(Switchable client){
    this.client = client;
  }
  public void press(){
    if (isOn()) { client.turnOff(); on=false; }
    else       { client.turnOn();  on=true;  }
  }
}
Fan.java & LightBulb.java both implement Switchableplug in anything
public class Fan implements Switchable {
  public void turnOn()  { System.out.println("Fan: Fan turned on..."); }
  public void turnOff() { System.out.println("Fan: Fan turned off..."); }
}
public class LightBulb implements Switchable {
  public void turnOn()  { System.out.println("LightBulb: Bulb turned on..."); }
  public void turnOff() { System.out.println("LightBulb: Bulb turned off..."); }
}

The same physical ElectricPowerSwitch object can now control a Fan, a LightBulb, or anything else that implements Switchable — a heater, a pump, a robot arm — with zero changes to the switch's code.

🎓 Professor's Note — the most confused principle

Students often conflate Dependency Inversion with Dependency Injection. They're related but not the same: Dependency Inversion is the design principle ("depend on abstractions"); Dependency Injection is one common technique for satisfying it (passing the concrete Switchable implementation into the constructor, as shown above, rather than the class instantiating it itself with new). You can have DI without full inversion, and you can achieve inversion without a DI framework — but in practice they're best friends.

📝 Likely exam question

"Refactor this class so it depends on an interface instead of a concrete class, and explain which SOLID principle you applied." Also be ready for: "Distinguish Dependency Inversion from Dependency Injection" — this is a favorite trick question.

Sheet 11 · Wrap-up

Self-Check Quiz

Format: MCQ, instant feedback
Rev: QZ-1

Click an answer to check yourself. No grade is recorded — this is just to catch gaps before the real exam.

Q1. A subclass overrides a method and throws a new exception the base class never declared, breaking code that used the base class. Which principle is violated?
Correct: Liskov Substitution Principle. Substitutability breaks exactly when a subclass surprises client code that trusted the base class's contract — new unexpected exceptions are a classic LSP violation, just like ReadOnlyDocument.save().
Q2. A class implements a 6-method interface but can only meaningfully support 2 of them, stubbing the rest with "not implemented." Which principle addresses this?
Correct: Interface Segregation Principle. Split the fat interface into smaller, role-specific ones, like CloudProvider → CloudStorageProvider / CloudHostingProvider / CDNProvider.
Q3. Every time a new shipping method is added, developers must edit and re-test the Order class's existing getShippingCost() method. Which principle is violated?
Correct: Open/Closed Principle. The class is not "closed for modification" — every new shipping method forces an edit. The fix is the Strategy pattern with a Shipping interface.
Q4. A high-level BudgetReport class directly instantiates and calls MySQLDatabase. Switching to MongoDB later requires rewriting BudgetReport. Which principle fixes this?
Correct: Dependency Inversion Principle. Introduce a Database abstraction that both BudgetReport and every concrete engine depend on.
Q5. Why does Java forbid a class from extending two classes, but allow implementing many interfaces?
Correct: it's the diamond problem. Two parent classes could hold conflicting concrete implementations of the same method, and the compiler has no principled way to choose.
Sheet 12 · Wrap-up

Recap & Reference

Rev: FIN-1

One-line recap of everything

  • Encapsulation — wall off what varies (method level and class level).
  • Interface > Implementation — program against a contract, not a concrete type; but only when a second implementation is real, not hypothetical.
  • Diamond Problem — the reason languages restrict multiple class inheritance.
  • Coupling — minimize how much a class knows about the concrete details of others.
  • Single Responsibility — one class, one reason to change.
  • Open/Closed — extend via new code, don't modify tested code.
  • Liskov Substitution — a subclass must never surprise code written for the base class.
  • Interface Segregation — no client should depend on methods it doesn't use.
  • Dependency Inversion — depend on abstractions, not concretions, in both directions.
🎓 Professor's closing note

If you remember nothing else from Lecture 1: every one of these principles is trying to keep the "cost of change" flat as software grows. The moment you're tempted to say "just add another if-statement" or "just cast it to the type I need," pause — that instinct is almost always the seam where one of these five letters wants to be applied.
